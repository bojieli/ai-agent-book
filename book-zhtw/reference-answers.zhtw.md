# 思考題參考答案

參考答案由 AI 生成，經人工略作審校。

## 第一章 AI Agent 入門

**1. (★★) 如果只能優先改進模型、上下文或工具中的一項，你會如何判斷最值得投入的位置？哪些評估結果會使你改變選擇？**

> 可以先檢查模型是否拿到了完成任務所需的資訊，這一步能直接發現遺漏，也便於局部修復。再分析失敗軌跡：缺少業務事實、歷史決定或任務狀態時，改進上下文；缺少觀測或執行介面時，補充工具；已有充分資訊和合適工具，模型仍難以完成推理時，再比較更強模型。用相同任務集分別調整一項，記錄完成率、錯誤類型、時間和成本。

**2. (★★★) 假設每輪新增的訊息量大致相同，且每輪都向模型提供此前的完整歷史，為什麼累計輸入量會隨輪數近似二次方增長？快取、壓縮和歷史裁剪分別改變了哪些成本？**

> 先只數訊息歷史，假設每輪新增 100 個 token。前三輪分別送入 100、200、300 個 token。第三次請求中的歷史只有 300 個 token，三次請求合計卻已送入 600 個。前一個數可以從第三次請求讀出，後一個數要把三次用量記錄中的歷史輸入相加。一般地，每輪新增 $m$ 個 token，第 $i$ 輪送入約 $mi$ 個，前 $n$ 輪累計約為 $mn(n+1)/2$。若另有長為 $P$ 的固定系統提示詞，每輪都要計入輸入，總數還要加上 $nP$。
>
> 仍只數上例的訊息歷史。假設服務從第二輪起都能完整複用上一輪的輸入，第二輪命中 100 個 token，第三輪命中 200 個。三輪合計，600 個輸入 token 中有 300 個命中快取，另有 300 個首次處理。快取複用了那 300 個 token 的前綴計算。
>
> 壓縮用較短摘要替換歷史，會產生摘要呼叫和快取重建開銷；裁剪直接移除部分歷史，需要保留目標、狀態及呼叫與結果的配對。可優先在階段邊界或長度閾值處批次處理歷史，減少逐輪壓縮帶來的摘要呼叫、快取重建與多次壓縮造成的資訊損失。將大塊產物移到外部儲存後按需讀取，或用子 Agent 隔離探索過程，再比較資訊損失與成本。

**3. (★★) 模型承擔越來越多的工具呼叫決策，Harness 也需要支援更長、更複雜的任務。兩者的職責會怎樣變化？哪些機制可以簡化，哪些需要加強？**

> 模型能夠直接規劃和選擇工具後，固定路由、格式修補和部分啟發式提示可以逐項簡化。任務越長，Harness 越需要組織上下文、管理工具介面，並執行約束、驗證和糾正。可加強的機制包括權限校驗、預算與超時、重複呼叫偵測、持久狀態和錯誤恢復。每次模型升級後，透過任務對照評估決定哪些規則可以減少；身份、授權和外部執行仍由可信執行階段與環境負責。

**4. (★★) 實驗中缺少工具結果會導致重複呼叫。在生產系統中，還有哪些原因會造成類似迴圈？如何偵測、恢復並設定終止條件？**

> 常見原因包括工具持續回傳相同錯誤、模型反覆請求不存在的能力、壓縮丟失已完成狀態、訊息格式不符合介面要求，以及任務缺少必要輸入。可結合工具名、參數、回傳結果和狀態變化偵測重複行為；發現迴圈後先核對錯誤原因，再補充資訊、調整路徑或恢復狀態。執行階段設定輪數、時間、費用和連續失敗上限，達到限制時儲存進度，並按任務規則結束或移交。

**5. (★) 選擇一個日常使用的 AI 產品，分別列出上下文中的主要資訊、可用操作和執行策略。它在哪個環節最容易失敗？你會如何改進？**

> 例如，分析一個旅行助手：上下文包含目的地、日期、預算、使用者偏好和已有查詢結果；操作包括搜尋航班、查詢飯店、修改草案和請求確認；執行策略可以將自主檢索與固定預訂流程結合。若它反覆推薦超預算方案，應檢查預算是否進入目前輸入、價格是否及時更新、篩選規則是否落實，再透過同一組行程任務評價改進。

> 可以把同一個報價放到兩次委託裡測試。兩位使用者都想買 1200 元以內的機票，客服報出的最低價都是 1250 元。一位商務旅客過去遇到這種小幅超支時更看重按時抵達，另一位帶家人出遊，每次都會先核算總預算。如果兩人都委託了助手代訂，按照前一位旅客一貫的取捨，助手可以接受這 50 元差價，訂好後告訴他實際票價。對後一位旅客，助手應先發去報價，請他決定。再給商務旅客的委託加一句「這次報銷上限就是 1200 元」，助手也要停在出票之前。如果商務旅客事後說這次多花的 50 元他不能接受，就應記住這次糾正，下次遇到類似報價先問他。等使用者答覆時，助手還可以向客服詢問能否暫時保價，或者查詢別的航班。

**6. (★★) 為航班訂票客服設計一套流程：哪些步驟適合工作流，哪些適合自主 Agent？使用者臨時改變行程時，兩部分如何配合？**

> 把身份核實、訂單狀態檢查、價格確認、付款和預訂組織為有明確前置條件的流程；將需求澄清、替代航班搜尋和方案比較交給自主 Agent。付款與出票的先後、佔座與超時規則按照具體業務介面執行。使用者改變日期後，更新行程版本，取消失效報價和待執行操作，再重新核對價格與授權。退款、大額付款等操作按風險規則請求確認，並透過回執檢查結果。

**7. (★★★) 同一個 `delete_file` 工具，刪除臨時檔案與刪除關鍵系統檔案的風險不同。你會怎樣結合參數、資源範圍和可恢復性進行動態風險評估？**

> 風險評估應同時考慮工具類型、參數、目標資源、呼叫者身份和操作後果。先由伺服器端解析並規範化目標路徑，檢查真實資源是否落在授權範圍內，再考慮檔案重要性、刪除規模、備份與恢復能力。軟連結和檢查後資源變化也需要在執行環節處理。低風險臨時檔案可按規則直接清理，關鍵資源則採用預覽、確認或禁止刪除等策略，並儲存結果記錄。模型提供任務意圖，執行階段落實存取控制。

**8. (★★) 開放式動作空間允許難以預先窮舉的內容與操作組合。在什麼任務中，把行動限制為少量預定義選項更合適？這種限制會帶來哪些收益與代價？**

> 退款、付款和帳戶狀態變更適合採用預定義操作與結構化參數，使金額範圍、狀態轉換和授權條件容易檢查。限制選項能減少無效組合，便於測試和追蹤，也會降低處理新需求的靈活性。可以為範圍內的任務提供明確操作，為超出範圍的請求設定澄清、人工處理或受控擴展入口，並用真實用例檢查覆蓋率。

**9. (★★) Agent 需要人工確認時，使用者可能不在線上、回覆緩慢或指令含糊。系統應儲存哪些狀態，可以繼續哪些工作，哪些操作必須等待？**

> 儲存原始目標、已完成事項、待確認操作、目前參數、授權狀態和相關產物版本。可繼續開展已獲授權且相互獨立的資料整理等工作；需要確認的支付、刪除或對外提交保持等待。按使用者選擇的管道通知，設定提醒與超時規則。回覆含糊時繼續澄清；恢復執行前重新檢查價格、庫存、身份與環境狀態，確認原操作仍然有效。

**10. (★★★) 舉一個會隨模型進步而簡化的工程方法，說明它原先解決什麼問題，以及背後的系統設計原則如何繼續發揮作用。**

> 例如，模型更穩定地生成結構化呼叫後，可以減少專門修補 JSON 和補齊參數的邏輯；介面 Schema 校驗、授權檢查與錯誤處理繼續保障呼叫可靠性。

> 外部知識庫也可以隨學習能力變化調整分工：部分穩定知識進入模型參數，即時更新、精確檢索、權限控制與來源追溯由外部系統承擔。

> 能力介面可以從大量專用工具擴展到「Skill 文字規程 + 通用執行器」。模型理解介面與遵循規程的能力增強後，越來越多的操作可以由通用執行器承接，專用工具的數量也就可以減少。模型根據規程生成命令，執行階段檢查參數與權限；標準化呼叫負責傳遞結構化參數，支援校驗和跨系統互操作。

> 提示詞與工具定義也可按需載入。早期實作常把它們放在固定位置，幫助模型識別與遵循；指令遵循能力提高、訓練覆蓋動態載入後，Skills 和動態發現的工具能夠追加到後續上下文，減少預先提供的內容。

## 第二章 上下文工程

**1. (★★★) 閱讀實驗 2-3 的滑動視窗執行記錄：五次工具呼叫分別做了什麼？要判斷重複呼叫是否由歷史裁剪造成，還需要記錄什麼、做什麼對照？設計一種保留關鍵狀態的裁剪方案，並說明它對前綴快取的影響。**

> 實驗 2-3 的滑動視窗記錄（`result_sliding_window_20260718_kimi_k2_6.json`）中，`task` 寫著使用者要求列出 Python 檔案，讀完 `main.py` 和 `agent.py`，用三句話總結。`tool_calls` 列出了五次呼叫：前三次都是 `find("*.py")`，每次都找到了 13 個檔案；後兩次各讀一個指定檔案。對照委託，到這裡還差最後的三句話。一輪回覆可以請求多個工具，單憑五條呼叫記錄無法把它們逐一對應到五輪模型請求。記錄儲存了工具呼叫，卻沒有逐輪儲存發給模型的完整訊息。目前實作每輪都會附上原任務。要檢驗裁剪是否造成重複，可以記下每輪保留和移除的訊息 ID，固定模型、任務與輪數上限，比較完整歷史和滑動視窗下的重複次數及完成率。
>
> 一種做法是把已讀檔案、關鍵結果和待辦寫入階段摘要，大段輸出歸檔並保留索引，近期的工具請求與結果成對保留。替換歷史會影響修改點之後的前綴快取；排在修改點之前的系統指令和工具定義仍有機會複用。另一種做法是把檔案探索交給子 Agent，讓它只把結論和檔案位置帶回主對話。

**2. (★★) Qwen3 的 Chat Template 按最後一個真實使用者查詢的位置處理歷史思考。若一次 ReAct 迴圈持續上百輪，你會如何管理逐漸增長的推理內容？請比較歷史思考的裁剪、回傳與前綴綁定協定，並說明 Harness 應如何適配。**

> 先按模型與介面協定決定哪些推理內容必須回傳，再設定歷史預算。歷史推理可能承載尚未執行的計畫和已排除的路徑，長程任務更需要保留這類狀態；直接刪除會使後續決策失去依據，完整回傳則會增加輸入量。允許裁剪的協定可保留近期推理，並把長期計畫整理為狀態摘要；要求回傳的介面應儲存原始回應欄位。若 thinking 與前綴綁定，改寫前綴後需按協定處理受影響的推理塊，或使用伺服器端壓縮。

**3. (★★) 假設要把約十五萬字元的搜尋材料壓縮到兩千字元，你會保留哪些事實、關係與來源？怎樣檢查摘要是否足以支持後續問題，又怎樣恢復被省略的細節？**

> 保留人物、時間、機構、關係、關鍵證據與尚未解決的問題，並原樣儲存用於定位的識別碼。為摘要設計後續查詢，檢查遺漏和歧義；將原始材料歸檔，儲存來源、抓取時間及讀取入口。連結幫助定位，原文快照支援長期複核。

**4. (★★) 工具計數器漏記了一次呼叫，狀態列因此給出錯誤的剩餘次數。請設計事件記錄、彙總校驗和執行層檢查，說明如何發現並修復這種不一致。**

> 呼叫次數優先由程式統計。需要模型從非結構化記錄提取事件時，也先逐條提取，再由程式彙總，減少長歷史中的漏計與重計。為呼叫建立唯一事件 ID，記錄請求、執行和回傳狀態，並明確上限針對呼叫嘗試次數還是成功次數。透過冪等更新避免重記，透過事件重放和定期對帳發現漏記。執行層根據可信計數檢查是否仍有呼叫額度，模型讀取狀態用於規劃。發生不一致時保留事件記錄，重建彙總後再繼續；來源不明的文字應作為待核實材料處理。
>
> 例如，執行器接受呼叫 A 後，同一條「已接受 A」的通知投遞了兩次。按呼叫標識歸併，兩條通知只消耗一次預算。若預算按實際執行次數計，另一次真正發起的重試就應有獨立的執行標識，並關聯到原請求。

**5. (★★) 實驗 2-4 比較了語氣、資訊組織與工具描述。若系統提示詞由多人長期維護，你會如何管理版本、檢查規則衝突，並用迴歸任務評估每次修改？**

> 將提示詞納入版本管理與評審，由業務、營運和工程人員共同檢查流程與邊界。維護典型任務、邊界案例及已知失敗的迴歸集，每次修改記錄目標和結果。使用 Markdown/XML 組織規則，檢查重複與衝突；穩定規則放在上下文中可複用的前部，動態狀態按訊息追加，專項流程可拆成 Skills。

**6. (★★★) 寵物店案例同時包含單條檢索與總體統計。請設計原始記錄、統計摘要和查詢路由，使系統能高效回答這兩類問題，並說明摘要需要在什麼時候更新。**

> 逐籠記錄按籠號索引，各顏色對應的數量由程式根據新增、移除和變更事件增量維護。單籠查詢讀取對應記錄，數量查詢讀取統計摘要，涉及新維度的問題回查原始資料。定期重算總數與增量狀態對帳。跨會話需要保留這些狀態時，將記錄與索引持久化，並在新任務中按需載入。

**7. (★★★) 一個 Skill 已在目錄中，但模型沒有發現它適用於目前任務。你會如何從描述、目錄組織、顯式觸發和評估樣例四個方面排查問題？**

> 檢查 Skill 名稱和描述是否覆蓋真實任務表達，補上具體觸發條件與容易混淆的邊界。目錄較大時可按任務檢索候選項。顯式觸發提供直接載入路徑；評估集同時包含應該觸發、不應觸發及描述相近的案例，分別統計漏選和誤選。

**8. (★★) Skill 已經成功載入，模型卻漏掉了其中的驗證步驟。請設計一個對照實驗，區分觸發、理解、工具使用和完成判斷中的問題，並比較不同模型的表現。**

> 固定任務、工具和 Skill 版本，分別測試自主觸發與顯式載入。先查發給模型的訊息裡有沒有 Skill 正文。再固定已載入的正文，分別給它「驗證交付物」和一條寫明檢查對象、命令與通過條件的指令，比較模型是否發起了驗證。對已經發起的呼叫，分別回傳預先準備的成功和失敗結果，觀察模型會不會在檢查失敗後照樣宣告完成。這樣能分別統計漏載入、漏呼叫和錯誤收尾的次數。不同模型使用各自支援的訊息協定，在相同產物標準下比較。快取成本可以用三份連續請求來查。首次把 Skill 正文追加一次，此後原樣保留，只要伺服器端仍有有效快取且前綴、分塊和快取邊界滿足命中條件，這段正文就能複用。若每輪又在末尾追加一份，新副本需要計算，原前綴仍可命中。若先刪掉舊位置的正文，再把它移到最新一輪，前綴從舊位置起已經改變，該位置之後的快取通常就無法直接複用。

**9. (★★★) 系統包含大量工具，工具集合又經常變化。你會如何安排固定定義、工具目錄、按需載入結果與執行階段狀態的位置？請同時考慮發現準確率、上下文預算和快取命中。**

> 將高頻穩定工具放在前部並固定順序，用目錄和工具搜尋按需提供其餘定義。新增內容按介面支援的方式載入，避免無關變動擴散到已有前綴。動態狀態放在後部，並選擇替換或追加策略。父子 Agent 可複用共同的穩定指令；各自的權限和任務差異應明確表達。

## 第三章 使用者記憶和知識庫

**1. (★★) 使用者說：「5 月 1 日我從 A 搬到 B，5 月 10 日至 20 日住飯店 C，這期間帳單寄電子郵件。」5 月 15 日，助手應怎樣回答家庭住址、臨時住處和帳單送達方式？請設計記錄與查詢規則，說明如何處理筆誤更正或相互衝突的地址。**

> 5 月 15 日，家庭住址是 B，臨時住處是飯店 C，帳單應寄電子郵件。給每條記錄保留用途、生效區間、來源會話和使用者原話。搬家使 A 的家庭住址記錄在 5 月 1 日前有效，B 自當天起生效；飯店和郵件要求僅適用於 5 月 10 日至 20 日。查詢時同時匹配用途和目標日期，因此今天回查 4 月 30 日的家庭住址仍應得到 A。
>
> 使用者明確更正筆誤時，修訂對應記錄並保留更正依據。兩條記錄若在同一用途、同一時段給出不同地址，又沒有足夠證據解釋差異，就保留兩處來源並向使用者確認。

**2. (★★) 原始文件包含矛盾資訊時，上下文前綴可能把錯誤一起寫入索引。你會怎樣儲存來源、版本和不確定項，並在檢索與生成階段使用這些資訊？**

> 假設舊手冊寫著「簽收後 7 天內可退」，新版改為 14 天，註明「適用於 6 月 1 日起下的訂單」。如果給新版的每個分塊都加上「退貨期為 14 天」，搜尋一筆五月的訂單時，前幾條結果可能全是 14 天，卻都來自同一句漏掉條件的概括。建索引時把生成的前綴與原文分開存，記下文件版本、發布日、生效條件、存取權限和引用段落。兩版條款互相連結，方便查明哪一條適用於這筆訂單。
>
> 可以用兩筆訂單驗收：一筆 5 月 31 日下單、6 月 2 日簽收，另一筆 6 月 1 日下單、同日簽收。先限定使用者有權查閱的手冊，再按下單日期找適用版本，核對原文後分別答 7 天和 14 天，並引用條款。若新版只寫了發布日期，沒說從哪批訂單起生效，就保留兩條來源，指出還缺哪項規定。這樣也能檢驗系統會不會把多個分塊裡重複出現的前綴誤當成多份獨立證據。

**3. (★★) 將圖表轉換為文字後，哪些空間關係容易丟失？請用表格、架構圖或折線圖舉例，設計原圖、結構化表示和文字索引協同檢索的方案。**

> 例如，表格中的合併表頭決定一個數值屬於哪個年份和地區。僅儲存「收入100」會丟失這組關係。可以同時儲存原圖、頁碼與區域座標，以及包含列標題、欄標題、數值和單位的結構化儲存格。文字索引用於定位，回答時讀取結構化記錄，遇到歧義再檢視原圖；架構圖還應保留節點、連線方向和包含關係。

**4. (★★★) 隨著模型和長上下文能力提升，分塊、索引和檢索流程中的哪些工作可能交給模型？請結合 Rich Sutton「苦澀的教訓」中對搜尋和學習的討論分析，並設計實驗比較全量輸入與按需檢索，同時檢查任務品質、計算成本和權限約束。**

> 模型可能承擔分塊邊界選擇、查詢改寫和結果整合，部分手工配置會隨能力進步而簡化。檢索和模型提煉本身也在使用搜尋與學習的方法。比較時固定資料、問題與模型，分別執行全量輸入、單次檢索和多輪檢索，並隨資料規模增長測量品質、延遲和費用。加入跨文件統計、精確條款、更新事實和權限差異等任務，檢查方法在哪些條件下仍有效。統計可以交給可驗證的聚合計算，權限則由輸入構造和執行層強制實施。

**5. (★★★) 如果模型已經掌握大量領域知識，外部知識庫還應儲存什麼？請分別討論公開常識、持續更新的規則、私有資料和需要精確追溯的證據。**

> 穩定公開知識可以主要依靠模型，但最新規則需要版本和生效範圍，私有資料需要存取控制，精確論證需要來源與原文。外部知識庫還支援更正、刪除和稽核。

**6. (★) RAPTOR 的多層摘要與 GraphRAG 的實體關係、社群摘要分別支援哪些查詢？請為總體概覽、局部細節和多跳關聯各舉一例，並說明需要檢查什麼證據。**

> RAPTOR 的高層摘要適合總體概覽，底層材料支援細節，檢索時可以結合不同層次的內容。GraphRAG 的局部實體關係支援「使用者—醫生—醫院—地址」等關聯查詢，社群摘要支援主題概括。例如，要概覽一本處理器手冊介紹了哪些指令擴展，可以先從摘要列出主題，再對目錄檢查是否漏了一整類。若只問 XCR0 的某一位表示什麼，就應翻到暫存器說明，核對位號和定義。圖3-11 問的是「我的牙醫所在醫院的地址」。從使用者本人出發，沿牙科就診關係找到張醫生 A，再查仁愛口腔醫院的地址。如果從使用者的父親出發，找到的會是心內科的張醫生 B。即使最後查到的醫院地址完全正確，前一步認錯了人，答案照樣錯。

**7. (★★) 目錄、連結與向量索引如何協同組織知識？請設計一個需要人和 Agent 共同維護的知識庫，說明導航、語義搜尋、版本更新與權限過濾各自的位置。**

> 以公司差旅手冊為例。員工知道要找「改票」，可以沿目錄翻到「差旅 → 機票 → 改票」，再順著條目裡的連結檢視報銷規則。如果他只記得「臨時換航班多花的錢能報嗎」，向量檢索可以幫他找到同一條規定；如果手頭有條款編號，用關鍵詞查更直接。入口頁的摘要足以指路，涉及金額和例外條件時，還要開啟生效版本的原文。
>
> 人和 Agent 都編輯同一套可讀、可做版本管理的檔案。財務人員修改改票規定後，要同步更新入口摘要、相關連結和受影響的檢索索引。用舊規定中的一句話再查一次，看回傳的是否已經是新版本。若協議價只有採購人員可見，還要用普通員工身份分別查目錄、搜尋和原文，確認標題、摘要和搜尋片段都遵守與原文相同的權限。

**8. (★★★) 從案例中提取欄位並聚類後，怎樣判斷原型有用？請區分聚類特徵的重要性、結果預測能力與因果解釋，並設計留出評估和專家複核流程。**

> 先檢查欄位提取是否準確、缺失處理是否一致，再看簇內共同特徵、簇間差異和重複取樣的穩定性。用於區分各簇的特徵及其權重，描述的是分組結構；預測能力需要在留出樣本上評價；因果解釋還需要控制混雜、選擇合適設計及領域證據。以實驗 3-12 為例，可以在 360 條建模材料上確定欄位、缺失值處理方式和聚類中心，然後固定這套流程，給 60 條留出材料分配原型。請專家先獨立讀原文，再核對歸類理由；既抽查典型成員，也查離中心最遠和難以歸類的案例。如果還主張原型能預測某個結果，就要事先指定預測目標，在留出材料上與簡單基線比較，並避免讓提取欄位洩露這個結果。

**9. (★★★) 為 Markdown 使用者記憶庫設計增量更新與定期整理流程。若審核者與提議者使用相同模型，且審核者只能看到提議者挑選的片段，哪些錯誤容易遺漏？請從證據覆蓋、工具權限和審核評估三個方面改進。**

> 增量更新時，提議者檢索舊知識，提交範圍儘量小且完整的改動及其來源，同時維護連結、索引和時間資訊。審核者獨立回查，程式檢查格式、連結、後設資料與權限標籤，通過後合入並更新受影響的索引。定期整理按覆蓋清單去重、合併、調整目錄並核查原始材料，重組仍走同一審核流程，候選透過檢索任務迴歸後發布，再持續觀察實際檢索效果。只看選定片段容易漏掉否定條件、時間變化和跨檔案衝突；相同模型還可能重複相似誤讀。給審核者開放授權範圍內的完整證據檢索與檢查工具，分別限制分支寫入、審核和發布權限。用預先植入的錯誤變更評估發現率，比較不同模型組合與證據範圍，並設定迭代預算和人工處理入口。

## 第四章 工具

**1. (★★) MCP 將工具接入與 Agent 框架分開。請選擇串流結果、雙向互動或長任務狀態管理中的一種需求，說明它需要哪些協定能力、哪些宿主能力，並討論接入現有 MCP 時需要補充的設計。**

> 以長任務為例，可以把「提交計算」和「獲取結果」分開：提交後回傳任務 ID，後續透過狀態查詢或通知獲取進展。伺服器端需要儲存任務狀態與產物，約定排隊、執行、完成、失敗和取消的轉換；宿主需要儲存任務 ID，在斷線後恢復查詢，並把新結果送回正確的 Agent 任務。接入時還要檢查所用 MCP 版本、擴展與用戶端支援情況，再決定使用已有能力還是補充明確的業務工具。協定連線關閉、用戶端停止等待、背景任務取消，是三個需要分別處理的狀態。還可以關注跨會話的事件編排：新郵件和外部回呼需要喚醒相應任務，排隊、恢復與重試也需要統一約定。
>
> 可以關掉正在顯示進度的視窗，再用儲存的任務編號重新開啟。若還能取得同一任務的最新狀態，說明任務生命週期與視窗已經分開。然後顯式取消任務，再檢查執行器是否真的停止。

**2. (★★) 多個 MCP 伺服器提供相似工具時，應如何選擇？以「一個回傳摘要，另一個回傳全文」為例，設計工具描述、來源標識和選擇依據，讓 Agent 能夠利用這種差異。**

> 假設目錄服務回傳摘要，典藏服務提供全文。宿主可以給兩項工具分別取別名 `catalog.summary` 和 `archive.read_full`，把每個別名綁定到已配置的伺服器身份和該伺服器發布的工具名。描述中寫清各自覆蓋的資料、回傳內容、分頁方式、更新頻率與呼叫成本。模型要從一批檔案裡挑候選，先查目錄；要核對某條原文或引用條件，就讀全文。宿主按綁定關係調度，並核對服務版本與授權範圍。
>
> 用一份有兩個版本的合約試走一遍：摘要能否給出典藏服務也認識的文件標識和版本？如果能，就帶著它們讀取對應原文；如果兩套服務的編號不通用，就按來源連結重新定位並核對版本。這樣既檢驗了工具描述是否符合實際回傳值，也能發現「摘要選對了，開啟的卻是另一版」的錯誤。

**3. (★★) 除了寫入程式碼後執行檢查，「執行—驗證—回饋」還能用於哪些場景？請選擇兩個例子，說明驗證方法、失敗回饋及成本，並討論何時適合立即驗證、抽樣驗證或非同步驗證。**

> 第一個例子是修改配置：先檢查格式與欄位，再在隔離環境中啟動服務，讀取健康狀態或行為結果。失敗時回傳出錯欄位、啟動診斷和實際狀態，幫助 Agent 判斷應修改配置還是恢復原值。第二個例子是生成簡報：渲染頁面，檢查文字是否溢出、圖表是否遮擋，並把頁碼和位置回饋給生成者。格式檢查開銷較低，可以立即執行；只改一頁正文，可以先渲染改動頁和相鄰頁。換了整套母版，就值得在背景渲染全稿，交付前讀回每頁的檢查結果。抽樣決定查哪些頁，非同步執行決定何時等待結果；兩種選擇可以並用。
>
> 外部操作也可以查詢執行結果。例如，郵件提交後讀取伺服器端訊息狀態，訂單建立後按業務編號查詢記錄。應選擇讀取狀態、回執或稽核記錄的驗證介面，並區分「已接收」「已完成」等不同含義。涉及外部影響時，事前核准與事後驗證各自承擔相應職責。

**4. (★★) 面對數千個工具，除了主動發現，還可以怎樣組織能力？結合分類目錄、工作流範本或通用執行器，說明一種方案的適用條件與取捨。**

> 對重複度較高的業務，可以把常見任務整理成工作流範本。例如，資料彙總範本規定「搜尋候選—讀取正文—核對來源—生成報告」，每一步只提供相關工具。範本減少同時暴露的定義，也幫助模型理解步驟間的資料依賴，適合流程穩定、輸入差異可控的任務。遇到新任務時，需要保留調整步驟或補充工具的入口。
>
> 還可以組合其他方法：按領域組織目錄，常駐少量高頻工具；將詳細用法寫入 Skill，按需讀取；用通用程式碼執行器呼叫穩定的函式庫或 API，減少專用介面數量。

## 第五章 Coding Agent 與通用 Agent

**1. (★★) 為一個需要讀取專案檔案、安裝依賴和執行測試的 Coding Agent 設計沙盒。你會如何配置檔案、網路、處理程序和資源權限？任務需要擴大權限時，怎樣表達請求、檢查範圍並保留記錄？**

> 先列出任務必需的存取：專案工作副本可寫，參考資料唯讀，依賴透過批准的源獲取。用獨立執行環境限制處理程序、執行時間、記憶體和磁碟；憑證由受信任服務保管。擴大權限時說明目標資源、操作、期限與原因，由執行層檢查並記錄授權。用建構、測試和資源超限用例檢驗配置。

**2. (★★★) 建立者連續生成和修改多代 Agent 時，框架缺陷與領域錯誤可能逐步累積。如何用參考版本、迴歸測試、行為評估和回退機制追蹤這種變化？**

> 分別儲存參考框架、每代產物及需求的版本，記錄生成來源和變更。迴歸集同時覆蓋訊息協定、工具關聯、狀態恢復和真實領域任務，並保留獨立任務檢查泛化。其中應有足夠困難且結果可驗證的任務；簡單樣例容易掩蓋代際累積的缺陷。比較新舊版本的成功率、成本與失敗類型，驗證通過後發布；發生退化時恢復最近通過驗收的版本。
>
> 例如，把同一個小專案固定在同一提交，讓初始版和下一代 Agent 各修一次同樣的錯誤。新版本即使修好了目標錯誤，仍要執行原有測試，再讀兩份補丁，看是否把針對這一題的特例寫進了通用框架。

**3. (★★) 日誌格式變化可能來自正常升級，也可能來自生產者缺陷。自適應解析系統應保留哪些證據，依據哪些條件決定新增解析器、報告異常或暫停處理？**

> 儲存原始日誌、生產者版本、變更說明和舊解析器結果。先對照介面約定檢查欄位含義、型別與取值，再驗證正常及異常樣本。已確認的格式升級進入解析器迭代；含義衝突、資料缺失或來源不明的變更寫入問題報告，必要時暫停相關處理。新解析器與告警記錄可以同時保留。

**4. (★★) 提議者—審核者迴圈中，審核者認為頁面資訊密度合理，使用者卻覺得擁擠。如何把使用者偏好轉化為示例、評分條件和互動回饋，並檢查後續修改是否符合要求？**

> 請使用者標註可接受和過於擁擠的頁面，形成字號、留白、資訊密度等具體標準。審核回饋帶頁碼和問題位置，修改後展示同一頁面便於對照。偏好記錄包含使用者、任務和適用範圍，後續任務按範圍引用；抽樣複核可以發現審核標準與使用者體驗的偏離。

**5. (★★) Coding Agent 可以更新知識庫、架構文件和專案指令，也可以把操作序列固化為程式碼。如何識別冗餘或過時的規則，為規則設計適用範圍、驗證方法和退出條件？從一次成功修改發展為第九章討論的持續進化，還需要哪些積累與評估機制？**

> 每條規則記錄來源、適用範圍、驗證用例及最近檢查時間。重複規則合併，失效規則隨版本歸檔，穩定且可判定的要求進入 Linter、測試或工具校驗。例如，原指令要求用 `pnpm test`。某個工作區遷移了包管理器後，先在乾淨檢出中用新命令跑通持續整合裡的測試，再替換該工作區的指令；仍使用 pnpm 的子專案繼續按原命令驗證。這就給出了舊規則退出的條件和範圍。先用歷史任務驗證規則變化，再檢查新任務收益。持續進化還需要把執行證據積累、候選修改、獨立評估、發布與回退組織成長期迴圈。

**6. (★) 對遠端協作友好的團隊通常也便於 Agent 獲取工作資訊。請檢查一個熟悉專案的需求、架構、決策記錄和驗收標準，列出最需要補充的文件，並說明它們能幫助 Agent 完成哪些具體任務。**

> 可用新成員首次接手專案的過程自查：能否找到需求背景、架構關係、建構方法、測試入口和驗收條件。優先補充影響目前任務的知識，例如解釋一個模組的職責、記錄一次技術取捨、提供可執行的驗收用例。只靠口頭傳遞的約定很難進入 Agent 的輸入，團隊日常討論形成的決定也應留下可檢索記錄。明確文件負責人和更新觸發條件，在修改程式碼時同步維護相關資料。

**7. (★★★) 對同時存取私有資料、處理不受信任內容、進行外部通訊並使用持久記憶的 Agent，如何安排身份授權、來源標記、資料流檢查與記憶寫入審核？請用一條正常業務流程說明這些檢查的位置。**

> 以讀取客戶資料並傳送服務通知為例：身份服務確定可存取客戶，資料來源與外部網頁分別標記，通訊介面檢查收件人和允許傳送的欄位。任務完成後，記憶寫入檢查來源、必要性、敏感程度及有效期。資料讀取、對外發送和跨會話儲存分別記錄，便於複核異常及撤銷失效授權。

**8. (★★) 在 SQL 與 HTML 的 Artifact 模式中，模型生成產物，執行服務處理查詢或渲染，介面直接呈現結果。哪些資訊適合再交給模型解釋？如何檢查查詢權限、資源預算、頁面隔離和展示結果的一致性？**

> 完整表格可由執行服務直接呈現，省去模型逐項生成資料的時間與 token，也減少數值抄寫錯誤。需要歸納或決策時，模型再按需讀取聚合結果、異常行和欄位解釋。查詢使用受限帳號與結構校驗，限制可存取資料、函式和執行預算；頁面在隔離環境中渲染，宣告式元件仍檢查屬性與動作。用參考查詢和頁面值對照檢查結果，再核對單位、日期與統計定義。

**9. (★★) 工具根據資料庫中的業務狀態校驗規則，參數說明則幫助模型準備呼叫。請以取消預訂為例，說明自然語言政策、參數例子、執行層校驗和邊界測試各自承擔什麼職責；政策變化後，哪些內容需要同步更新？**

> 自然語言政策讓模型知道該查哪些條件，也能向使用者解釋結果。以使用者改變行程為例，呼叫時傳入 `reservation_id` 和 `cancellation_reason="change_of_plan"`；模型還可以填 `expected_has_insurance` 表明自己的判斷。執行服務核實身份與訂單授權，用資料庫裡的預訂時間、保險及航段狀態和伺服器端時鐘作出裁決。模型以為已投保、訂單記錄卻顯示未投保時，服務記錄差異，仍按訂單事實處理。校驗與提交之間也要防止並行修改使判斷失效。
>
> 按正文示例政策，先固定其他條件：經濟艙、未投保、航班正常、所有航段均未使用。預訂後恰好 24 小時應允許取消，24 小時零 1 秒應拒絕。再單獨改變航段狀態：哪怕只過了兩小時，只要已有航段被使用，也應拒絕。這三例分別檢查了時間邊界和規則的先後順序。政策變化時同步更新說明、執行程式碼、參數示例和邊界測試，並確認舊預訂適用哪個政策版本。

## 第六章 互動：觀測與動作空間的擴展

**1. (★★) 非同步 Agent 收到新事件時，需要判斷它與目前任務的優先關係。如果這個判斷涉及語義理解，例如識別使用者是在補充條件還是要求立即停止，應如何分配規則引擎與 LLM 的職責？請比較回應時間、費用和誤判後果。**

> 可以先按可信來源和事件類型設定規則：明確的停止訊號、執行器故障和到期任務進入相應處理通道。自然語言中的意圖由分類模型輔助識別，結果交給執行階段按權限和目前狀態排程。規則開銷小、行為容易檢查；模型能處理表達變化，但增加推理費用、延遲和誤判機率。關鍵停止訊號應能透過專門通道直接生效，並為分類超時或不確定結果規定處理方式。外部事件正文作為待分類資料，權限和優先順序由可信後設資料與排程策略約束。
>
> 用兩條接連到達的訊息檢驗方案。使用者先說「先停一下」，工具隨後回傳了報價。暫停涉及承諾的操作，仍可儲存報價供恢復時使用。重播時檢查收到暫停與實際停止之間有沒有新訂單。

**2. (★★) 事件佇列積壓了 20 個事件：10 個工具結果、5 條使用者訊息和 5 個系統提醒。你會如何組織它們的順序、格式和處理狀態，使模型能夠追蹤任務依賴並回應重要變化？**

> 先按任務標識、來源、時間和依賴關係歸組，識別真正重複的事件；同一任務的條件更新按時間保留，工具結果攜帶原呼叫與背景任務標識，按介面協定歸入對應任務。原呼叫已回傳執行狀態時，稍後的完成結果透過約定的事件形式送達。需要立即處理的停止或故障事件由執行階段優先接入，其餘事件按任務組織成清單，標記未處理、處理中和已處理。長工具結果保留決策所需的事實與狀態，完整內容放在可檢索的外部儲存中。每輪結束更新清單，避免已經消費的事件重複觸發動作。使用者新條件應與受到影響的計畫或待完成任務關聯。

**3. (★★★) Agent 可以使用專屬信箱和電話號碼，也可以在授權後操作使用者的個人帳號。請結合背景執行、對方的身份核驗要求、權限範圍與稽核，討論兩種身份方式各自適用的場景。**

> 對預約、查詢與日常溝通，可優先使用獨立身份，便於背景執行、區分 Agent 的活動並單獨管理存取範圍。涉及使用者帳戶內的資料或業務操作時，可以採用範圍明確、可撤銷的授權，並在對方要求帳戶持有人確認時接入使用者。例如，客服電話可以由 Agent 先說明需求，再透過三方通話完成本人確認；視覺化登入可由使用者在受控介面中完成。

**4. (★★) 端到端語音模型直接處理音訊，中間環節的錯誤較難從外部定位。如何設計觀測與對照實驗，區分感知錯誤、推理錯誤和表達錯誤？**

> 儲存經過授權採集的輸入音訊、事件時間線、工具結果與輸出音訊，並記錄模型可提供的文字輸出。用同一段輸入做直接音訊回答和先轉錄再回答的對照，再加入人工核對的轉錄，觀察錯誤是否隨輸入形式變化。例如，音訊算術題答錯，給同一模型看準確的文字轉錄後卻答對了，值得先查音訊路徑。換成文字也改變了輸入介面，單憑兩次答案還定不出是哪一步出錯。若模型同時回傳文字和播報，可以再對照兩者，找出只在播報中遺漏的數字。實驗 6-6 的兩段錄音詞句相同、語速不同；要問哪段說得快，就必須保留聲音，文字轉錄已經丟了答題所需的線索。另對語速、雜訊、端點、插話和首段延遲分別評估。

**5. (★) Step-Audio R1.1 的 MPS 讓構思與表達協同推進。系統應如何使用停頓、進展說明和分段表達？後續推理改變了已說出的結論時，應怎樣處理？**

> 表達節奏應服務於目前任務：需要等待查詢時說明正在核對什麼，解釋複雜內容時分段並適當停頓。能夠提前表達的內容包括已確認事實、任務理解和接下來的處理步驟；業務結論需要相應證據支持。若後續發現結論有誤，應及時指出具體修正及其影響，並同步更新後續行動。評價時既檢查首段回應和語音自然度，也檢查結論一致性與實際完成情況，避免把填充詞數量當成自然交流的目標。

**6. (★★) SoM 的視覺區域標註與 DOM 元素索引都讓模型能用一個編號指明要操作哪裡。遇到非標準控制項、遮擋或動態變化時，如何組合重新標註、座標預測和操作後檢查？**

> 先檢查候選是否因滾動、重新整理或動態載入而過期，必要時重新獲取頁面狀態並生成對應。結構化資訊缺失時，可以透過截圖補充視覺候選；目標清晰而候選未覆蓋時，再使用座標預測。執行前校驗影像到桌面的座標變換，執行後檢查預期介面變化。若目標本身仍不清楚，可以放大區域或進一步讀取介面資訊。三條路線都需要應對遮擋與狀態變化，並儲存本次定位所依據的畫面。

**7. (★★) 遙操作資料的品質受操作者技能影響。抖動、繞路、停頓和抓取失敗會怎樣影響 VLA 訓練？如何篩選資料，同時保留有價值的失敗恢復過程？**

> 模仿學習可能把頻繁抖動和無效繞路學進動作策略。採集時可以記錄成功狀態、路徑長度、速度與加速度變化、碰撞、越界、人工接管和觀測缺失，用這些指標定位需要複核的片段。篩選還要考慮任務難度：成功恢復一次滑落可能比順利完成更能補充訓練覆蓋。將穩定示範、失敗動作和恢復過程分別標註，再按訓練目標選擇資料，既能提高基礎動作品質，也能保留糾錯經驗。基礎動作仍不穩定時，可以先檢查和改善示範品質，再考慮增加模型結構的複雜度。

**8. (★★★) 語音、Computer Use 和機器人都可以採用統一模型、模組化級聯或前台互動與後台推理分工。面向未來五年，你傾向於怎樣組合這些路線？請結合延遲、可觀測性、升級成本與任務風險說明判斷。**

> 可以先確定場景約束，再選擇組合。連續語音需要維護聽說時序，複雜業務分析需要較長推理，兩者可以透過任務與狀態介面協作。Computer Use 需要持續取得頁面變化，機器人還要維持高頻控制。模組化便於替換、定位問題和獨立升級，代價是增加介面通訊開銷，並需要維護跨模組的狀態一致性；統一訓練有機會改善資訊利用與時序協調，但升級和診斷需要更多整體評估。前沿推理模型更新較快，保留後台模型的替換能力，就能單獨接入新能力，減少重新訓練整套互動系統的成本。可以保留可替換的後台推理能力，同時持續改進前台互動模型。

**9. (★★) 標準 Web 頁面可以提供 DOM 或無障礙資訊，Canvas、WebGL 與自繪控制項往往依賴視覺定位。同時維護結構化與視覺兩條路徑，會增加哪些成本，又能獲得哪些收益？**

> 結構化路徑提供角色、標籤和元素引用，便於理解表單與頁面關係；視覺路徑覆蓋截圖中可見但未暴露結構的內容。維護兩者需要處理狀態同步、元素與影像的對齊、不同失敗類型以及額外測試。收益是能夠按頁面條件選擇更合適的定位方式，並用截圖檢查結構化資訊是否符合目前介面。可以用相同任務分別測量定位成功率、操作輪數、延遲和恢復成本，決定何時使用單一路線、何時組合。短期內，可以保留兩條路徑；長期更看重視覺路線覆蓋不同軟體介面的潛力。視覺模型能力增強後，應重新評估結構化路徑帶來的實際收益，逐步簡化收益較低的適配。

**10. (★★) 動作分塊讓 VLA 一次生成一段未來動作。若執行期間物體被移動，怎樣協調分塊長度、重新觀測、後台推理和動作中斷，兼顧執行效率與回應速度？**

> 區分模型預測的動作長度與每次實際執行的長度：可以預測較長軌跡，只執行前一小段，再用新觀測滾動更新。推理與執行重疊時，需要處理新舊動作塊的銜接；環境變化較快或接近障礙物時，縮短執行片段並提高狀態檢查頻率。控制層持續偵測限位與異常，必要時按硬體要求減速或停止，並丟棄失效的剩餘動作。選擇參數時一起測量推理延遲、軌跡連續性和最壞回應時間，避免僅根據吞吐量決定動作長度。

**11. (★★★) 快速互動需要及時行動。請分別以語音回覆、網頁提交和機器人抓取為例，設計動作分級、狀態確認與停止機制，使回應速度與任務後果相匹配。**

**12. (★★★) 選擇喚醒、安全點、取消、搶佔或快慢分工中的一個原語，比較它在事件驅動任務與機器人動作分塊中的實作。環境變化速度、動作可逆性和觀測成本怎樣影響設計？**

> 可以選「取消」。實驗 6-2 中，使用者要求停止分析時，排程器先停止派發這項任務的後續工作，再通知執行器終止子處理程序。核對結果要用任務編號：T1 有退出回執，後來上報完成的是新任務 T2。若 T1 在退出前已寫入檔案，還要檢查檔案狀態，決定保留、清理還是從上次完整寫入的位置恢復。
>
> 換成機械臂，假設它正按一段預先生成的動作靠近杯子，杯子卻被挪走了。撤掉佇列裡的後續動作，機械臂仍可能在執行已經下發的那一段。控制層要按裝置允許的方式減速、停止，讀取機械臂和杯子的實際位置，規劃器才能從新的狀態接手。杯子移動越快，允許連續執行而不重新觀測的時間就越短；抓取接觸後，鬆開夾爪可能讓杯子落下，恢復前還要確認是否握住了物體。若視覺定位開銷大，可以在接近或接觸時增加觀測，在平穩移動時拉長間隔。緊急停止要有直接通向控制層的通道。

**13. (★★) 同一筆訂單的顧客聊天、核准討論和支付回呼，是否應當歸入同一條訊息串？請從處理順序、並行度、分割區鍵遷移和權限隔離四個方面，比較合併訊息串與按關聯物件訂閱兩種做法。**

> 合併訊息串把同一訂單的事件排進一條佇列，任務讀取上下文最簡單；代價是無關訊息相互阻塞，售後群裡的討論要排在顧客訊息後面，大訂單還會形成熱點。佇列裡排的是到達順序，支付回呼本身可能遲到或亂序，事件仍要帶來源時間戳。訊息串標識通常兼作分割區鍵，合併規則一旦調整，就要遷移已有資料。不同來源的發言者權限不同，合併後還要在同一訊息串內逐條區分誰能觸發什麼操作。
>
> 按關聯物件訂閱保留各來源的訊息串，順序只在各自訊息串內保證，跨訊息串的先後由任務狀態和來源時間戳判斷。任務可以按需訂閱或退訂訊息串，分割區鍵不受影響，權限也隨訊息串保持隔離。代價是任務需要合併多條訊息串的事件，並處理同一件事從兩個來源到達的情況。
>
> 用一個場景檢驗：支付回呼先到，顧客的「取消退款」後到。兩種做法下，任務都要比較兩個事件的來源時間與目前退款狀態，才能判斷取消是否還來得及：回呼可能是遲到的，到達順序不等於發生順序。合併訊息串省掉的只是跨訊息串收集事件這一步。

**14. (★★) 語音出行助理要查天氣、讀取使用者記憶、搜尋網頁、查航班和訂票。前台、後台和執行階段應怎樣分工？如果使用者口述同行人的姓名，又在等航班結果時插問天氣，怎樣避免訂錯票或漏報結果？**

> 執行階段提前把使用者記憶放進上下文。查天氣、查航班和簡單的網頁搜尋由前台直接呼叫，省去委派時後台的兩次模型呼叫。需要綜合搜尋結果、比較改票方案時，再交給後台。
>
> 訂票可由前台直接辦理，聽清姓名用字並請使用者確認後再下單。需要委派時，前台把聽準的姓名、號碼和使用者的更正寫進任務說明，後台據此填寫。使用者插問天氣時，執行階段記下尚未播報的航班結果，讓前台答完天氣後再報航班。

## 第七章 Agent 的評估

**1. (★★) 評判模型可能偏好較長回答、特定文風或某個展示位置。怎樣設計控制樣本、交換測試和人工校準集，區分內容品質與這些偏好？**

> 把兩份回答記作 A 和 B，先按 A、B 的順序給評判模型看，再交換位置。若兩次都選 A，這一對的結果一致；若兩次都選左邊，換個位置就換了贏家。記下這種翻轉在多少對回答裡出現，再用隨機順序重複評判，檢查分歧有多大。一次翻轉還不足以認定模型總偏愛左邊。
>
> 要查篇幅偏好，可以保留退款金額、到帳時間、退款方式這三項事實，只把同一答覆寫得更長。查文風時則儘量保持長度相近，改用另一種措辭。長短、語氣和事實一起改，即使評分變化也很難解釋原因。請熟悉業務的人按同一份評分標準獨立判讀一批樣本，留下任務要求、事實依據和人工判定。逐類核對評分分歧；若使用離散標籤，還可用 Cohen’s κ 衡量扣除偶然一致後的吻合程度。遇到評分標準寫得不清的邊界案例，就補上判例，另留一批樣本檢驗修訂後的標準。換一個模型家族複評，也要用人工判定檢查兩者有沒有共同漏掉的錯誤。

**2. (★★★) 公開評估集可能進入訓練資料。怎樣組合新任務、參數化環境、未公開的測試題與生產樣本，降低資料汙染對結論的影響？canary 標記能夠提供哪些線索？**

> 讓評估同時包含定期更新的新任務、參數化實例、獨立保留集與經過脫敏確認的生產案例。任務生成規則可以複用，評估實例與訓練實例應分別管理，並在任務結構、時間和環境上保持足夠差異。參數變化還應保留需要推理的關係，避免僅替換名稱和數字。canary 標記可以幫助發現文字被複製或接觸的線索，判斷訓練汙染還需要結合資料來源、發布時間和行為證據。分別報告不同來源的成績，有助於觀察模型是否只熟悉某一類公開題。

**3. (★★) 根據專家指導、全面覆蓋、重要性加權和自包含四項準則，為「回答有幫助」和「語氣恰當」設計 Rubric。怎樣用邊界案例處理評價者的分歧？**

> 先定義受眾與任務。「有幫助」可以拆成是否回應目前訴求、是否提供可執行下一步、是否保留必要條件；「語氣恰當」可以拆成是否尊重使用者、是否與溝通場景匹配、是否避免無依據承諾。每項給出檔次、正反例和邊界情況，例如投訴回覆中簡潔承認問題與冗長重複道歉的差異。比如客服正在處理「帳單多扣了一筆，怎麼核實」的投訴。可以試用五分量表：準確指出要核對哪筆收費給 2 分，給出使用者當下可執行的核對步驟給 2 分，措辭尊重且沒有擅自保證退款給 1 分。每項條件完整滿足才給該項分。只答「很抱歉給您添麻煩了」，在這道題上只能得到最後 1 分。請多位熟悉業務的人獨立評分，討論分歧背後的任務理解，再更新參考材料和判例。評分可以保留有意義的偏好差異，聚合方式按產品目標預先規定。

**4. (★★) τ²-bench 使用模型模擬使用者。怎樣檢查模擬使用者是否遵循任務設定，能否覆蓋情緒、歧義和資訊遺漏等真實互動條件？**

> 從遵循設定和代表真實互動兩個層面檢查。前者逐輪核對模擬器知道什麼、可以透露什麼、是否編造事實，以及是否正確回應 Agent 的提問；後者比較真實使用者樣本中的歧義、遺漏、情緒、糾正和中斷。為這些條件建立場景矩陣，檢查不同模擬策略下的任務成功率、輪數和錯誤類別。再用人工互動樣本校準關鍵任務，觀察絕對成績和模型排名是否隨模擬器改變。

**5. (★★) Bradley–Terry 用一維潛在實力解釋配對偏好。哪些任務分布或使用者群體可能形成循環偏好？怎樣利用分組分析與模型擬合誤差解釋排行榜？**

> 假設三位評審分別把三個模型排成 A、B、C，B、C、A 和 C、A、B，每人都把最喜歡的排在第一位。現在兩兩投票：A 對 B，兩人選 A；B 對 C，兩人選 B；C 對 A，兩人選 C。每個人的偏好都有先後，合起來卻繞成了一圈。Bradley–Terry 給每個模型一個實力分，三個分數排不出這種循環。
>
> 實際讀榜時，先看每一對有多少次對戰、勝率的不確定範圍有多大，再對照模型擬合的勝率。如果有足夠的資料，可以按任務或使用者群體分別擬合：有人最重視答得準，有人更在意答得快，合併後可能看不出這種差異。最後按照目標業務中各類任務的佔比作選擇。

**6. (★★) 一個 Agent 的單次成功率為 60%。在獨立嘗試假設下，比較 $k=5$ 時的 Pass@k 與 Pass^k；再結合重試成本、結果選擇和動作副作用，說明怎樣設計實際評估。**

> 在每次成功機率均為 0.6 且相互獨立的假設下，Pass@5 = 1 − 0.4⁵ = 98.976%，Pass^5 = 0.6⁵ = 7.776%。前者描述五次中至少一次成功，後者描述五次全部成功。實際重試還需要可用的結果驗證或選擇器，並計入失敗嘗試的時間和費用。對有外部副作用的任務，應設計隔離狀態、冪等與恢復機制，在可控條件下測量每次失敗及後果。k 取自實際允許的嘗試預算或重複執行要求，並記錄任務間差異與嘗試相關性。

**7. (★★) 在有限預算下，怎樣安排小規模診斷、配對比較、重複執行，以及用未參與選型的任務做最後一次驗證，使每一輪評估儘量幫助決策？**

> 先根據失敗簇選擇少量診斷任務，明確每輪要區分的原因假設；用配對條件比較單項變化，優先檢視能解釋行為的中間觀測。篩出有價值的改動後增加任務覆蓋與重複次數，估計差異區間。每題對兩個配置各執行一次時，可以用 McNemar 檢驗分析二元結果的配對差異；同題重複執行時，先彙總到任務層，或按任務聚類重取樣。執行前先定下值得採用的最小改進和最多能評多少題。如果區間仍包含有實際意義的收益和損失，而且還有預算，就按預定計畫再測一批。預算用完仍分不清，應報告現有結果和區間，暫緩更換配置。保留未參與調參的任務用於確認，涉及多方案篩選時處理多重比較。高風險邊界與常見生產任務分別覆蓋，避免將診斷集的集中取樣當成總體分布。

**8. (★) AndroidWorld 四項 Wi-Fi 任務中，完整元素樹將成功率從 25% 提高到 100%，token 用量為原方案的 2.498 倍；精簡後四項仍全部成功，token 為完整樹的 0.506 倍。怎樣設計裁剪規則與迴歸任務，保留控制項狀態、無障礙關係和後續操作依賴？**

> 可以先設計兩道迴歸題。一道把 Wi-Fi 從開切到關，檢查裁剪後還能否找到開關並操作它；另一道從已經關閉的狀態出發，要求確認 Wi-Fi 已關閉。這時模型得讀出目前狀態並及時結束，再點一下反而會把 Wi-Fi 開啟。H5 對照組的 `SystemWifiTurnOffVerify` 正好說明了第二題的價值：模擬器在開始和結束時給的狀態分都是 1，Agent 卻沒有報告完成。實驗要求目標狀態正確且 Agent 報告完成，因此這次仍記失敗。
>
> 裁剪時保留控制項文字、無障礙標籤、狀態值，以及可操作、可聚焦或可滾動的元素。摺疊空容器後，仍要能沿原有關係把標籤對應到正確的開關，把操作定位到正確的控制項。用相同起始狀態分別跑完整樹和精簡樹，逐項核對控制項覆蓋、任務成功、token 用量與延遲。若某一步找不到控制項，回看兩份樹，把缺失的關係補入規則，再用需要滾動、跨屏的任務和其他應用做迴歸。

**9. (★★) 使用者模擬器按 Agent 提問逐步透露資訊。怎樣比較不同透露策略，並判斷互動輪數、成功率和任務難度受到了什麼影響？**

> 固定任務事實、初始環境和 Agent，分別配置主動完整透露、按問答逐步透露、允許遺漏或歧義等策略，比較需要的澄清次數、工具呼叫、成功率和錯誤類型。將真實使用者軌跡中的透露行為作為校準依據，並分層覆蓋熟練與不熟練使用者。模擬器改變了資訊取得的難度，既可能影響絕對分數，也可能影響模型排序；因此應在多個合理策略下觀察結果，並給出對應的使用者與任務條件。

**10. (★★) 使用者交給科研助手三次觀測值 2、5、8，要求畫圖並報告均值。讀取日誌顯示檔案開啟失敗，繪圖程式隨後用 4、5、6 生成了圖，報告給出的均值是 5。現有檢查只要求「圖能開啟、均值正確」。這個檢查會給出什麼結果？怎樣修改驗收與迴歸用例，才能發現資料被換過？**

> 現有檢查會通過。兩組數的和都是 15，均值都是 5，但圖上的第一個點從 2 變成了 4，第三個點從 8 變成了 6。先從使用者檔案獨立讀取三個值，再對照傳給繪圖函式的資料，按觀測順序逐點核實。只看到日誌裡出現過檔名，仍不足以確認畫圖用的是檔案裡的值。
>
> 迴歸時可以做兩次試驗。先讓檔案無法讀取，檢查助手能否指出缺失的資料、請求重新提供，並將分析記為待完成。再把有效檔案裡的第一個值改成 11，另兩項保留 5 和 8。此時第一個點應移到 11，均值應變成 8。兩項一起檢查，就能發現只更新圖或只更新報告的錯誤。

## 第八章 模型後訓練

**1. (★★) 一次定向微調改善了目標任務，卻降低了通用工具呼叫能力。你會如何設計檢查原有能力的測試集、調整資料配比和訓練量，並比較全參微調與 LoRA 的效果？**

> 假設微調是為了讓助手在退款尚未到帳時繼續查證。先準備三組獨立於訓練的題：退款尚未辦成，看它會不會過早收尾；退款已經到帳，看它能不能及時結束；換成查航班等原本會做的任務，看它還能不能選對工具、填對參數。後兩組檢查原有能力有沒有退步。固定工具、權限和任務起點，讓未微調的模型先跑一遍，記下每組的基線。
>
> 從同一基座出發，用相同的資料劃分和訓練預算分別做全參微調與 LoRA。訓練中混入原分布的樣本，在開發集上調整新舊資料的配比、學習率和停止位置；選好配置以後，再在留出的三組題上各跑一遍。若未到帳的題進步了，已到帳的題卻多查好幾次，只看退款任務的平均分就會漏掉這次退步。LoRA 凍結了基座參數，掛載適配器以後仍要做這項檢查。進一步的選擇包括訓練時加入參考策略約束、只在相關任務掛載適配器；若處理圖文輸入，還可根據錯誤來自哪裡，決定調整投影層、語言模型還是視覺元件。

**2. (★★) 某項領域能力既可以透過參數訓練學習，也可以透過上下文示例和知識檢索來提供。你會依據哪些因素選擇方案？**

> 先判斷需求屬於事實檢索、可描述規則，還是感知與隱式決策模式。需要更新、引用、權限控制和刪除的事實適合 RAG；少量規則與示例可以先放入上下文；穩定且反覆使用的行為可以考慮參數訓練。再比較呼叫規模、延遲、訓練與維護成本。確定性的核准規則由程式執行，模型負責理解輸入和處理規則之外的語言任務。
>
> 例如，一項退款政策本月剛改，更新檢索材料後可以用新舊日期各問一次，檢查模型是否引用了當時生效的版本。另一類問題是模型讀到了正確政策，卻在多種問法中持續漏掉關鍵條件；這樣的記錄才有助於構造行為訓練樣本。

**3. (★★) 分別蒸餾直接回答的 Chat 模型、生成推理過程的 Reasoning 模型，以及多輪使用工具的 Agentic 模型，需要哪些訓練材料和驗證方法？**

> Chat 蒸餾需要有代表性的輸入、可靠回答與任務品質檢查，兼顧事實和表達。Reasoning 蒸餾需要可獲取的推理示範，檢查答案及關鍵中間步驟，並比較推理長度與品質。Agentic 蒸餾還需要工具定義、環境觀測和狀態變化，驗證整條動作鏈；策略損失只覆蓋模型生成位置，環境回饋作為上下文。學生容易進入示範之外的狀態時，可以用在軌蒸餾補充這些前綴的監督。

**4. (★★★) 客服 Agent 用 10 輪互動完成任務，最終獲得成功獎勵。你會如何把這一訊號關聯到中間決策？哪些步驟適合增加過程獎勵？**

> 設第 2 輪問清了哪筆收費有爭議，第 7 輪解釋了費用，第 10 輪收到退款成功的回執。整條軌跡可以記為成功，僅憑這張回執還看不出第 7 輪的解釋起了多大作用。用 PPO 時，可以讓價值模型估計每一步開始時的預期回報，再結合實際回報估計動作的優勢。用 GRPO 時，可以從同一筆爭議出發，比較多次辦理的軌跡；若每次都辦成，只憑相同的成功獎勵就分不出哪種做法更好。
>
> 身份核驗有可信回執、所需的訂單號已經核實，這些中間事件可以單獨檢查。給它們加過程回饋後，還要用終點判據核對錢是否確實退到了指定訂單。客服先解釋費用還是先查訂單，只要兩條合法路徑都能辦成，就應允許兩種順序。至於哪句解釋最有幫助，可以多採幾條軌跡，或請教師模型結合證據給出示範。

**5. (★★★) 你有 10,000 美元預算提升客服 Agent 的表現。如何安排評估、上下文與知識、Prompt／Skills、程式約束和參數訓練的投入？**

> 先用一部分預算建立代表性任務集，統計錯誤分布，按失敗頻率、業務影響及修復成本排序。知識缺失優先改善檢索，流程理解問題先試 Prompt／Skills，權限與金額約束用程式執行。可以先把這些成本較低、容易修改的方案做到位，再為仍然存在的感知、表達或隱式決策問題安排參數訓練與部署評估。舉一個可調整的預算：3,000 美元用於建基線、迴歸測試和上線觀察，2,500 美元修知識與檢索，1,000 美元調整 Prompt 和 Skills，1,500 美元實作並測試程式約束，餘下 2,000 美元留給小規模訓練。若基線顯示主要問題是檢索到過期政策，就先把訓練預留款用於補充帶生效日期的案例，並複測新舊政策交替時的表現。

**6. (★★★) 任務缺少明確獎勵，環境互動又很昂貴。可以從哪些來源獲得學習訊號？你會如何驗證這些訊號確實改善了任務表現？**

> 可以從人工示範、偏好比較、教師逐 token 評價、環境中的可驗證事件，以及模型生成的診斷中獲得訊號。一個值得比較的方向是把豐富回饋轉化為具體學習訊號：例如「還缺少哪項客戶資訊」已經指出了下一步，保留這類回饋能比單個成敗標籤提供更密集的監督。模型模擬器能增加互動量，在軌蒸餾能增加每條軌跡的監督密度。

**7. (★★) 為每位使用者或每家公司訓練專屬 LoRA，適合承載哪些個性化能力？哪些資訊更適合保留在外部知識庫中？**

> 長期穩定的表達風格、領域術語使用習慣和重複出現的決策模式，可以透過專屬 adapter 學習。帳戶狀態、頻繁變化的產品事實、需要逐條引用或刪除的記憶，更適合外部儲存與檢索。選擇時還要考慮使用者資料量、隔離、更新頻率以及多 adapter 的部署成本。

**8. (★★★) 結合 Weak-to-Strong Generalization 的研究思路，小模型能否為更強的 Agent 提供有用監督？請分別考慮局部驗證、偏好標籤和額外上下文，並設計檢查監督偏差的方法。**

> 小模型可能擅長一個較窄的驗證任務，也可能因為掌握規則、參考答案或額外材料而提供有用訊號。強模型生成候選，小模型評價自己能夠可靠判斷的部分，再結合程式驗證或人工抽查。可以用金標測量監督錯誤，按任務類型分析偏差，並檢查強模型在獨立評估中的表現。對分歧較大的樣本降低權重或轉交更可靠的評價來源。

**9. (★★) 一條軌跡的中間步驟大多正確卻最終失敗，另一條軌跡得到正確結果但違反了流程約束。如何結合過程和結果評價這兩條軌跡？**

> 以實驗 8-16 的檔案操作為例。甲先讀了配置，再改指定欄位，驗收時發現值寫錯了。結果記為失敗，但檢查器可以確認它讀過原檔案。乙寫對了值，卻直接覆蓋了已有檔案。結果檢查會通過，路徑檢查則能指出哪一次寫入違反了「先讀再改」的規則。如果這條規則是交付的硬性條件，乙也不能通過驗收。建立新檔案時沒有舊內容可讀，應允許直接寫入。
>
> 訓練時可以分別保留結果分和路徑回饋。甲的合規操作有記錄可查，最後寫錯的值仍要糾正；給乙扣分時，可以把懲罰落在那一次違規寫入上。要判斷訓練是否有效，再用留出的任務分別統計完成率和違規次數。如果模型乾脆少做任務，違規次數也會下降，這時完成率會提醒你檢查它究竟學到了什麼。

**10. (★★★) SWE-bench、τ²-bench 和 AndroidWorld 的環境與驗證器可以用於訓練。如何劃分任務實例和範本，使訓練材料得到利用，同時保留獨立評估？**

> 共享環境介面與驗證邏輯，分開訓練和評估實例，並儲存劃分規則。參數化生成器可以產生同類新實例，用於檢查分布內泛化；跨範本、跨業務或跨環境的留出任務用於檢查更遠的遷移。已用於訓練的公開測試題可以保留為診斷材料，獨立評估則使用未參與訓練的任務。分別報告各類留出結果，可以判斷收益來自實例適應還是更廣泛的能力改善。

**11. (★★★) 目標任務的 pass@1 很低。怎樣結合 pass@k、格式解析率、部分進展率和失敗歸因，決定採用 Mid-training、SFT 或 RL？**

> 先區分三類問題：知識與基礎能力不足，格式和協定錯誤，以及策略選擇不當。pass@k 顯示增加嘗試後能否獲得成功，解析率說明軌跡能否被執行和評分，部分進展率說明是否存在可用的中間訊號。基礎能力不足時補充相應的領域訓練；已有能力但輸出格式或操作流程不穩定時用示範訓練；能生成可評分且有獎勵差異的軌跡時可以試 RL。小規模試驗還可以看出，新方法多做對了哪些題、訓練要花多少錢，以及原先會做的題是否還做得對。

**12. (★★★) 一批 rollout 中只有少數超長回應尚未結束，其餘任務已完成。如何提高訓練叢集利用率，同時控制非同步取樣帶來的策略陳舊度？**

> 使用連續批處理和動態排程補入新請求，按長度分桶或分離取樣與訓練資源。非同步管線可以減少等待，同時記錄行為策略版本與生成機率，限制允許的滯後並監控重要性比率。長度預算或柔性的超長懲罰可減少長尾，但需要區分無效重複與必要推理，並正確處理被截斷的軌跡。

**13. (★★★) 使用模型模擬搜尋引擎或使用者時，哪些模擬偏差可能誤導 Agent？如何用任務狀態和真實互動校準訓練？**

> 模擬搜尋可能過於容易回傳相關材料，模擬使用者可能總能理解含糊表達或對未兌現的承諾給出好評。這會減少模型練習查證、澄清和恢復的機會。評分儘量結合可驗證的狀態變化與交付物，另用人工樣本檢查語義品質。對有真實介面的工具，可以比較模擬與真實回傳；對模擬使用者，可以用真實對話中的行為分布和經授權的使用者測試校準。

## 第九章 Agent 的持續進化

**1. (★★) 一條經驗文件有三次成功軌跡和一次失敗軌跡，失敗發生在較新的 API 版本上。怎樣區分經驗失效與適用條件變化？**

> 先按 API 版本、任務條件和環境狀態整理四條軌跡，再對照導致成功或失敗的具體步驟。若舊策略在舊版本成功，而新版本改變了介面或前置條件，可以保留舊經驗並收窄適用範圍，為新版本生成候選策略。若相同條件下也出現失敗，則檢查遺漏的條件與偶發因素，透過補充驗證決定修訂或撤銷。每個版本都保留支持和反駁證據。
>
> 可把同一條經驗分別交給舊版和新版介面，在相同輸入上重播，再只改那項疑似變化的參數。若補上新版本要求的欄位便能恢復成功，經驗文件應記錄該欄位從哪個版本起必填。

**2. (★★) 客服 Agent 的滿意度與規則違規率同時上升。應怎樣組合學習訊號，並設定發布時的護欄指標？**

> 假設客服答應了政策不允許的退款，使用者當場給了好評。把好評直接當作訓練獎勵，下一版就可能學會更爽快地作出同樣的承諾。先把三份記錄對起來：使用者怎樣評價服務，當時的政策允許什麼，退款工具實際執行了什麼。這個例子可以用來教客服解釋政策、尋找允許的替代辦法；單憑這條好評，還不能把答應退款當成示範。
>
> 發布前，用同一批請求比較新舊版本，分別記錄解決率、滿意度、合規變通和表達是否簡潔。另按事先約定的計算基準統計違規、洩露隱私、越權、無依據的陳述，以及承諾與執行不符的情況。例如，兩版都接到 100 個退款請求，舊版違規批准 1 次，新版 4 次；若發布條件要求這項違規率不升，新版即使獲得更多好評也不能通過。

**3. (★★★) 某個 Agent 經常聲稱操作已完成，工具記錄卻顯示尚未執行。怎樣根據根因選擇 Prompt、Harness 檢查或參數訓練？**

> 先對照回覆時間、工具請求與執行結果。如果模型已經獲得正確狀態，卻反覆使用不合適的完成式措辭，可以先補充明確的表達規則和例子。如果操作狀態能由程式可靠讀取，則在 Harness 中檢查回覆與狀態的一致性，並在需要時要求修正。如果問題橫跨大量任務與表達方式，再用多樣化訓練資料改善語言與行動的對齊。可優先選擇範圍小、容易驗證和回滾的修改。

**4. (★★★) Agent 需要修改工具與業務驗證元件，批准自身更新的控制面由獨立模組維護。怎樣劃分兩側的權限、程式碼和測試？**

> Agent 可以在自己的工作區修改工具和業務驗證程式，用受限帳號試執行補丁。評估用例、發布標準、權限配置、稽核日誌和穩定版本都由獨立模組管理，測試帳號無權修改。即使改的是驗證程式，也由這個模組評估。Agent 可以按授權檢視診斷結果、修改補丁。獲批後由有發布權限的帳號部署，記錄哪份補丁通過了哪些測試、由誰批准。

**5. (★★) 經驗知識庫增長後出現檢索錯誤與規則衝突。怎樣設計版本、時效、合併和淘汰機制？**

> 為每條經驗記錄來源軌跡、適用條件、環境版本、驗證時間和狀態。遇到衝突時，先判斷是否屬於不同版本或場景，按條件拆分；相同條件下仍然衝突的經驗進入待核實佇列。定期合併重複經驗，將過期或被新證據推翻的版本移出預設檢索範圍，並保留歷史與恢復入口。

**6. (★★★) 請為醫療客服設計一套持續進化方案，說明模型參數、知識、Skill 和程式碼約束的分工，以及各類更新的驗證與發布流程。**

> 參數訓練側重意圖理解和表達方式；知識庫維護經審核的指南、藥品說明與機構政策，並儲存版本和來源；Skill 組織資訊收集、轉人工和隨訪等流程；程式碼執行身份驗證、資料存取控制和機構批准的業務校驗。先按事實準確性、流程合規、承諾與行動一致性及表達品質評價軌跡，再根據出錯的環節修改知識條目、辦理流程、程式或訓練樣本。由專業人員審核涉及醫療內容的變化，在新場景、原有任務和安全任務上驗證，分批發布並監控異常。

**7. (★★★) 某個探索策略在所有舊發現樹上得分最高，下一輪線上探索卻退化了。怎樣分析歷史資料覆蓋範圍（支撐集）偏差、隨機性和評價過擬合，並據此劃分重播世界、設定發布門檻？**

> 舊發現樹覆蓋的是歷史策略實際探索過的分支，新任務或新策略可能進入其他區域。模型取樣、工具雜訊與環境變化也會影響策略排名；反覆用同一批樹選擇策略容易使結果偏向這些樹。重播到某個節點時，如果新策略選的動作從未在這棵樹上執行過，就記為「無觀測」，這條軌跡到此為止。分別報告能走完整個重播的比例和這些軌跡上的成績，把未覆蓋的分支列為線上驗證的優先對象。可按任務族、時間和獨立發現樹劃分開發、驗證與封存測試集合，將同一棵樹及其衍生軌跡放在同一集合。固定模型、工具版本和預算，採用多個隨機種子與基線配對比較品質、成本、違規率及不確定性。離線達到預先設定的門檻後，再做小規模線上對照，根據收益與護欄結果逐步發布，並保留回滾條件。

## 第十章 多 Agent 協作

**1. (★★) 角色切換後，程式碼審查員沿用了需求分析階段的上下文，卻仍主要討論需求。怎樣偵測這種角色干擾？如何調整輸入、工具配置與交接方式？**

> 假設需求分析員剛討論過「匯入空檔案時應該提示什麼」，程式碼改動卻漏掉了空檔案分支。先看交接後的第一份模型請求：審查員收到了哪一版程式碼、哪些工具和什麼任務？如果它根本讀不到改動，先補上交接材料。如果它讀得到，再看它有沒有開啟相關程式碼、核對介面和錯誤處理、指出缺少哪項測試。僅憑回答裡出現「空檔案」，很難判斷它是在複述需求，還是發現了缺陷。

> 用同一份改動做三次對照。第一組保留完整討論；第二組把討論整理成一份交接單，寫清目前職責、需求依據和待查事項；第三組另開上下文，只給審查所需的程式碼、需求和測試材料。固定模型、工具和預算，比較各組找到了哪些缺陷、漏掉了哪條需求、花了多少次呼叫。若問題出在工具配置，再單獨調整審查員看到的工具，權限仍由 Harness 檢查。

**2. (★★) Manager 的任務分解遺漏了一項依賴，導致多個子 Agent 返工。怎樣評價分解品質，並在執行中發現和修正計畫問題？**

> 分解結果應列出子任務輸入、輸出、依賴、負責人和驗收條件，並檢查是否覆蓋原始要求。執行前可以驗證介面與資源是否可用，對高風險依賴做小規模試行；執行中用里程碑和子 Agent 回饋發現缺失條件，更新計畫版本並通知受影響成員。透過返工率、阻塞時間、遺漏需求和最終結果評價規劃品質。確認瓶頸在任務分解時，優先為 Manager 配置更強模型、完整任務資訊和足夠推理預算；錯誤分解會讓多個執行者一起返工，單純增加執行者難以解決問題。
>
> 例如，譯者在術語表定稿前已經翻譯了三節。把「術語表版本」加入任務輸入，找出使用舊版本的段落，只返工受影響的部分。下次分解任務時，可以讓不依賴術語的工作先行，同時給譯者一個能看到版本變化的入口。

**3. (★★) 去中心化協作中，成員可能出現溝通遺漏、職責爭議和目標衝突。請選擇兩種情況，設計能夠定位原因、推進處理並結束爭議的機制。**

> 以譯者和審校者協作為例。**漏收訊息。** 術語表已升到第三版，譯者交稿時仍註明使用第二版。先按任務編號查第三版通知有沒有發出，再查譯者有沒有確認收到。如果需要補發，就沿用原通知編號，譯者收到兩次也只處理一次。直到受影響段落改完、審校者核對了交稿版本，這次遺漏才算處理完。

> **職責爭議。** 譯者認為插圖中的舊術語該由製圖者改，製圖者認為應先由譯者定名。兩人把圖號、現用詞和定稿依據記在同一條任務記錄裡。按事先約定，由術語負責人定名、製圖者改圖、審校者核對圖文。若往返幾次仍無新證據，交給約定的負責人裁決。

**4. (★★★) 並行搜尋只需找到一個符合條件的結果。請設計「驗證成功後取消其餘分支」的完整流程，處理兩個結果同時到達、重複訊息、取消超時與資源清理。**

> 子 Agent 回傳候選與來源，Manager 先驗證匹配條件，再以原子操作將任務從搜尋中轉為已獲選。兩個有效結果同時到達時，只有一個完成狀態轉換；重複事件讀取已有處理結果。登記獲選者時，在同一筆事務裡為其餘分支及派生任務寫下待發的取消通知。Manager 按通知編號跟蹤確認，重啟後補發，各子 Agent 按編號識別重複通知。收到新通知的成員在安全點儲存進度、釋放鎖、關閉會話並回傳確認。超過取消期限的執行由執行階段接管清理。已經提交的外部操作還需查詢結果，最後將獲選證據與各分支終態一併彙總。

**5. (★★★) 多個 Agent 同時修改書稿和圖片編號，還可能建立重複檔案或誤刪共享產物。怎樣組合權限、版本、工作副本、語義檢查與恢復機制來管理檔案系統？**

> 按私有工作區、共享產物、外部資源和唯讀系統資源劃分存取權限，為每個成員分配名稱空間。檔案提交採用原子版本檢查，程式碼與書稿修改可在獨立 worktree 中完成，再集中合併。圖號變化屬於跨檔案語義關係，需要檢查圖片、圖題與引用的一致性；目錄鎖可以限制同時修改的範圍，語義正確性仍由關聯檢查判斷。保留版本歷史、受保護備份與恢復入口，限制批次刪除權限，並驗證恢復後的產物完整性。

**6. (★★★) Agent 透過 Pinchwork 或 RentAHuman 委派付費任務時，應怎樣約定並檢查交付品質？雙方對驗收結果有爭議時，怎樣組織複核、付款與申訴？**

> 委派前明確交付物、品質標準、證據要求、時限與預算。程式碼任務可執行測試，視覺產物可檢查渲染，現場任務可結合約定的照片、記錄和人工核實。驗收依據與結果一併儲存，未通過時說明具體修復條件。爭議按預先約定交由獨立複核者或人工處理，資金託管與申訴流程配合執行。信譽記錄應包含任務類型、交付品質、時效和爭議處理結果，幫助後續委派綜合判斷價格與能力。

**7. (★★) Agent 可以透過市場和支付介面委派真人任務。人除了現場執行，還能在目標設定、專業判斷、驗收和責任分工中承擔哪些職責？請結合一個例子說明。**

> 例如，Agent 安排房產實地檢視時，人可以幫助確定真正需要檢查的問題，判斷現場異常，解釋影像未覆蓋的情況，再參與驗收與後續決策。委派方負責授權範圍和預算，執行者負責如實記錄與回饋，具備相應資格的人承擔專業判斷。

**8. (★★) 同一模型既可以獨立完成任務，也可以組成多個角色。怎樣設計對照，判斷專業分工、上下文隔離、並行搜尋和外部回饋分別帶來多少收益？**

> 固定任務集、模型、工具與評價方法，為單 Agent 和多 Agent 設定可比較的預算。分別改變角色分工、上下文組織、並行執行和回饋管道，觀察品質、牆鐘時間、token 用量與錯誤分布。外部回饋也應提供給單 Agent 對照，避免把工具收益全部歸因於協作。例如，先固定總 token 上限和呼叫次數，讓同一組工作者完成四組配對試驗：同角色共享上下文、分角色共享上下文、同角色隔離上下文、分角色隔離上下文。在前兩組之間看角色分工帶來的變化，再在後兩組之間作同樣的比較，就能看出分工的收益是否依賴上下文隔離。在選定的配置下再比較循序和並行，分別記錄使用者等了多久、系統總共用了多少 token，以及交接中遺漏了什麼。

**9. (★★★) 借用《三體》中思維透明的設定，以及迴紋針思想實驗對目標設定的追問，討論多 Agent 系統中的資訊共享、共同目標與觀點多樣性。怎樣透過可觀測的實驗判斷共享範圍和獨立分析階段是否合適？**

> 文學設定與思想實驗可以幫助提出問題，實驗判斷則落實到資訊範圍、目標與行為指標。可比較立即共享全部結論、獨立分析後彙總、只共享原始證據等方案，同時保持任務與預算一致。觀察候選差異、錯誤相關性、最終品質和協調成本，並檢查共同目標是否遺漏約束。可以先讓交叉審核者讀取原始證據、獨立形成判斷，再按需檢視前序解釋，減少已有結論對審核的干擾。

**10. (★★★) 同一個 Coding Agent 分別獲得 30 步和 300 步預算。怎樣安排規劃、實作、驗證與修訂，並根據剩餘預算和實際進展調整策略？**

> 兩種預算都應保留基本規劃和必要驗證。30 步時優先確定核心要求、選擇較短路徑，預留結果檢查與例外處理空間；300 步時可以增加方案比較、邊界測試和獨立審查。執行階段記錄總預算、剩餘預算、已完成事項與未解決問題，按里程碑判斷是否繼續探索、集中修訂或請求輸入。預算分配與實際消耗共同進入日誌，連續多輪沒有進展時調整策略，避免把額外步數消耗在重複操作上。

**11. (★★) 虛擬記憶體與分頁、檔案權限、死鎖偵測和排程演算法，分別能為多 Agent 系統提供哪些設計啟發？請說明這些類比的適用範圍，以及需要由執行階段明確執行的約束。**

> 分頁可啟發按需檢索與冷熱資訊管理，檔案權限可啟發唯讀掛載、工具授權與憑據隔離，等待圖可幫助發現成員互相等待，排程演算法可用於控制並行、優先順序與資源額度。上下文摘要會改變資訊表示，而記憶體換頁通常保留位元組內容；任務語義依賴模型判斷，權限與預算則應由執行階段執行。還要區分正常修訂迴路和沒有進展的死鎖或活鎖，結合狀態、依賴與時間進行診斷。
