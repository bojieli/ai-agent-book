# 後記：回到 Agent = LLM + 上下文 + 工具 {.unnumbered}

本書從一個公式開始：**Agent = LLM + 上下文 + 工具**。讀完十章，再看這三個要素，我們已經能把它們放進一個實際執行的系統：模型理解任務、作出決策，上下文提供目前所需的資訊，工具獲取觀測並執行行動。

第一章用這套功能分解建立全域認識，再用 **Agent = Model + Harness** 說明生產實作中的分工：模型負責決策，Harness 組織上下文、工具介面、執行迴圈和狀態，實施約束、驗證與糾正。

- **建構 Agent（第二至六章）。** 上下文工程組織一次決策所需的資訊，記憶與知識庫支援跨會話儲存和檢索。工具提供觀測與動作介面，程式碼生成讓 Agent 能夠編寫新的工具和系統。互動一章進一步把這些介面擴展到語音、圖形介面和物理世界，並討論持續接收事件的執行方式。
- **評估與進化（第七至九章）。** 評估幫助我們比較系統表現、發現失敗原因，後訓練透過資料與環境更新模型參數，持續進化則把執行經驗轉化為知識、指令、程式或參數的更新，並用驗證和發布流程管理變化。
- **協作（第十章）。** 多 Agent 系統為成員分配不同的上下文、工具與職責，再透過通訊和相互檢查共同完成任務。成員數量增加後，還需要管理共享狀態、任務依賴、資源和爭議。

回到前言的那張帳單。客服說「可以減免」時，我們能從通話記錄裡查到這句承諾。等下一期帳單開出，才有另一份憑據可核對實際減免。如果回呼電話響在使用者手機上，助手事先發去的事項編號和協商摘要，就成了使用者接著辦理的依據。

假如使用者接起電話，還得從頭講一遍，應該改哪裡？先讀上次通話的摘要：如果客服答應減免的金額都沒記下來，就要改進記錄協商結果的步驟。如果摘要寫得清楚，卻在回呼結束後才到，問題就出在交接時機。可以請 Coding Agent 調整發送工具，在上次通話結束時就把摘要交給使用者。下次商家回呼時，使用者手邊就有事情的來龍去脈。

## 兩朵烏雲 {.unnumbered}

1900 年，開爾文用「兩朵烏雲」描述熱與光的動力學理論面臨的難題，其中涉及以太運動與能量均分。[^kelvin] 借用這個比喻，筆者也看到 Agent 發展中的兩朵烏雲：即時互動，以及從互動中持續學習。

**第一朵烏雲，是 Agent 怎樣跟上隨時變化的環境。** 按輪次對話時，你說完一句，助手想好了再答。可你也許話剛出口就想改口，助手查資料時頁面也可能已經更新。即使誰都沒開口，新郵件照樣會來。筆者期待的 Agent 應該有一種「活著」的感覺：邊聽邊想、邊說邊想，在使用者話說到一半時就開始規劃，也能根據使用者設定的目標主動發現「這封郵件該處理了」。

在筆者看來，能多快接上使用者的話，和能把事情想得多周全，是兩個可以分別改進的問題。使用者問「還有更早的航班嗎」，助手可以馬上接話，可要把航班和退改條件查清楚，還得花時間。

一條是**在架構上分離快慢路徑**。背景還在查航班，使用者忽然補上一句：「我得在中午以前到。」前台要能聽見這句話、及時回應，把新的到達時間交給背景。背景可以接著查，也可以取消已經失去意義的查詢。筆者傾向於這樣分工：前台判斷何時接話、何時停下來聽，背景花時間檢索和推理。查到新航班後，背景把結果發給前台，由正在交談的前台決定怎樣答覆。

另一條是**加快模型推理**。生成速度提高，可以縮短同一段推理的耗時，同樣等幾秒鐘，助手就有機會多想幾種改簽方案，再比較哪一種能在中午前到達。小米 MiMo 報告，透過 FP4 量化、DFlash 推測解碼與 TileRT 推理系統的協同最佳化，在單個通用 8 卡節點上實作了萬億參數模型超過 1000 token/s 的生成速度。[^mimo] Taalas HC1 則採用模型專用晶片，在 Llama 3.1 8B 上報告了約 17000 token/s 的單使用者生成速度。[^taalas] 兩個例子分別展示了通用硬體上的系統最佳化，以及針對特定模型的硬體專用化。

生成速度足夠快時，按輪次等待的時間會顯著縮短，互動也就更接近即時對話。要讓 Agent 跟上環境變化，還需要持續接收輸入、及時排程事件，並在決策改變時取消舊操作、同步狀態。

**第二朵烏雲，是 Agent 如何像人一樣，從與環境互動的成功與失敗中持續積累經驗。** 一個模型可以在訓練時學到廣泛知識，上崗後卻還需要了解新使用者、新業務。每次任務都會帶來新的經驗：哪些步驟有效，哪個工具容易出錯，使用者接受了怎樣的表達。如果任務結束後這些經驗隨上下文一起丟失，下一次就可能重犯同樣的錯誤。怎樣儲存這些經歷，讓 Agent 越用越好，是第三章與第九章貫穿討論的問題。

持續學習有多重要，取決於我們怎樣看待模型需要掌握的知識。筆者用「小世界」和「大世界」概括兩種思路。

**「小世界假設」**強調通用知識可以被一個足夠大的模型吸收。沿著這個方向，幾萬億參數的模型可能容納極其廣泛的知識和方法，主要瓶頸就在於能否獲得足夠多的高品質訓練資料。程式設計提供了一個有啟發的例子：大量公開程式碼、文件和可執行測試，為模型學習與結果檢驗創造了條件。行業合作則可以把專業任務和經驗引入訓練，讓更多領域的能力進入基礎模型。

**「大世界假設」**強調具體情境的豐富性與變化。某家公司的程式碼規範、某位使用者喜歡的 PPT 風格、某個客戶的溝通習慣，都需要在實際互動中瞭解。這些知識既有很強的個體差異，又會隨著組織流程和使用者偏好的變化不斷更新，一次預訓練很難提前覆蓋。系統因此要持續維護記憶、知識和操作方法，再根據回饋調整行為。經驗可以先寫成知識文件、指令或程式，經過篩選和驗證後，也可以用於更新模型參數。

當任務擴展到遞迴自我改進（RSI）與 AI for Science 時，Agent 還要探索人類尚未解決的問題。一個猜想經不起實驗，Agent 得能說清哪一步出了問題，據此改動假設，再做一次實驗。走到沒有現成答案的地方，連下一次該試什麼，也要從前一次的結果中學。**筆者認為，學習與適應終將成為模型最強的能力。**

把目光放到未來幾年的個人 Agent，怎樣判斷一個新產品究竟推進了哪一步？筆者在 2026 年 11 月的波爾圖演講中把這個問題拆成五個方向。互動模型、快速推理和觸達現實世界的工具已經有了可以體驗或測量的實作。面向人和多個 Agent 的原生作業系統，以及能在長期使用中學會判斷、同時保有舊能力的持續學習系統，在筆者看來仍需要新的設計。[^porto-jarvis]

2026 年 9 月，Meta 公布了個人助手 Muse，並開始面向美國使用者推出。按其產品說明，使用者可以讓 Muse 留意某件商品何時降價，然後關掉應用。專屬虛擬機器裡的瀏覽器仍可替使用者盯著價格，等有了變化再通知他。如果還想讓它代買，使用者可以先看它準備下哪筆訂單，再決定要不要買。這樣的助手已經能把人從守在螢幕前等待的工作中解放出來。使用者後來調低了預算，助手下次看見降價還能不能照舊代買？從幫人盯價格到替人作判斷，中間隔著使用者的偏好和授權。[^afterword-muse]

出行也會遇到同樣的問題。手機上隨手就能喚起它，解決的是**入口**問題。它記得你這次帶孩子，知道轉機時間不能太緊，體現的是**上下文**。它能查到合適的航班，能否出票還要看你給了什麼**授權**、航空公司接受哪種辦理方式。

[^afterword-muse]: Meta，Muse 發布說明與瀏覽器使用說明。

[^porto-jarvis]: 李博傑，2026 年 11 月 10 日波爾圖演講《The Road to JARVIS: Where the Moats Are for Personal Agents》。

## 模型與 Agent 的共同演進 {.unnumbered}

回頭看 Harness 中層層疊疊的邏輯：多級上下文壓縮、失敗重試、結果驗證、存取控制，每一層都記錄著真實任務中的困難。資訊超過輸入容量，就要壓縮；工具回傳異常，就要判斷能否重試；模型遺漏完成條件，就要獨立驗證；操作需要特定權限，就要落實授權檢查。這些工程經驗也告訴我們，模型和系統下一步該改進什麼。

個人助理的能力還取決於商家開放哪些辦理方式。設想一次帳單協商：使用者授權助手代為詢價，商家可以向它說明優惠條件，但要求帳戶本人在電話中確認變更。助手可以先談清金額、生效時間和附帶條件，等需要本人開口時，向用戶簡要說明談妥了什麼、現在要確認哪一項。這樣即使最後一步必須由人完成，使用者也省去了前面的查詢、等待和反覆解釋。若商家只接受本人辦理，助手仍可以先整理材料、列出問題，幫助使用者一次把事情說清楚。

使用者接了商家的回呼，助手怎樣把事情接回來？假設使用者轉述：「客服答應從下個帳期開始減免。」助手可以記下這個答覆，等帳單出來再核對金額。電信業者若提供出帳通知，收到通知再查即可；若只能主動查詢，助手可以按帳期設一次提醒，到時查進展。需要本人出面的是電話裡的確認，後續跟蹤仍可以交給助手。

這次委託也可能留下一個值得改進的細節：使用者還得追問減免從哪一天生效。先翻助手與客服的通話記錄。如果客服只說「可以減免」，就該讓助手在通話時追問生效日期。如果客服說清了日期，助手卻在摘要裡反覆漏寫，才有了另一類訓練材料：把含有日期的原話與核實過的摘要配成示例。

第一章提出過一個問題：**模型會不會最終吃掉 Harness？** 筆者的判斷是：**會一層一層地吃下去，而 Harness 會不斷走向新的能力前沿。** 模型每穩定掌握一種原先靠外部編排實作的能力，相應的編排就可以簡化。第六章的互動模型就是一個例子：模型直接學習輪次判斷、插話和語音回應後，系統可以減少相應的啟發式規則；音訊傳輸、執行取消與狀態管理繼續由執行時承擔。

有些職責則要留在模型之外。業務權限由可信身份和授權規則決定，預算由執行時與服務配額執行，外部操作由工具和環境完成。

即使某項能力將來能學進模型，業務也未必等得起下一輪訓練和部署。一家企業今天改了審批規則，助手今天就得按新規辦事；團隊可以先改 Harness，再把反覆遇到的難題留給下一輪訓練。這也是筆者理解《苦澀的教訓》的一種方式：通用的搜尋與學習方法會持續擴大優勢，而在它們逐步成熟的過程中，Harness 把目前能力接入真實任務，並為下一步學習留下回饋。

模型與產品由同一團隊持續打磨時，這條回饋鏈可以更緊密。以 Anthropic 的 Claude Code 為例，模型能力影響工具與上下文設計，真實使用中的問題又能為後續模型和系統改進提供方向。第一章介紹的 LangChain 案例展示了系統工程的直接收益：固定使用 GPT-5.2-Codex，調整 Harness 後，Terminal Bench 2.0 得分從 52.8% 提高到 66.5%。完成前自檢、重複操作偵測和預算分配，都來自對失敗過程的具體分析。

筆者認為，**真實業務、回饋資料與模型迭代相互推動的這條迴圈，是這個時代最深的一條護城河。** 三者結合得越緊密，團隊就越能從實際問題中形成別人難以複製的積累。對模型團隊而言，應儘快讓有價值的任務與回饋進入訓練和評估，讓這條迴圈真正運轉起來。

對應用團隊，筆者的建議是：**把 Harness 作為短期最鋒利的技術槓桿，用它爭取時間，積累長期優勢。** 模型掌握了原先需要工程補足的能力後，相關實作會越來越容易被複制。獨特的資料、穩定的渠道、使用者信任、網路效應，以及人與 Agent 共同參與的物理世界場景，則需要長期經營。把產品做好、把使用者服務好，正是在利用這段時間建立自己的壁壘。

模型、API 和產品會繼續變化，「目前需要什麼資訊」「允許採取哪些行動」「怎樣驗證結果」仍會貫穿系統設計。理解這三個問題，就能判斷新能力適合放在什麼位置，哪些元件可以簡化，哪些環節需要補強。

筆者希望這本書能幫助你形成這樣的判斷力：從具體任務出發，理解 Agent 的結構，建構能夠執行的系統，再根據回饋持續改進。正文、配圖與配套實驗程式碼都已開源，歡迎親手執行實驗、嘗試新的方案，並透過 issue 和 PR 分享發現。Agent 能透過程式碼創造工具、擴展能力，也讓我們擁有了更多實作想法的方式。
