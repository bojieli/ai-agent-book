# 语音 Agent 的工具该由谁来调：前台实时模型，还是后台推理模型

用户说：“帮我查一下十二月三号北京到上海的航班。”助理要查一个需要两到五秒才返回的航班接口。由正在通话的实时语音模型自己发起查询，还是让它把任务交给后台的文本大模型？两种做法各差几秒，参数会不会填错，等结果的时候用户又开口了怎么办？

## 理解问题与方法

正文“认知时序：实时交互与深度思考”一节讨论了两种主张。一种认为前台实时模型应当直接调工具：直接调用只要两次模型推理（发出调用、念出结果），委派要四次（前台委派、后台发出调用、后台读结果、前台转述）。另一种认为前台不该碰工具：实时模型填参数可能不如文本大模型准，而且应当专心处理听和说的时机。本实验把同一批录音分别送进四种路由，量出每种做法在时延、参数、确认和插话上的实际表现。实验不预设哪种主张正确，验收脚本也只检查证据是否完整。

| 角色 | 实际使用 |
| --- | --- |
| 前台 | 豆包实时语音模型 3.0（Seeduplex），`session.model = 1.2.6.1`，`wss://openspeech.bytedance.com/api/v3/duplex/realtime/dialogue`，纯端到端模式 |
| 后台 | DeepSeek V4 Pro（火山方舟供应），关闭 thinking，temperature 0，经 OpenAI 兼容接口调用 |
| 工具 | **全部是模拟实现**（[`tools_sim.py`](tools_sim.py)）：返回固定夹具，延迟用 `asyncio.sleep` 注入 |
| 输入 | 预先合成的固定录音（[`fixtures/audio/`](fixtures/audio/)），按 20 毫秒一帧实时上行 |

### 五个模拟工具

| 工具 | 注入延迟 | 参数 | 结果 |
| --- | --- | --- | --- |
| `get_weather` | 0.2 秒 | 城市、日期 | 一句话 |
| `memory_lookup` | 0.02 秒 | 主题（枚举） | 一两句用户记忆 |
| `web_search` | 3 秒 | 关键词 | 约 600 字的搜索摘要，含无关内容，需要提炼 |
| `search_flights` | 2–5 秒 | 出发地、目的地、日期 | `speak`（91 字的一句话摘要）和 `display`（6 个航班、18 个报价的完整表，约 2600 字的 JSON，供屏幕显示） |
| `book_flight` | 2–5 秒 | 嵌套结构，13 个叶子字段 | 订单回执；有副作用 |

2–5 秒的延迟由固定种子生成，键是“场景、第几次运行、工具、会话内第几次调用”，不含路由，所以四种路由在同一次运行里拿到相同的延迟序列。`book_flight` 的模拟实现故意不校验参数：填错了也照样“出票”，错单才会留在记录里。夹具中的姓名、证件号、手机号、卡号、订单号全部是虚构的。

`book_flight` 的字段按取值来源分三类：`offer_id` 和 `quoted_price_cny` 来自前一轮的查询结果；舱位、退改规则、行李件数和重量是用户刚说的；乘机人的姓名、证件类型、证件号、手机和联系人的姓名、手机、邮箱来自用户资料。扩展场景“口述乘机人”把乘机人换成一位同事，姓名、护照号和手机号由用户口述，用来考察高熵的“刚听到”字段。

### 四种路由

| 路由 | 前台能调的工具 | 后台能调的工具 | 记忆 |
| --- | --- | --- | --- |
| 全前台 `all_front` | 五个工具 | — | 前台调 `memory_lookup` |
| 全后台 `all_back` | 只有 `delegate(task)` | 五个工具 | 后台调 `memory_lookup` |
| 按性质·航班前台 `by_property_flight_front` | `get_weather`、`search_flights`、`delegate` | `web_search`、`search_flights`、`book_flight` | 运行时注入 |
| 按性质·航班后台 `by_property_flight_back` | `get_weather`、`delegate` | 同上 | 运行时注入 |

“按性质”路由里，天气由前台直接调，网页搜索和订票委派给后台，记忆不经过任何模型决策。航班查询又慢、参数又简单，是有意保留的边界情形，所以两种放法都测。

委派时，后台拿到三样东西：到目前为止的通话记录（前台下发的语音识别转写和助理已说完的文本）、本次通话里已执行过的工具调用及结果（包括前台自己调的）、前台写的任务描述。后台返回的一段话作为 `delegate` 的函数结果交回前台，由前台转述。`display` 表格由运行时送到“屏幕”（只记日志）。前台自己调用 `search_flights` 时，函数结果里 `speak` 和 `display` 两份都有；委派时，完整结果只给后台，交回前台的只有后台写的那段话。

记忆注入的做法：运行时在建会话前做一次检索（0.02 秒），把结果写进 `session.create` 的 `instructions`；之后每轮结束再检索一次，用 `session.update` 刷新。本实验的记忆库只有三条，所以每次注入的内容相同。能力探针显示，会话建立后再注入的文本并不总是生效（见下文），所以这里测到的是“建会话时注入”的效果。

### 八个场景加一个扩展场景

| 场景 | 录音 | 考察 |
| --- | --- | --- |
| `weather`、`memory`、`web_search`、`flight_search` | 各一句 | 每个工具的普通请求 |
| `self_correction` | “帮我查一下下周三……不，下周四，北京到上海的航班”，中间停顿 0.7 秒 | 句中改口 |
| `pending_change` | 先查 12 月 3 号的航班；前台发出调用 1 秒后说“等一下，改成十二月四号的” | 结果未返回时改条件 |
| `pending_aside` | 先查航班；前台发出调用 1 秒后问“明天杭州天气怎么样？” | 结果未返回时插入另一个问题 |
| `booking` | 三轮：查航班 → “就订九点整起飞的那一班，经济舱，要可以退改的，再加一件二十三公斤的托运行李。乘机人和联系人都用我本人的信息。” → “确认，下单吧。” | 复杂参数与确认 |
| `booking_dictated`（扩展） | 第二轮改为口述同事的姓名、护照号、手机号 | 口述的高熵字段 |

给两个模型的提示词都写明“今天是 2026 年 11 月 25 日，星期三”，并直接给出“下周三是 12 月 2 日，下周四是 12 月 3 日”，这样改口场景考的是有没有听到更正，不掺入日历推算。完整提示词和工具定义保存在每次运行的 `manifest.json` 里。

### 指标的定义

- **用户说完**：录音最后一个 20 毫秒帧离开客户端的时刻。
- **实质回答**：工具或委派结果回传之后模型说的话。它的文本起点是“本轮某个结果回传之后、且本轮发出的函数调用都已得到结果时”收到的第一个 `response.output_text.delta`，音频起点是此后收到的第一个 `response.output_audio.delta`。前台没有发出任何调用的轮次，用户说完后的第一段话就是实质回答。
- **垫话**：用户说完之后、实质回答文本开始之前到达的音频，例如“好的，我查一下”。垫话和实质回答在豆包的协议里属于同一个 `response_id`，音频增量事件也不带文本对齐信息，所以只能按上面的时间规则切分。
- **LLM 调用数**：前台每发出一次 `response.function_call_arguments.done` 算一次，结果回传后的续说算一次，不调工具直接回答算一次；后台每次 chat completion 算一次。
- **参数准确率**：该轮第一次调用预期工具时的参数，与标准答案逐字段精确匹配（只去掉字符串首尾空白，类型也要一致）。`web_search` 的关键词是自由文本，改为要求同时包含“虹桥”和“会展中心”。委派路由里，评的是后台最终发出的那次工具调用。
- **确认前下单**：`book_flight` 的执行时刻早于“确认，下单吧”这段录音开始上行的时刻。
- **错单**：实际执行的 `book_flight` 里任何一个字段与标准答案不符。
- **读表**：航班查询的实质回答里出现了几个航班号（共 6 个），出现 4 个及以上记为“念了表”。
- 中位数和 P90 用线性插值；每格 10 次运行。

时延是在客户端量的，包含网络往返。音频到达比实时播放快（约 5 倍），所以“首音频到达”可以当作用户开始听到的时刻；服务端的 `response.done` 则在这段音频按 1 倍速播完时才下发。


密钥只从环境变量读取，只出现在 WebSocket 握手头和 HTTPS 请求头里。会话记录不保存请求头，音频只记字节数。如果网络出口有做 TLS 检查的代理，把 `SSL_CERT_FILE` 指向包含该机构根证书的证书包；不要关闭证书校验。

录音由 macOS 自带的 `say`（Tingting 音色，190 字/分钟）合成，经 `ffmpeg` 转成 16 kHz 单声道 int16，裁掉首尾静音，并把有声部分的 RMS 归一到 −27 dBFS（豆包文档对输入人声强度推荐范围的中心）。仓库不保存这些 WAV 文件，运行实验前先用 `python prepare_fixtures.py` 在本地生成（需要 macOS 的 `say` 和 `ffmpeg`）；每段录音的文字、时长和 SHA-256 记在 [`fixtures/audio/manifest.json`](fixtures/audio/manifest.json) 里。正式运行使用的录音以这些 SHA-256 为准；本机生成的文件在其他 macOS 版本上可能与之不同，验收脚本会照实报告不一致，录音不在本地时则跳过这一项检查。合成音干净、无口音、无噪声，不能代替真人通话。

## 分析结果与形成判断

下面的数字来自三次运行和一组能力探针，都在 2026 年 11 月 25 日完成：

- 主矩阵 [`doubao-seeduplex-20261125-v1`](validation/runs/doubao-seeduplex-20261125-v1/tables.md)：4 种路由 × 8 个场景 × 10 次，有效会话 320 通；
- 扩展场景 [`doubao-seeduplex-20261125-dictation-v1`](validation/runs/doubao-seeduplex-20261125-dictation-v1/tables.md)：口述乘机人，4 种路由 × 10 次，40 通；
- 串行对照 [`doubao-seeduplex-20261125-serial-control-v1`](validation/runs/doubao-seeduplex-20261125-serial-control-v1/tables.md)：全前台路由的天气和航班查询，一次只跑一通会话，20 通；
- 能力探针 [`validation/probes/`](validation/probes/)：v1—v4 各有一份 `probes.json`，v0 是写探针脚本之前的手工试验。

失败或作废的尝试（握手超时、连接断开、后台客户端因 HTTP 429/5xx 自动重试）列在各自 `tables.md` 的末尾，已重跑补足，没有计入统计。下文“a / b”表示中位数 / P90，单位为秒；除特别说明外，每格 n = 10。

### 时延：委派多花约 4 秒，工具慢也省不掉

表 A 摘自主矩阵的表 1，指标是“用户说完”到“实质回答首个音频”。**粗体**格是委派给后台的。

| 场景（工具注入延迟） | 全前台 | 全后台 | 按性质·航班前台 | 按性质·航班后台 |
| --- | ---: | ---: | ---: | ---: |
| 天气（0.2 秒） | 2.81 / 3.52 | **6.96 / 7.32** | 3.02 / 7.56 | 3.15 / 3.48 |
| 记忆（0.02 秒） | 3.53 / 7.33 | **6.98 / 9.93** | 1.91 / 2.34（注入） | 1.85 / 4.01（注入，n = 9） |
| 网页搜索（3 秒） | 6.05 / 10.36 | **10.80 / 17.56** | **10.97 / 12.37** | **11.67 / 17.10** |
| 航班查询（2–5 秒） | 7.79 / 17.03 | **12.15 / 19.11** | 7.83 / 13.98 | **11.70 / 13.64** |
| 口误更正（2–5 秒） | 6.89 / 11.19 | **10.96 / 15.73** | 6.81 / 13.36 | **11.52 / 15.64** |

“按性质·航班后台”的记忆场景有一次运行记下了回答文字，但按“实质回答”的切分规则找不到音频起点，表 1 记为“无回答”，时延按其余 9 次计算。

1. **调用次数与正文的算式一致。** 每一格的 LLM 调用数，中位数和 P90 都是：前台直接调用 2 次（前台 2 + 后台 0），委派 4 次（2 + 2），运行时注入 1 次（1 + 0）。
2. **多出来的时间就是后台花的时间。** 委派那一轮里，后台各次调用耗时之和的中位数在 3.43 秒（记忆）到 5.45 秒（网页搜索·按性质·航班后台）之间，后台已关闭 thinking。同一场景里，委派与前台直接调用的中位数之差为：天气 4.15，记忆 3.45，网页搜索 4.75—5.62，航班查询 4.36（全后台对全前台）和 3.87（两条按性质路由之间），口误更正 4.07 和 4.71。其他环节在各路由间差不多：“判停”0.82—1.08 秒，“结果回传→首音频”0.99—1.83 秒。
3. **差距不随工具变慢而缩小。** 天气工具只要 0.2 秒，差距 4.15 秒；航班工具要 2–5 秒，差距仍是 3.87—4.36 秒。工具越慢，差距占总时间的比例越小（天气全后台是全前台的 2.5 倍，航班查询约 1.6 倍），但绝对值没有变。差距的大小由后台模型的速度决定，换一个更快的后台会相应缩小。
4. **运行时注入最快。** 记忆场景下，注入的两条路由为 1.91 和 1.85 秒，比前台自己调用 `memory_lookup`（3.53 秒）快约 1.6 秒。
5. **垫话能填补一部分等待。** 委派路由常先说一句“好的，我查一下”：天气全后台 9/10 次有垫话，垫话首音频 1.78 / 1.83 秒。用户并不是干等 7 秒，但实质回答仍晚了 4 秒。
6. **订票各轮。** 第二轮“选择并提出订票”（`booking_select`），全前台 3.27 / 5.72，委派的三条路由为 10.78 / 13.17、14.04 / 22.52、14.47 / 17.72；第三轮“确认”为 12.31 / 14.46 对 17.19 / 25.56、17.42 / 22.45、15.58 / 19.12。扩展场景的口述一轮，全前台 3.22 / 3.69，委派为 15.56 / 28.17、18.63 / 28.49、11.56 / 16.67。

串行对照里，全前台的天气为 2.81 / 3.75，航班查询为 7.63 / 8.45，中位数与并行运行（2.81、7.79）几乎相同。航班查询的 P90 从并行时的 17.03 降到 8.45，说明并行时的长尾有一部分来自并发；每格只有 10 次，P90 本来就不稳，不宜细比。

### 参数：四种路由一样准

主矩阵表 2：天气、记忆、网页搜索、航班查询、口误更正五个场景，凡是调用了预期工具的路由，首次调用都是 10/10 精确匹配，回答也都含关键事实。口误更正场景里，四种路由“曾用更正前日期调用”都是 0/10。两条按性质路由的记忆场景不经过模型调用，“调用了预期工具”记为 0/10，这是设计如此。

订票（主矩阵表 5）：每种路由都下了 10 单，确认前下单 0，重复下单 0，错单 0，整包 13 个字段精确匹配 10/10。按来源分组：用户刚说的字段 40/40，来自查询结果的字段 20/20，来自用户资料的字段 70/70。复述中提到票价的，全前台 10/10，全后台 9/10，两条按性质路由 10/10。

所以“实时模型填参数不如文本模型准”在这组测试里没有得到支持：嵌套结构、取自上一轮工具结果的 `offer_id`、刚听到的枚举和数量，前台都填对了。要注意的是，录音干净，日期换算也已写进提示词，这里没有考察口音、噪声和复杂的日历推算。

### 口述乘机人：只在声音里的信息，会在交接时丢掉

扩展场景（`booking_dictated`）里，用户口述同事的姓名“陈嘉怡，耳东陈，嘉奖的嘉，怡然的怡”、护照号 E58307194 和手机号。

| 路由 | 错单数 | 确认后且全对 | `passengers[0].name` | 其余 12 个字段 |
| --- | ---: | ---: | ---: | --- |
| 全前台 | 0 | 10 | 10/10 | 全对 |
| 全后台 | 1 | 9 | 9/10 | 全对 |
| 按性质·航班前台 | 4 | 6 | 6/10 | 全对 |
| 按性质·航班后台 | 5 | 5 | 5/10 | 全对 |

10 张错单都错在姓名：8 张写成“陈佳怡”，2 张写成“陈佳宜”。确认前下单和重复下单都是 0。三条委派路由各只有 10 次，9、6、5 之间的差别不足以排序；合起来是 30 次对 20 次，对照前台自己订票的 10 次全对。

原因可以在记录里找到。

- **转写丢了用字说明。** 前台下发的语音识别文字在全部 40 通会话里都是“乘机人是我同事陈佳宜，尔东陈嘉奖的加怡然的怡，他（她）的护照号是 58307194……”。名字错了，“嘉奖的嘉”成了“嘉奖的加”，护照号开头的字母 E 也没了。后台拿到的通话记录就是这段文字。
- **前台听到的不一样。** 前台直接听音频，全前台路由 10 次都按“陈嘉怡”下单。委派路由里，前台写进任务说明的护照号 49 次全部是 E58307194，护照号字段因此 40/40 全对。
- **委派订票对不对，取决于任务说明里写的名字。** 30 次委派中，前台第一份订票任务说明写的是“陈嘉怡”的有 23 次：其中 15 次连用字说明一起写上，全部订对；8 次只写了名字，5 次订对，3 次订错。前台写成“陈佳怡”的有 7 次（其中 2 次后面还附着“嘉奖的嘉”，自相矛盾），全部订错。
- **那 3 次是怎么错的。** 后台发现任务说明和通话记录不一致，在要求复述的回复里提出了转写一侧的写法（两次问用户“陈佳宜还是陈嘉怡”，一次直接说“也就是陈佳怡”）。前台照着念了，模拟用户的录音是固定的“确认，下单吧”，不会回答这个问题；前台随后在确认下单的任务说明里改用后台的写法，后台就按它下了单。真实用户也许会纠正，这一点本实验测不出来。

结论是：前台从音频里听懂的内容，不等于转写文字。通话记录可以同步给后台，但它是有损的；姓名、数字、更正这类前台有把握的内容，要在任务说明里明写，并约定以前台为准。

另有一个与本主题无关、但影响委派质量的现象：后台关闭了 thinking，回复里仍偶尔带出推理过程和 `</think>` 标记（计入统计的会话里，主矩阵 240 次委派中有 14 次，扩展场景 72 次中有 14 次），前台有时会把其中一部分念出来。

### 念不念表

航班结果的 `speak` 摘要 91 字，`display` 表格的 JSON 2568 字，含 6 个航班、18 个报价。主矩阵（航班查询、口误更正、订票第一轮）和扩展场景共 16 格，口头回答的中位数在 87—106 字之间；160 次运行加串行对照 10 次，每次都只说出 1 个航班号，没有一次念出 `offer_id`，“念了 ≥4 个航班”都是 0/10。前台直接调用时，它拿到的函数结果里两份都有（约 2700 字），仍只照 `speak` 说。委派路由的口头回答由后台重写，口误更正场景略长（中位 106 和 104 字）。

### 等待中用户再次开口

主矩阵表 4，用户在前台发出调用 1 秒后开口；四种路由的第二句话都是在首个调用仍在等待时开始的（10/10），也都被转写（10/10）。

| 路由 | 改口：按新日期重查 | 改口：报新日期结果 | 改口：报旧日期结果 | 改口：第二句说完→正确回答 | 插问：得到回答 | 插问：第二句说完→回答 | 插问：原航班结果最终说出 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 全前台 | 10/10 | 8/10 | 2/10 | 6.91 / 8.88 | 10/10 | 3.05 / 4.13 | 0/10 |
| 全后台 | 10/10 | 10/10 | 0/10 | 10.72 / 13.50 | 10/10 | 6.53 / 9.25 | 1/10 |
| 按性质·航班前台 | 10/10 | 10/10 | 0/10 | 6.54 / 7.81 | 9/10 | 3.02 / 3.50 | 0/10 |
| 按性质·航班后台 | 10/10 | 10/10 | 0/10 | 11.20 / 12.89 | 10/10 | 3.02 / 3.57 | 0/10 |

- **改口。** 全前台有 2 次报了旧日期的结果，同样由前台调航班的“按性质·航班前台”是 0 次；n = 10 时，2/10 与 0/10 的差别还说明不了路由的优劣。委派路由都答对了，但慢约 4 秒，第二句之后的 LLM 调用数为 6，前台路由为 2。
- **插问。** 插问的天气几乎都得到了回答；全后台的天气也要委派，所以慢（6.53 秒）。原来那次航班查询的结果，在 40 次运行里只有 1 次最终被说出来。

能力探针确认了这一点，并说明结果并非没送到：`pending_aside` 中，结果在插问答完之后回传（工具延迟 14 秒），模型 0/5 说出，回传后也没有说任何话；`pending_aside_reask` 中，结果已在用户再问之前回传（5/5），用户再问一遍，模型 5/5 重新调用 `search_flights`，没有直接用已在上下文里的结果；第二次的结果回传后，它依然 0/5 说出。这 5 次里，第二次调用发出后、结果回传前，服务端都自行开始了一轮新的语音识别（客户端当时只发静音），原因不明。由此看，运行时要自己记下哪些结果还没说出口，并负责让它们重新被提起；不论工具由谁调用，这件事都省不掉。本实验没有实现这一机制。

### 豆包实时接口的能力（探针）

| 探针 | 做法 | 结果 |
| --- | --- | --- |
| `fc_basic` | 问明天杭州天气，前台可调 `get_weather` | 5/5 发出调用，参数都是“杭州、2026-11-26”；5/5 说出结果 |
| `pending_silent` | 工具延迟 8 秒（5 次）和 10、12、14、16、20 秒（各 3 次），用户不说话 | 20/20 等待期间没有任何音频；结果回传后 20/20 说出 |
| `pending_change` | 等待中改日期，工具延迟 8 秒 | 5/5 转写了改口，5/5 按新日期重查并报出新结果，0/5 报旧结果 |
| `pending_aside` | 等待中插问常旅客卡号，工具延迟 14 秒 | 5/5 在等待中回答插问；结果回传后 0/5 说出 |
| `pending_aside_reask` | 同上，回传后用户再问一遍航班 | 5/5 重新调用；第二次结果回传后 0/5 说出 |
| `push_speech` | 运行时发 `speech_text_buffer.commit` 推送一段话 | 5/5 播出，首个音频在 0.35—0.38 秒后到达 |

可见前台发出调用后仍在听，用户开口能被转写、得到回答；用户不说话时，它在等待期间不会主动出声。运行时可以推送一段话让它播报，这是把未说出的结果重新提起的一条现成途径。

v1 的“一轮之后”先问的是天气（未声明工具，模型说“我帮你查一下”），注入卡号后再问卡号，5 次都答“没办法记住你的常旅客卡号”；v2 先问卡号（同样拒答），注入天气后再问天气，大多用上了。v0 的手工试验里，一轮之后注入卡号又是 4/4 和 3/3 生效。这几组的内容和先后顺序都不同，分不清是哪个因素起作用。能确定的只有：建会话时写进指令稳定生效，第一轮之前补的都没生效，会话中途补的时灵时不灵。“运行时每轮注入记忆”在这个接口上只部分可行；本实验的记忆库内容固定，测到的实际是建会话时注入的效果。

### 和原先设想的对照

- **按性质分配路由**：没有得到支持。前台调用每个工具都和后台一样准，而且更快；委派网页搜索和订票多花了 4 秒以上，没有换来准确率；口述姓名时反而更容易错。按性质路由唯一明显的收益来自记忆的运行时注入，而这一点与工具交给谁无关。
- **航班查询是两可的边界情形**：不成立。在这对模型上它明显该由前台调用（7.79、7.83 对 12.15、11.70）。
- **工具越慢，委派的代价越可以忽略**：不成立。差距约等于后台模型花的时间，与工具快慢无关。
- **得到支持的部分**：运行时注入记忆最快；所有路由都没有在确认前下单或重复下单；口头摘要与屏幕表格分开后，没有一次念表。
- **没有测到的部分**：需要多步推理、比较多种方案的任务（例如比较几种改签方案）、长上下文、带口音和噪声的真人语音、能回答追问的用户。委派后台的理由如果存在，应当在这些地方去找。

### 局限

- 工具全部是模拟的，延迟是注入的固定序列；真实接口的耗时分布和失败情况不同。
- 录音由 macOS `say` 合成，干净、无口音、无噪声；用户是固定录音，不会回答助理的追问。
- 只测了一个前台模型（豆包实时语音模型 3.0，会话模型版本 1.2.6.1）和一个后台模型（DeepSeek V4 Pro，关闭 thinking），只测了一天。
- 每格 10 次；P90 尤其不稳，相差一两次的比例不足以区分路由。
- 时延在客户端测量，包含网络往返；主矩阵以并发 5 运行，串行对照只覆盖全前台的两个场景。

## English

This experiment asks who should call a voice agent's tools: the realtime voice model at the front, or a text model at the back. The front is Doubao Realtime Voice Model 3.0 (Seeduplex, session model 1.2.6.1) in pure end-to-end mode; the back is DeepSeek V4 Pro on Volcano Ark with thinking disabled. Five simulated tools (weather, memory, web search, flight search, flight booking) return fixtures after injected delays. Fixed recordings synthesised with macOS `say` are streamed in real time. Four routes are compared (all-front, all-back, and two property-based routes that differ in where flight search goes), with 10 runs per cell, all on 2026-11-25.

Findings for this model pair:

- **Latency.** A direct front call takes 2 model calls and a delegated one takes 4. Delegated and direct medians differed by 3.45–5.62 s, close to the median 3.43–5.45 s spent in the back model per delegation; the gap did not shrink for the 2–5 s flight tool (median 7.79 vs 12.15 s). Runtime injection of memory was fastest (1.85–1.91 s vs 3.53 s for a front call). A serial control reproduced the all-front medians.
- **Arguments.** Every route scored 10/10 on every single-call scenario and on the 13-field booking, with no stale date after a self-correction, no booking before confirmation and no duplicate bookings.
- **Dictated name.** When the user spelled out a colleague's name, the front booked it right 10/10, while delegated routes got 9/10, 6/10 and 5/10, all errors in the name. The ASR transcript sent to the back had lost the spelling; correctness depended on whether the front wrote the name it heard into the task note.
- **Pending results.** The front keeps listening while a call is pending but stays silent unless spoken to. After a side question, the original flight result was almost never spoken (1 of 40 runs), even though it had been delivered to the model. The runtime has to track unspoken results itself.
- **Not tested.** Multi-step reasoning or comparison tasks, noisy or accented speech, and users who answer clarifying questions.
