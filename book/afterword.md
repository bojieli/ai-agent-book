# 后记：回到 Agent = LLM + 上下文 + 工具 {.unnumbered}

本书开篇提出了一个公式：**Agent = LLM + 上下文 + 工具**。全书十章，都在这三个词里展开。

第一章解释这个公式，随后各章分别讨论上下文、知识、工具、交互，以及如何评估和改进它们。

实际项目中的问题常常跨越章节：一次任务失败，可能是缺少信息、工具接口不合适，也可能是模型没有正确使用已有证据。记录轨迹、定位原因，再做有针对性的修改，是我希望读者从这本书中带走的工作方法。

## 两个待解的问题 {.unnumbered}

写完本书，仍有两个问题让我持续关注：Agent 怎样实时应对变化，以及怎样从长期使用中学习。

**第一个问题是实时交互。** 对话可能被打断，界面会变化，任务执行中也会收到新消息。Agent 需要在这些变化发生时更新判断，而不只是更快地完成一轮回答。第六章介绍了快慢分离和原生异步等尝试；推理加速也能缩短等待，例如 MiMo 与 Taalas 分别从推理系统和专用芯片入手提高生成速度[^mimo][^taalas]。但更高的 token 吞吐量并不自动解决打断、事件调度和过期动作的问题。

**第二个问题是从经验中学习。** 模型的参数不会在每次推理后自动更新；即使保存了轨迹，也还需要判断哪些经验值得复用。这是第三章记忆系统与第九章持续进化共同面对的问题。

我把两种侧重点暂称为“小世界”与“大世界”假设。前者相信，扩充训练数据可以让模型提前掌握更多通用知识与技能，减少部署后的补救。这个思路把重点放在数据覆盖与训练能力上。

后者更关注部署后不断变化的具体情境：公司的代码规范、用户的表达偏好、新版工具接口，以及实验中才出现的结果。这些信息需要在使用中取得，再决定写入知识、指令、程序还是参数。我更关心的是，系统能否在获得新经验后改善行为，同时保留原本有效的能力。

这两个问题都需要模型与应用系统共同改进。

## 模型与 Agent 的共同演进 {.unnumbered}

应用系统中的压缩、重试和恢复逻辑，常常来自模型在实际任务中暴露的不足。经验证的失败案例可以成为下一轮训练的数据；模型能力改善后，部分补救逻辑也可能简化。但业务权限、外部状态和验收规则仍需要明确的系统实现。

第一章提出过一个问题：**模型会不会最终取代 Harness？** 我的判断是，二者的边界会继续变化。例如，一些交互行为可以从外部流程进入模型，但模型是否获得某项权限、退款是否到账、交付物是否通过检查，仍要由运行环境提供依据。升级模型后，应重新测试哪些流程可以删除，哪些约束必须保留。

模型和应用由同一团队开发时，更容易把运行问题反馈到训练中，也更容易共同调整接口。外部应用团队同样可以积累任务集、失败轨迹和用户反馈，用它们评估模型升级，并判断是否需要改动 Harness。

对应用开发者而言，我建议持续维护三类材料：真实任务及其验收条件、能够复现问题的轨迹，以及每次修改的对照结果。它们比某个框架的暂时优势更容易保留下来，也能帮助团队解释为什么采用或放弃某项设计。

本书中的 API、产品和榜单会变化。重新选型时，仍可以回到几个具体问题：Agent 看到了什么，能采取什么动作，结果由谁验证，失败后如何恢复。

本书正文、配图和实验代码均已开源。欢迎在自己的环境中运行实验，记录与书中不同的结果，并通过 issue 或 PR 交流。课程和 Pine AI 的实践推动了这本书的写作，我也期待它在更多实际项目的反馈中继续修订。
