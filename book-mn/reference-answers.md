# Бодох асуултуудын жишиг хариулт

Энэ файлд номын арван бүлгийн бодох асуултуудын жишиг хариултын ерөнхий бүтцийг нэгтгэсэн. Ихэнх асуулт нээлттэй бөгөөд ганц зөв хариултгүй. Жишиг хариултуудыг AI-ээр үүсгэж, хүн хөнгөн хянан засварласан тул зөвхөн уншигчид харьцуулж үзэх, шинэ санаа авах зориулалттай. Уншигчид номын агуулгыг LLM-тэй хамт ашиглан эдгээр асуултыг цааш хэлэлцэхийг зөвлөж байна.

## Бүлэг 1: AI Agent-тай ажиллаж эхлэх нь

**1. (★★) Agent системд зөвхөн нэг чадвар нэмэх боломжтой бол илүү хүчтэй Model, илүү баялаг Context, эсвэл илүү олон Tool-ийн алийг сонгох вэ? Ямар нөхцөлд сонголт тань өөрчлөгдөх вэ?**

> «Тархи/нүд/гар, хөл» томьёог дагаж эхлээд сул холбоосыг ол. Ихэвчлэн Context-ийг баяжуулах, өөрөөр хэлбэл ажиглалтын орон зайг өргөжүүлэх нь тэргүүлэх зорилт байдаг. Хэрэв даалгавар Model-ийн дүгнэлт хийх чадвараас хэтэрвэл илүү хүчтэй Model сонго. Үйлдлийн орон зай хангалтгүй (жишээ нь байгууллагын дотоод системд нэвтрэх боломжгүй) бол Tools нэм. Үүнийг тогтоохдоо бүтэлгүйтсэн ажлын явцын бүртгэлийг шинжилж, саад нь мэдээлэл хүлээн авах, шийдвэр гаргах, эсвэл үйлдэхийн алинд байгааг олно.

**2. (★★★) ReAct давталтад кэшээс унших нийт хэмжээ давталтын тооноос ойролцоогоор квадрат хамааралтай өсдөг. Энэ өсөлтийг хэрхэн бууруулах вэ?**

> i дэх ээлжинд кэшлэгдсэн угтварын урт ойролцоогоор i-тэй пропорциональ учраас нийт уншилт 1 + 2 + ... + n = O(n²) болно. Квадрат өсөлт нь кэшээс унших нийт төлбөрт хамаарах бөгөөд ажлын явцын бүртгэлийн урт, KV Cache-ийн эзлэх хэмжээ ойролцоогоор шугаман өсдөг. Token-ийн тодорхой босго хүрэхэд эхний хэсгийн бүртгэлийг багцаар шахаж, дүгнэлт болон чухал төлөвийг хадгал; их хэмжээний завсрын үр дүнг шаардлагатай үед татаж авах гадаад хадгалалтад шилжүүл, эсвэл дэд Agent-д тусгаарла. Ээлж бүрд шахалт хийх хэрэггүй: энэ нь Agent-ийн гүйцэтгэлийг муутгаж, нэмэлт шахалтын дуудлага, кэшийг дахин бүтээх зардал үүсгэдэг.

**3. (★★) «Model as Agent» хандлага нь Model-ууд Tool дуудах шийдвэрээ улам бие даан гаргадаг болж байгааг илэрхийлнэ. Гэтэл энэ бүлэгт Harness инженерчлэлийн ач холбогдол нэмэгдэж байна гэж үзсэн. Энэ хоёр чиг хандлага хэрхэн зэрэгцэн орших вэ? Agent-ийн Framework-уудын ирээдүйн үндсэн үнэ цэн юунд орших вэ?**

> Морь ба жолооны зүйрлэл: Model хүчтэй, бие даасан байдал өндөр болох тусам алдааны нөлөөллийн хүрээ томорч, хязгаарлалт, баталгаажуулалт, засвар улам хэрэгтэй болно. Framework-ийн үнэ цэн «LLM дуудлагыг зохион байгуулах»-аас Harness-ийн таван бүрэлдэхүүн дэх найдвартай байдлыг хангах давхарга руу шилжинэ: зөвшөөрөл ангилах, хэлхээ таслагч, алдаанаас сэргээх, Context шахах, Tool-ийн экосистем.

**4. (★★) Бүрэлдэхүүн хасах туршилтад «Tool-ийн үр дүнгийн эргэх холбоо» байхгүйгээс Agent хязгааргүй давталтад орсон. Бодит ашиглалтын орчинд үр дүн дутсанаас гадна өөр ямар нөхцөл Agent-ийг давталтад оруулж болох вэ? Үүнийг илрүүлэх, зогсоох ямар механизм зохион бүтээх вэ?**

> Бусад шалтгаан: Tool нэг алдааг дахин дахин буцаах; байхгүй Tool-ийг зохиож дуудах; Context шахахдаа чухал төлөвийг гээх; дүгнэлтийн агуулгыг арилгахад Model-ийн API алдаа өгөх; даалгавар өөрөө шийдэх боломжгүй байх. Шийдэл: давталтын дээд тоо зэрэг зогсоох нөхцөл тогтоох; ижил Tool, ижил аргументын хурууны хээтэй давтан дуудлагыг илрүүлэх; алдааны босго давбал хүний оролцоонд шилжүүлэх.

**5. (★) Энэ бүлэгт таван Agent бүтээгдэхүүнийг ажлын Context, үйлдлийн интерфейс, стратеги гэсэн гурван хэмжээсээр шинжилсэн. Өдөр тутам хэрэглэдэг AI бүтээгдэхүүнээ ижил аргаар шинжилж, архитектур нь тохиромжтой эсэхийг дүгнэ. Та түүнийг зохион бүтээвэл юуг сайжруулах вэ?**

> Нээлттэй асуулт. Гол санаа: бүлгийн хүснэгтийг дагаж «нүд» (ямар мэдээллийн эх сурвалж харж чаддаг), «гар, хөл» (үйлдлийн орон зай нь нээлттэй эсэх, дотроо дүгнэлт хийж чаддаг эсэх), стратеги (Agent-ийн гүйцэтгэлийн давталтын хэв маяг)-ийг тодорхойлон бич.

**6. (★★) Зөвхөн нислэгийн тасалбар захиалах хэрэглэгчийн үйлчилгээний систем зохион бүтээвэл ажлын урсгалын хэв загвар уу, автономит Agent-ийн хэв загвар уу? Хоёуланг нэг системд хослуулж болох уу?**

> Ажлын урсгалыг үндсэн тулгуур болго: таних баталгаажуулалт → хайлт → төлбөр → захиалга гэсэн дөрвөн зангилаатай байх нь «төлбөрөөс өмнө захиалга хийхгүй» гэх зөв дарааллыг баталгаажуулж, Prompt Injection халдлагын хүрээг нэг зангилаанд хязгаарлана. Нээлттэй хэсгүүдэд (шаардлага ойлгох, дахин захиалах, нислэг цуцлагдсан үед хувилбар санал болгох) автономит Agent ашигла. Өндөр эрсдэлтэй үйлдэлд (их хэмжээний төлбөр, буцаан олголт) хүний баталгаажуулалт нэм.

**7. (★★★) Хамгаалалтын хязгаарлалтын хэсэгт Tool-ийн эрсдэлийн үнэлгээг дурдсан. Ерөнхийдөө бага эрсдэлтэй Tool тодорхой параметрийн хослолд өндөр эрсдэлтэй болдог бол (жишээ нь `delete_file` ердийн файл устгах ба системийн файл устгах) динамик эрсдэлийн үнэлгээг хэрхэн зохион бүтээх вэ?**

> Үнэлэх нэгжийг «Tool»-ээс «Tool + аргумент» болгон нарийвчил: дуудлага бүрд буцаах боломж, зөвшөөрөл, нөлөөллийн хүрээнд тулгуурлан эрсдэлийг тооц. Model-ийн дүгнэлтэд найдах бус дүрэмд суурилсан тодорхой шалгалт (зөвшөөрсөн/хориглосон замын жагсаалт, тогтмол илэрхийлэл) ашигла. Prompt Injection-ээр нөлөөлөхөөс сэргийлж баталгаажуулалтыг зөвхөн бүтэцтэй өгөгдөлд тулгуурлан хий.

**8. (★★) Энэ бүлгийн Agent бүтээгдэхүүний хүснэгтэд бүгд «нээлттэй» үйлдлийн орон зайтай. Ямар нөхцөлд хязгаарлагдмал үйлдлийн орон зай (жишээ нь зөвхөн урьдчилан тодорхойлсон сонголтоос сонгох) нээлттэй орон зайгаас давуу байх вэ?**

> Дүрэм мөрдөх өндөр шаардлагатай, өндөр эрсдэлтэй, буцаах боломжгүй алдаа үүсэх нөхцөлд. Буцаан олголт, төлбөрийн хувьд хязгаарлагдмал сонголтууд нь системийн «хязгаарлалт» бөгөөд алдааг анхнаас нь боломжгүй болгох дизайны арга юм.

**9. (★★) Хүн оролцдог механизмд Agent «удирдлагыг хүнд зүй зохистой шилжүүлэх» ёстой. Гэвч хэрэглэгч сүлжээгүй, удаан хариу өгдөг, эсвэл бүдэг заавар өгдөг бол Agent яах ёстой вэ?**

> Аюулгүй анхдагч горим: баталгаажуулалт ирээгүй үед өндөр эрсдэлтэй үйлдлийг автоматаар хийхгүй, түр зогсоо; буцаах боломжтой, бага эрсдэлтэй хэсгийг эхлээд гүйцэтгэж, өндөр эрсдэлтэй хэсгийг хүн шийдэхээр баримтжуулан Agent дараа нь үргэлжлүүлэх боломж үлдээ; хугацааны хязгаартай асинхрон харилцааны хэрэгслээр (мессеж, цахим шуудан) мэдэгд; заавар тодорхойгүй бол зорилгыг тодруул.

**10. (★★★) Танилцуулгад «дизайны сайн зарчим Model-ийн шинэчлэлийн мөчлөгийг даван оршино» гэжээ. Гэвч тэдгээрийг хэрэгжүүлдэг инженерчлэлийн тодорхой арга Model-ийн чадвар сайжрахын хэрээр хуучирч болно. Ийм аргын жишээ гаргаж, шалтгааныг тайлбарла.**

> Жишээ 1: Tool дуудлагыг хатуу форматтай болгохын тулд хязгаарласан түүвэрлэлт хэрэглэх. Энэ нь хүчингүй JSON гаргадаг, эсвэл параметр орхигдуулдаг Model-ийн найдвартай байдлыг нөхөх арга. Model формат мөрдөхдөө сайжирвал ашиг нь багасаж болох ч өндөр эрсдэлтэй нөхцөлд тодорхой формат шалгалтыг хадгалах ёстой.
>
> Жишээ 2: Model шинэ мэдлэгийг тасралтгүй шингээж чаддаггүйг нөхөхийн тулд гадаад мэдлэгийн сан нэмэх. Model найдвартай тасралтгүй суралцах чадвартай болбол мэдлэгийн удирдлагын зарим хэсэг гаднын системээс Model-ийн параметр рүү шилжиж болно. Гэхдээ гадаад мэдлэгийн сан бодит цагийн шинэчлэлт, яг таг хайлт, хандалтын удирдлага, эх сурвалжийн мөрдөх боломжийн хувьд бие даасан үнэ цэнтэй тул бүрэн алга болохоосоо илүү хамрах хүрээ нь багасна.
>
> Жишээ 3: Бүх чадварыг Model-ийн API дахь стандарт Tool дуудах интерфейсээр заавал ил гаргаж, өөр форматаар дуудахыг хориглох. Skills өөр нэг замыг харуулдаг: чадвар болон ажиллуулах дарааллыг текстээр тайлбарлаад ерөнхий зориулалтын командын мөрийн Tool-ээр Model-д гүйцэтгүүлэх. Model-ийн үүднээс энэ нь ерөнхий гүйцэтгэгч дээр давхарласан тусгай текстэн дуудлагын протоколыг ойлгон мөрдөхтэй адил. Model янз бүрийн интерфейсийг ойлгохдоо сайжрахын хэрээр «стандарт Tool дуудах форматыг үргэлж ашигла» гэдэг нь бүх нөхцөлд мөрдөх зарчим байхаа болино. Стандарт формат харилцан нийцэл, бүтэцтэй баталгаажуулалт, харьцангуй сул Model-д хэрэгтэй хэвээр ч нөхцөлөөс хамаарсан инженерчлэлийн сонголт болно.
>
> Жишээ 4: Prompts болон бүх Tool-ийн тодорхойлолтыг Context-ийн эхэнд заавал байрлуулах. Эрт үеийн Model-ууд заавар дагах чадвар хязгаарлагдмал, хэвшмэл байрлалаас гадуурх Prompt, Tool-ийн тодорхойлолтыг таньж, хэрэгжүүлж чаддаггүй байснаас энэ дадал үүссэн. Skills хэрэгцээний дагуу Prompt-ийг Context-ийн дунд ачаалдаг бол динамик Tool илрүүлэлт шинээр олсон тодорхойлолтыг одоогийн ажлын явцын бүртгэлийн ард нэмдэг. Заавар дагах чадвар сайжирч, Model-ууд ийм динамик ачааллын хэлбэрт зориулсан сургалтын дараах шатны сургалт авах тусам Prompt болон Tool-ийн тодорхойлолтыг Context-ийн эхэнд тогтмол байрлуулах шаардлагагүй болно.

## Бүлэг 2: Context-ийн инженерчлэл

**1. (★★★) Туршилт 2-3-т харилцан ярианы түүхийг гүйдэг цонхоор хадгалахад Agent ижил Tool дуудлагыг дахин дахин хийдэг нь тогтоогдсон. Гэтэл бүтэн түүхийг хадгалбал Context хязгааргүй өснө. KV Cache-ийн угтварыг эвдэхгүйгээр мэдээлэл алдалгүй Context-ийн уртыг хянах стратеги зохио.**

> ① Устгахын оронд шахалт ашигла: мессежүүдийг зөвхөн нэмж, өмнөхийг нь устгахгүй, засахгүй; цонхны дээд хязгаарт (жишээ нь 80%-д) ойртоход хуучин Tool-ийн үр дүнг багцаар шах. ② Давхарласан механизм: их хэмжээний Output-ийг хураангуйн хамт дискэнд хадгал, хэрэггүй шуугиантай мэдээллийг бүрмөсөн устга, харин үйл явдлын шугамыг хадгалдаг архивын хураангуйг үлдээ. ③ Дэд Agent-уудыг тусгаарлаж, завсрын төлөв үндсэн Context-д огт орохгүй болго.

**2. (★★) Qwen3-ийн Chat Template дахь бодлын гинж хадгалах механизм зөвхөн «жинхэнэ хэрэглэгчийн сүүлийн мессежийн дараах» дүгнэлтийн агуулгыг хадгалдаг. ReAct давталт хэдэн зуун Tool дуудлага үргэлжилбэл хуримтлагдсан дүгнэлтийн агуулга Context-ийн ихээхэн хэсгийг эзэлнэ. Маш урт давталтад энэ механизмыг хэрхэн өөрчлөх вэ? DeepSeek R1 өмнө нь бүх хуучин дүгнэлтийг арилгах шаардлагатай байсан бол DeepSeek V4 үүнийг эсрэгээр эргүүлж, бүх `reasoning_content`-ийг буцаан дамжуулахыг шаардсан. Эдгээр эсрэг стратегийн давуу, сул талыг харьцуулж, өөрчлөлт юуг илэрхийлж байгааг тайлбарла.**

> Сайжруулах чиглэл: гүйдэг цонхоор хадгалах — сүүлийн хэдэн ээлжийн дүгнэлтийг бүрэн үлдээ; цонхны гаднах хэсгийг ээлжийн тогтмол тоогоор бус Token-ийн төсөвт тулгуурлан үе үе шахаж, бүтэцтэй төлөвийн мөр (одоогийн зорилго, батлагдсан баримт, үгүйсгэсэн хувилбар, хийх зүйл) гарга. Шахалтыг тогтмол байрлалд нэг л удаа хийснээр ээлж бүр бус зөвхөн тэр үед кэшийг дахин бүтээх зардал гарна. R1-ийн арилгах арга: Token хэмнэнэ, угтварыг тогтвортой байлгаж кэш ашиглахад таатай, сургалтын өгөгдлийн тархалттай нийцнэ (өмнөх CoT Input-д орохгүй); харин ээлж бүр шинээр дүгнэлт хийх тул урт хугацааны төлөвлөгөө алдагдаж, алдаа давтагдана. V4-ийн заавал буцаах арга: бодлын уялдаа сайжирч, урт хугацааны Agent даалгаврын гүйцэтгэл дээшилнэ; харин Token-ийн зардал өндөр, угтвар ээлж бүр хэт томорно, бодохгүй горим руу саадгүй шилжиж чадахгүй. Энэхүү эргэлт цэвэр харилцан ярианд дүгнэлтийн түүх илүүдэл байж болох ч Agent-ийн ажилд дүгнэлт нь төлөв болж байдгийг харуулна. Салбарын практик сүүлийнх рүү чиглэжээ.

**3. (★★) Context-д мэдрэмжтэй шахалтын туршилтад ойролцоогоор 148 мянган тэмдэгтийг 2000 орчим болтол шахсан. Ийм эрс шахалт «эргүүлж сэргээх боломжгүй мэдээлэл алдалт» үүсгэх үү? Үүнийг хэрхэн шийдэх вэ?**

> Тийм, эрсдэлтэй: шахалт нь алдагдалтай дүрслэл тул асуулт хадгалж үлдээгээгүй мэдээлэлд хамаарвал хариулт бүтэлгүйтнэ. Шийдэл нь «алдагдалтай шахалт + алдагдалгүй индекс»: баримт бүрд эх сурвалжийн URL холбож, эргэн мөрдөх боломж үлдээ; эх Output-ийг дискэнд хадгалж, Context-д зөвхөн хураангуй харуул; архитектурын шийдвэр, утгын бүрэн байдал (цаг хугацаа, компанийн нэр), баталгаажуулалтын төлөв, UUID/хэш зэрэг таних тэмдэгтийг яг хэвээр хадгалах тэргүүлэх журам тогтоо; дасан зохицох цонхоор шахалт хийх мөчийг хойшлуул.

**4. (★★) Agent-ийн төлөвийн мөр далд төлөвийг ил тод болгодог. Гэвч төлөвийн мөр өөрөө алдаатай мэдээлэл агуулбал (жишээ нь Tool-ийн тоолуурт алдаа гарвал) Agent буруу мэдээлэлд тулгуурлан хор уршигтай шийдвэр гаргаж болно. Энэ «мета мэдээллийн найдвартай байдал»-ын асуудлыг яаж бууруулах вэ?**

> Model төлөвийн мөрөнд бараг болзолгүй итгэдэг тул алдаа шууд дамжина. Шийдэл: ① тодорхой үр дүнтэй кодоор мөрийг удирд — урт түүхийг LLM-ээр бөөнд нь тоолуулахгүй (зайлшгүй бол зүйл бүрийг салгаж, кодоор нэгтгэ); ② төлөвийн мөрийн нарийвчлалыг бодит ашиглалтын үндсэн хэмжүүр болго; ③ мэдээллийг зөвхөн бодит ертөнцийн найдвартай ажиглалтаас авч, төлөвийн мөрийг хордуулах оролдлогоос хамгаал.

**5. (★★) Prompt-ийн инженерчлэлийн бүрэлдэхүүн хасах туршилтаас замбараагүй мэдээлэл амжилтын түвшнийг 30 гаруй хувиар бууруулдгийг харуулсан. Гэвч бодит хөгжүүлэлтэд системийн Prompts-ийг өөр өөр цагт олон хүн засварладаг. Цаг хугацаа өнгөрөх тусам системийн Prompts эмх замбараагүй болохоос сэргийлэх ямар дадал ашиглах вэ?**

> ① Prompts-ийг кодтой адил авч үз: хувилбарын хяналт, хянан батлах процесс хэрэглэж, бүтээгдэхүүний менежер бизнесийн дүрмийг тодорхойлж, инженерүүд хэрэгжүүлнэ. ② Tau-Bench-тэй төстэй жишиг тестийг регрессийн шалгалтад ашиглаж, өөрчлөлтийн өмнө ба дараа бүрэлдэхүүн хасах туршилт хийж нөлөөг тогтоо. ③ Олон замбараагүй дүрэм нэмж бөөгнүүлэхийн оронд SOP-д суурилсан урсгал, XML/Markdown давхарласан бүтэц мөрд. ④ Хэсгүүдийг «кэшлэгдэх/кэш эвдэх» гэж ангилан нэрлэж, динамик агуулгыг кэшийн заагийн хойно байрлуул. ⑤ Хэт том агуулгыг хэрэгцээний дагуу ачаалах Skills-д салга.

**6. (★★★) Энэ бүлэгт «Context дотор суралцах нь үндсэндээ дүгнэлт биш, харин хайлт» гэсэн санаа дэвшүүлсэн. Үнэн бол «Context-д илүү их мэдээлэл хийх»-д суурилсан өнөөгийн бүх оновчлолыг дахин үнэлэх шаардлагатай. Энэ хязгаарлалтыг хэрхэн даван туулах вэ?**

> Энэхүү «хагас хайлтын хөдөлгүүр»-т нэрж нэгтгэх давхарга нэм: ① Context-ийг нэрж нэгтгэх/төлөвийн мөр — шууд татаж ашиглах дүгнэлтүүдийг кодоор урьдчилан тооц; ② идэвхтэй шахалт — түүхий бүртгэлийг өндөр нягтралтай бүтэцтэй мэдлэгээр орлуул; ③ дэд Agent-ийг тусгаарлаж, үндсэн Context-д хэрэггүй шуугиан оруулахгүй байх; ④ гурав дахь хэмжээс болох харилцан үйлчлэл — гадаад хэрэгслүүд Model өөрөө бодож олж чадахгүй шинэ мэдээллийг ажиглан буцааж бичих; ⑤ тэргүүлэх чиглэл — засварлаж, нэгтгэж болох KV Cache-ийн «тэмдэглэл» болон олон сесс дамнасан Memory нэгтгэл.

**7. (★★★) Skills-ийн шаталсан ил болголт нь Agent хэрэгтэй гэж үзсэн үед л бүрэн агуулгыг ачаалдаг. Гэвч энэ дүгнэлт Model-ийн чадвараас хамаарна. Model өөрөө юу мэдэхгүйгээ мэдэхгүй бол Skill-ийг зөв ачаалж чадахгүй. Энэхүү «өөрийн мэдлэгээ таних» асуудлыг хэрхэн шийдэх вэ?**

> ① Skill-ийн мета өгөгдөл (нэр, тайлбар)-ийг Context-д байнга байрлуулж, Model «өөрт нь юу байгааг» үргэлж мэддэг болго; ② Skill-ийн тайлбарыг бүдэг функцийн танилцуулга бус, «Хэзээ хэрэглэх / Хэзээ хэрэглэхгүй» гэсэн чиглүүлэлтийн нөхцөлөөр бич.

**8. (★★) Skills механизмд Agent `SKILL.md`-ийн зааврыг динамикаар ачаалсны дараа цаашдын үйлдэл түүнийг найдвартай дагаж чадах уу? Skills-ийн хэв загварыг дэмжих Model-уудын хооронд ямар ялгаа байдаг вэ?**

> Skill-ийг хаана оруулснаас хамаарна: системийн Prompt-д оруулахад заавар дагах чадвар хамгийн сайн боловч KV Cache эвдэрнэ; Context-ийн дунд ердийн файл шиг уншуулахад заавар дагах чадвар сул байж болно; Context-ийн төгсгөлд оруулахад заавар сайн дагадаг боловч Tool дуудлага бүрд Skill-ийн хэсгийн KV-г дахин тооцох шаардлагатай тул зардалтай.

**9. (★★★) Динамик мэдээлэл (жишээ нь системийн цаг, Tool-ийн жагсаалтын дараалал) өөрчлөгдөхөд KV Cache-ийн угтварын таарцыг эвдэж болохыг энэ бүлэг онцолсон. Маш олон Tool-тэй, Tool-ийн багц нь байнга өөрчлөгддөг бодит системд кэш таарах хувийг хамгийн их байлгах Context-ийн бүтцийг хэрхэн зохион байгуулах вэ?**

> ① Цөөн тооны (жишээ нь долоон) тогтвортой үндсэн Tools дээр ерөнхий гүйцэтгэгч нэмж, тусгай чадварыг Skills-ийн шаталсан ил болголтоор хүргэ; Tool-ийн тодорхойлолтуудыг тогтмол дараалалтай, өөрчлөгдөхгүй угтварт бэхэл. ② Дэд Agent-ууд үндсэн Agent-тай ижил угтвар ашиглана.

## Бүлэг 3: Хэрэглэгчийн Memory ба мэдлэгийн сан

**1. (★★) Нэг хэрэглэгч өөр өөр сессэд хоорондоо зөрчилтэй мэдээлэл өгвөл (жишээлбэл, гэрийн хоёр өөр хаяг хэлбэл) хэрэглэгчийн Memory систем энэ зөрчлийг хэрхэн шийдэх ёстой вэ?**

> Mem0-тэй төстэй «извлэх–харьцуулах–шийдэх» Pipeline ашигла: эхлээд вектор хайлтаар өмнөх төстэй Memory-г олж, дараа нь LLM-ээр ADD/UPDATE/DELETE/NOOP шийдвэр гаргуул. Жишээлбэл, «Шанхай руу нүүсэн» гэвэл «Бээжинд амьдардаг» мэдээллийг UPDATE хийж солино. Хувилбаржуулахдаа хаягийн мэдээллийн зөвхөн хамгийн шинэ хувилбарыг цагийн тэмдэгтэй хадгал; харин ажлын туршлагын мэдээллийн түүхийг бүрэн үлдээ. Хайх үед Context угтвар (хүн, цаг, зорилго — гурван удаа өөрчилсөн шилжүүлгийн жишээний адил) ашиглавал аль бичлэг эцэстээ хүчинтэй болохыг тогтооход тустай.

**2. (★★) Contextual Retrieval нь баримтын эх Context-ийг хэсэг бүрд нэмж өгдөг. Гэвч эх баримт бүтэц муутай эсвэл зөрчилтэй мэдээлэлтэй бол энэ арга алдааг улам тарааж, томруулж болно. Хайлтын үе шатанд «мэдээллийн чанар»-ын дохиог хэрхэн оруулах вэ?**

> «Мэдлэгийн сангийн шинэлэг байдал ба удирдлага»-ын зарчмыг хэрэглэ: хэсэг бүрд хувилбарын дугаар, хүчинтэй болох/дуусах хугацаа, эх сурвалж зэрэг мета өгөгдөл хавсарга; хугацаа дууссан мэдээллийг хайх үед шүүж, эсвэл угтвар дээр «энэ бичлэгийг тэдэн өдөр хүчингүй болгосон» гэж тодорхой тэмдэглэ; дахин эрэмбэлэхдээ зөвхөн утгын төстэй байдлаар бус, эх сурвалжийн найдвартай байдал, цаг хугацааны шинэлэг байдлыг оноонд тусга; индексжүүлэх үеэр угтвар үүсгэдэг LLM-ээр Memory-ийн хувилбар хоорондын зөрчил илрүүлэхтэй адил хэсгүүд хоорондын зөрчлийг шалгуулж, тэмдэглүүл.

**3. (★★) Олон модаль мэдээлэл извлэхдээ диаграм, графикийг хайхаас өмнө текстэн тайлбарт хөрвүүлдэг. Энэ «орчуулга» нь дүрс дэх орон зайн холбоог алдагдуулж болно. Цэвэр текст бүрэн дамжуулж чадахгүй графикийн мэдээллийн жишээ гаргаж, үүнийг хадгалах шийдэл зохио.**

> Жишээ нь системийн архитектурын зураг дахь логик холбоо; шугаман график дээр хоёр муруйн огтлолцох цэгийн байрлал; PDF хүснэгтийн нүд, мөр ба баганын гарчгийн харгалзаа. Нэгдүгээр хувилбар — төрөлхийн олон модаль боловсруулалт; хоёрдугаар хувилбар — олон модаль зураг шинжлэх Tool ашиглах.

**4. (★★★) Рич Саттоны «Гашуун сургамж»-д ерөнхий аргууд (хайлт ба суралцах) эцэстээ гараар зохиосон шинжээс илүү үр дүнтэй гэж үздэг. Энэ бүлгийн мэдлэгийн систем бүхэлдээ (хэсэгчлэх стратеги, индексийн бүтэц, хайлтын Pipeline) өөрөө «гараар зохион бүтээсэн дизайн» мөн үү? Model хангалттай хүчтэй болбол «бүгдийг Input-д өгөх» замаар эдгээрийг орлуулж болох уу?**

> Үнэхээр гараар зохион бүтээсэн дизайн мөн. Context уртсахын хэрээр хэсэгчлэх, нэгтгэх тохиргоо зэрэг зарим алхмын ач холбогдол буурч магадгүй. Гэхдээ хар муур/цагаан муурын жишээ «бүгдийг оруулах» хангалтгүйг харуулдаг: Attention нь зөөлөн хайлт бөгөөд олон баримтын мэдээллийг нэгтгэх, статистик гаргахад индексжүүлэх үеийн урьдчилсан нэрж нэгтгэл хэрэгтэй хэвээр. Мэдлэгийн хугацаа дуусах, шинэчлэгдэх, зөвшөөрөл/түрээслэгчийн тусгаарлалт, аудит, зардал зэрэг инженерчлэлийн хязгаарлалт Model-ийн чадвараас үл хамаарна. Индексжүүлэх үед хайлтыг LLM-ээр нэгтгэх нь өөрөө ерөнхий «хайлт + суралцах» арга учраас «Гашуун сургамж»-тай зөрчилдөхгүй.

**5. (★★★) Model-ийн чадвар сайжрахын хэрээр тодорхой салбарын мэдлэгийн сан чухал хэвээр байх уу? Ирээдүйн хүчирхэг суурь Model салбарын мэдлэгийн сан дахь бүх мэдээллийг өөртөө агуулж, түүний хэрэгцээг арилгаж чадах уу?**

> Чухал хэвээр: сургалтын өгөгдлийн хугацааны зааг бий, харин мэдлэгийн санг хэзээд шинэчилж болно; компанийн дотоод үйл явц, нийтэд нээлттэй бус эрх зүйн баримт зэрэг нь нийтийн өгөгдөлд огт байхгүй; олон хэрэглэгч мэдээлэл хуваалцахад зөвшөөрлөөр шүүх, түрээслэгчийг тусгаарлах шаардлагатай бөгөөд параметрт шингэсэн мэдлэгийг хандаж буй хэрэглэгч бүрт тохируулах боломжгүй; гадаад хадгалалтад аудит, хувилбарын хяналт хийх, хуучирсан мэдээллийг хасах боломжтой, харин параметрийн Memory-д үүнийг хэрэгжүүлэх хэцүү. Параметрийн замаар (сургалтын дараах шат / User as Engram) явсан ч «баримтыг санах амархан, харин олон алхамт дүгнэлтэд ашиглах хэцүү» гэсэн асуудал үлдэнэ.

**6. (★) RAPTOR доороос дээш шаталсан хураангуйгаар мод хэлбэрийн индекс бүтээдэг бол GraphRAG нэгжүүдийн хоорондын холбоогоор граф индекс бүтээдэг. Энэ хоёр бүтэцтэй индекс тус бүр ямар асуултад сайн хариулдаг вэ?**

> RAPTOR: ерөнхий ойлголтоос нарийвчилсан мэдээлэл рүү үе шат дамнан шилжих асуулт — жишээлбэл, эхлээд «SIMD зааврын багц»-ын хураангуйг олоод SSE-ийн дэлгэрэнгүй рүү орох; тойм ба нарийвчлалын аль алиныг хамарна. GraphRAG: олон дамжлагат харилцааны дүгнэлт («миний эмчийн ажилладаг эмнэлгийн хаяг» гэсэн холбоосын гинжийг дагах) болон ижил нэртэй нэгжийг ялгах (хоёр өөр «доктор Жан» хоёр өөр зангилаа) — «A ба B ямар холбоотой вэ?» төрлийн асуулт. Бүлгэмийн хураангуй нь сэдвээр нь бүлэглэхэд тусална.

**7. (★★) Файлын системийн хэв загвар мэдлэгийг файлын систем шиг шаталсан бүтэцтэй зохион байгуулдаг. Уламжлалт вектор өгөгдлийн сангийн RAG-тай харьцуулахад энэ арга ямар нөхцөлд давуу вэ?**

> Энгийн текстийг хэрэглэгч шууд уншиж, засаж, алдааг нь залруулж, Git-ээр хувилбар хянаж буцааж болдог — хүн, машин хамтран мэдлэг хадгалж, хянахад тохиромжтой. write_file чадвартай бол Agent туршлагаа бие даан тэмдэглэж, өөрөө хөгждөг Memory-ийн давталт (гадаад хэлбэрийн суралцах үйл явц) үүсгэнэ. L0/L1/L2 шаталсан ил болголтын ачаар ихэнх хайлтыг L1 түвшинд шийдэж, Token хэмнэнэ. Гэхдээ Wikipedia шиг харилцан холбоос, индекс хуудсууд бүтээх шаардлагатай; үгүй бол тусгаарлагдсан файл ихсэх тусам олоход хэцүү болно.

**8. (★★★) Бүтэцтэй өгөгдлөөс (жишээ нь шүүхийн шийдвэрийн өгөгдлийн сан) «шийдвэрлэх хүчин зүйл» болон «хүчин зүйлийн ач холбогдлын шатлал»-ыг автоматаар илрүүлэх нь Agent өгөгдлөөс дүрэм индукцлэх үйл явц юм. Ийм өгөгдөлд суурилсан мэдлэг извлэлт хүний мэргэжилтнүүдийн гараар боловсруулсан дүрмийн чанарт хүрч чадах уу?**

> Давуу тал: CAIL2018 туршилтын адил «доороос дээш» хүчин зүйл илрүүлэх нь хүний урьдач төсөөлөл бус өгөгдөлд нийцдэг; мэргэжилтнүүд үгээр тодорхой бичиж чадахгүй хэдэн арван мянган шийдвэрт тархсан далд сонголт, харилцан буултын туршлагыг барьж чадна; тоон хэмжилт хийх боломжтой. Хязгаарлалт: LLM-ээр извлэх үеийн алдаа мэдлэгийг бохирдуулна; өгөгдлийн өөрийн хазайлт өвлөгдөнө; кластерын төлөөлөл зөвхөн харилцан хамаарлыг илэрхийлж, шалтгааныг тайлбарлаж чадахгүй. Зөвшилцсөн шийдэл: өгөгдөлд суурилсан загварчлал дээр схем болон үр дүнгийн мэргэжилтний хяналт нэмэх; асуултыг Model чиглүүлж, тайлбарыг статистик бататгана.

**9. (★★★) Markdown хэрэглэгчийн Memory сангийн нэмэгдэл шинэчлэл болон үе үеийн дахин зохион байгуулалтын ажлын урсгалыг хоёуланг нь зохио. Хянагч (Reviewer) ба санал гаргагч (Proposer) ижил Model ашиглаж, Хянагч зөвхөн санал гаргагчийн сонгосон ярианы хэсгийг хардаг бол ямар алдаа батлагдаж нэгтгэгдэх боломжтой вэ? Model-ийн хараат бус байдал, нотлох баримтын хамрах хүрээ, Tool-ийн зөвшөөрлөөр сайжруулалтыг тайлбарла.**

> Нэмэгдэл шинэчлэл: Memory санг кодын репозитор мэт үзэж, өөрчлөлт бүрийг PR-ээр дамжуул. Санал гаргагч эхлээд холбогдох одоогийн мэдлэгийг хайж, дараа нь холбоос, индекс, цагийн мета өгөгдөл, нотлох баримтын холбоосыг хамтад нь хадгалах хамгийн бага боловч бүрэн diff санал болгоно. Хянагч өөрчлөлтөөс өмнөх мэдлэг, diff, түүхий нотлох баримтад тулгуурлан бие даан шалгаж, татгалзвал тодорхой баримт, мөрийн дугаартай хэрэгжүүлж болох тайлбар буцаана. Давталт дээд тоо эсвэл зардлын төсөвтэй байх бөгөөд хэтэрвэл автоматаар зөвшөөрөх бус хүнд шилжүүлнэ. Нэгтгэсний дараа CI эхлээд формат, холбоос, мета өгөгдөл, зөвшөөрлийн шошгыг шалгаж, дараа нь нэгтгэсэн хувилбараас нөлөөлөгдсөн хэсэг ба вектор индексийг нэмэгдлээр дахин бүтээнэ. Үе үеийн нэгтгэл: хуваарь эсвэл шинэ бичлэгийн тоогоор бүхэл санг шалгаж, давхардлыг арилгаж, нэгтгэж, хэт том файлыг салгаж, индекс хуудсыг дахин бүтээ. Хамгийн чухал нь хуучин хураангуй үгүйсгэл, цаг хугацааны нөхцөл, тодотголыг орхисон эсэхийг түүхий харилцан яриа руу буцаж догол мөр бүрээр шалгах явдал. Зөрчлийг «хамгийн шинэ мэдээллийг үлдээ» гэдгээр шийдэхгүй; мэдэгдэл бүрийг эх сурвалжтай нь холбож, ямар нөхцөлд хүчинтэйг тэмдэглэ. Нотлох баримт хангалтгүй бол зөрчлийг хэвээр үлдээж, шийдэгдээгүй гэж тэмдэглэ. Дахин зохион байгуулалтыг ч PR-ээр оруулах бөгөөд шаардлагатай бол хавтсаар нь салга. Бүгд шалгалтад тэнцсэний дараа индексийг дахин бүтээж, түгээмэл хайлтын жишээг дахин ажиллуулан өмнө нь олддог байсан мэдлэг далд болоогүйг баталгаажуул.
>
> Ижил Model ба урьдчилан сонгосон хэсгүүд гурван төрлийн алдааг анзаарахгүй өнгөрөөнө. **Model-ийн хараат бус байдал**: нэг бүлгийн Model-ууд сургалтын урьдач хандлага, сул талыг хуваалцдаг тул Хянагч баримт руу буцалгүй Санал гаргагчийн дүгнэлтийг давтаж, ижил буруу уншилт илрэхгүй; ижил төстэй чадвартай боловч өөр бүлгийн Model-оор хөндлөн хяналт хий. **Нотлох баримтын хамрах хүрээ**: зөвхөн Санал гаргагчийн сонгосон хэсгийг харвал Context-оос тасалсан эшлэл, орхисон үгүйсгэл ба урьдчилсан нөхцөл, бусад файлтай зөрчилдөх байдал харагдахгүй; Хянагч зөвшөөрөгдсөн хэрэглэгч эсвэл байгууллагын хүрээнд бүхэл мэдлэгийн сан, түүхий нотлох баримтын хадгалалтад өөрөө хайлт хийж чаддаг байх ёстой. **Tool-ийн зөвшөөрөл**: Санал гаргагч үндсэн салбарт шууд бичиж, эсвэл ашиглагдаж буй индексийг өөрчилж чадвал хяналт утгагүй. Үүргийг хатуу салга: Санал гаргагч зөвхөн ажлын салбарт бичнэ; Хянагч зөвхөн баримт уншиж дүгнэлт өгнө; зөвхөн нэгтгэх Pipeline үндсэн салбар болон ашиглагдаж буй индексийг шинэчилнэ; баталгаажуулагч болон нийтлэх хаалтууд нь өөрчлөх боломжтой хүрээнээс гадуур үлдэнэ.

## Бүлэг 4: Tools

**1. (★★) MCP стандарт Tool-ийн тодорхойлолтыг Agent-ийн Framework-ээс салгадаг. Гэвч стандартчилал нь урсгал Output, хоёр чиглэлийн харилцаа, төлөв хадгалдаг сесс зэрэг төвөгтэй Tool-ийн харилцан үйлчлэлийг стандарт протоколд илэрхийлэхэд хүндрэл учруулж болно. Ирээдүйд MCP-ийн аль чадварыг хамгийн түрүүнд өргөжүүлэх хэрэгтэй гэж үзэж байна вэ?**

> Хамгийн хэрэгтэй өргөтгөл бол сесс дамнасан, үйл явдалд суурилсан чадвар. MCP олон ээлжийн харилцаа, өөрчлөлтийн захиалга, удаан үргэлжлэх даалгаврыг аль хэдийн дэмждэг ч түүний гол зорилго Agent-ийг тасралтгүй онлайн байлгах бус чадвар дуудах аргыг стандартчилахад оршдог. Шинэ цахим шуудан эсвэл гадаад системийн буцаан дуудлага ирэхэд Agent-ийг сэрээх, олон үйл явдлыг дараалалд оруулах, үргэлжлүүлэх, дахин оролдох нь Agent-ийн Framework-ийн үүрэг хэвээр. Эдгээр зохион байгуулалтын илүү нэгдмэл дүрэм нь протоколын энгийн байдлыг алдагдуулахгүйгээр MCP-ийн хүрээг өргөжүүлнэ.

**2. (★★) MCP-ийн экосистемд өөр өөр MCP Server-үүд маш төстэй үйлдэлтэй Tools санал болгож болно. Ижил төстэй олон Tool-тэй таарахад Agent хэрхэн сонгох ёстой вэ? Өөр эх сурвалжийн ижил нэртэй Tools бага зэрэг өөрөөр ажилладаг бол (нэг нь хураангуй, нөгөө нь бүтэн текст буцаах гэх мэт) Agent энэ ялгааг таньж, ашиглаж чадах уу?**

> Сонгох шалгуур: холбохоос өмнө тайлбарыг хянаж, хувилбарыг тогтоож, хамгийн бага эрхтэй нэвтрэх мэдээллийг тохируул; ижил нэрээр халхавчлан мэдрэмтгий дуудлагыг хортой талд чиглүүлэхээс болгоомжил; ажиллах үед шаталсан ангилал, динамик илрүүлэлтээр боломжит Tool-уудыг цөөл. Model зан үйлийн ялгааг таньж чадах эсэх нь Tool-ийн тайлбарын чанараас хамаарна.

**3. (★★) Энэ бүлэгт «гүйцэтгэх–баталгаажуулах–эргэх холбоо өгөх» давталт (жишээ нь код бичсэний дараа linter автоматаар ажиллуулах) санал болгосон. Үйлдлийн дараах шууд автомат баталгаажуулалтыг өөр ямар Tool-ийн хэрэглээнд ашиглаж болох вэ? Баталгаажуулалт өөрөө үндсэн үйлдлээс илүү зардалтай эсвэл эрсдэлтэй тул хэрэгжүүлэх боломжгүй тохиолдол бий юу?**

> Ерөнхийшүүлж болох жишээ: тохиргоо өөрчилсний дараа sandbox-д бодитоор ажиллуулж, өөрчлөлт хүчин төгөлдөр болсныг шалгах; баримт бичиг эсвэл танилцуулга үүсгэсний дараа зураг болгон дүрсэлж, Model-ийн олон модаль чадвараар байрлалыг шалгах. Боломжгүй жишээ: цахим шуудан илгээх, утсаар залгах, мөнгө шилжүүлэх зэрэг буцаах боломжгүй, давтахад ижил үр дүн гарахгүй үйлдэл. Ажиглах зүйлгүй эсвэл баталгаажуулалт өөрөө дахин бодит үйл явдал үүсгэнэ. Иймд өмнө нь баталгаажуулах санал гаргагч–хянагчийн аргыг хэрэглэ.

**4. (★★) Энэ бүлэгт «Tool-ийн хэт олшрол» буюу мянга мянган Tool-оос сонгох үед Agent-ийн сонголтын нарийвчлал буурах асуудлыг хөндсөн. Идэвхтэй Tool илрүүлэлтээс өөр ямар арга бий вэ? Хүний мэргэжилтнүүд асар олон хэрэгслээс хэрхэн сонгодгийг харгалзан үз.**

> ① Шаталсан бүлэглэлт: эхлээд «Server/апп»-ийг, дараа нь тусгай Tool-ийг ол. ② Skills шиг «шаардлагатай үед лавлах»: лавлах ном ашиглаж буй мэт каталогийг Context-д байнга үлдээж, дэлгэрэнгүйг хэрэгтэй үед ачаална. ③ Түгээмэл цөөн үндсэн Tools-ийг Context-д байнга «гарын дор» байлгаж, үлдсэнд нь каталогийн индексээр хүрнэ.

## Бүлэг 5: Код бичдэг Agent ба код үүсгэх

**1. (★★) Код үүсгэхийг Agent-ийн «мета чадвар» гэж нэрлэдэг. Гэвч код ажиллуулах нь аюулгүй байдлын эрсдэл дагуулна: Agent-ийн үүсгэсэн код эмзэг байдалтай, хязгааргүй давталтад ордог, нөөц шавхдаг байж болно. Sandbox зарим эрсдэлийг бууруулдаг ч сүлжээ, файлын системд нэвтрэхийг хориглох зэрэг нь кодын боломжийг хязгаарлана. Аюулгүй байдал ба чадварын оновчтой тэнцвэрийг хэрхэн олох вэ?**

> Нөхцөлөөс хамааран sandbox тусгаарлалтыг шатал (контейнер/microVM); анхдагчаар сүлжээг хааж, шаардлагатай үед зөвшөөрсөн жагсаалттай proxy-оор нэвтрүүл; эх кодыг зөвхөн унших горимоор холбож, API түлхүүрийг sandbox-д оруулахгүй; нөөцийн хязгаар тогтоо; ажиллах хугацааны хязгаар зэрэг sandbox-ийн амьдралын мөчлөгийг удирд.

**2. (★★★) Agent өөр Agent бүтээдэг Agent-ийг эхлүүлэн хөгжүүлэх нь «оюун ухаан өөрийгөө дахин бүтээх» боломж олгодог. Гэвч ийм давталт бүр шинэ хазайлт эсвэл алдаа үүсгэж болно. Эдгээр алдаа үе үеэрээ хуримтлагдах уу? Agent-ийг дахин бүтээх үед чанар доройтохоос хэрхэн сэргийлэх вэ?**

> Үе бүр өмнөх үеийн бүтээсэн материал дээр дахин тулгуурлан өөрийгөө үржүүлбэл зарим согог хуримтлагдаж болно. Гол нь хангалттай төвөгтэй, баталгаажуулж болох даалгавартай байх — жишээлбэл, хангалттай хэцүү программчлалын даалгавар.

**3. (★★) Код үүсгэдэг Agent лог файл задлан боловсруулахдаа формат өөрчлөгдөхөд автоматаар дасан зохицож чадна. Гэвч формат өөрчлөгдсөн нь зориудын шинэчлэл бус алдаа бол Agent-ийн дасан зохицол асуудлыг нууж мэднэ. «Дасан зохицох шаардлагатай өөрчлөлт» ба «мэдэгдэх ёстой хэвийн бус байдал»-ыг Agent хэрхэн ялгах вэ?**

> Дасан зохицохоосоо өмнө оношил: шинэ форматыг архитектурын баримт бичиг болон PRD-тай тулгаж, хүлээгдэж байсан эсэхийг тогтоо (Туршилт 5-11-ийн санаа); хувилбарын хяналтын бүртгэлээс өөрчлөлт хууль ёсны commit-тэй тохирч байна уу, эсвэл эх сурвалжгүй зөрүү юу гэдгийг шалга; τ-bench-ийн log_mismatch-ийн адил дасан зохицохоор шийдсэн ч чимээгүй хүлээн авах бус анхааруулга бүртгэж, issue автоматаар үүсгэ; эргэлзээтэй үед хүний баталгаажуулалтад шилжүүл. Зарчим: дасан зохицох ба мэдэгдэхийг зэрэг хий — дасан зохицол хэвийн бус байдлын дохиог нууж болохгүй.

**4. (★★) Энэ бүлэгт PPT үүсгэх, видео засварлах, лог дүрслэхдээ санал гаргагч–хянагчийн механизмыг олон удаа ашигласан. Хянагчийн гоо зүйн сонголт зорилтот хэрэглэгчийнхээс өөр бол (жишээ нь Хянагч мэдээллийн нягтралыг зохистой гэж үзэхэд хэрэглэгч хэт шахцалдсан гэж үзвэл) эргэх холбооны давталт буруу орон нутгийн оновчтой цэгт тогтож болно. Хэрэглэгчийн сонголтын эргэх холбоог Хянагчийн давталтад хэрхэн оруулах вэ?**

> Хэрэглэгчийн саналыг Agent-ийн ажлын явцын бүртгэлд хамгийн өндөр ач холбогдолтой бүтэцтэй үйл явдал болгон оруул; хэрэглэгчийн сонголтыг MEMORY.md-д бичиж гадна хадгалан нэгтгэснээр дараагийн даалгаварт ч хэрэгжүүл; хэрэглэгч өөрөө шалгаж болохын тулд баримтыг Markdown бус HTML форматаар хүргэ.

**5. (★★) Энэ бүлэгт код бичдэг Agent ажиллуулж, алдаа засах явцдаа олсон туршлагаа кодын санд буцаан нэгтгэх хэд хэдэн аргыг үзүүлсэн: мэдлэгийн сангийн файл бичих, архитектурын баримт бичгийг шинэчлэх, төслийн зааврын файл хөтлөх, ажиллагааны дарааллыг код болгох. Үүнийг системийн Prompt дахь дүрэм болгон цааш нэрж нэгтгэвэл дүрмийн багц улам томорно. Хуримтлагдсан дүрмүүдийн давхардсан, хуучирсан бичлэгийг олж арилгах «хог цэвэрлэгээ»-г хэрхэн хийх вэ? Нэг удаа код амжилттай өөрчилсөн нь яагаад есдүгээр бүлгийн утгаар тасралтгүй хөгжил биш вэ?**

> Цэвэрлэх арга: linter, CI эсвэл Tool-ийн баталгаажуулалтаар кодолж болох дүрмийг Prompt-оос гарга; дүрэм хэдэн удаа ашиглагдсан, зөрчил үүссэн эсэхийг хянаж, кодын сантай үе үе тулгаж шалга; Markdown ба Git-ээр эх сурвалж, хувилбар, буцаах боломжийг хадгал. Амжилттай засвар нь зөвхөн одоогийн тохиолдлыг шийдсэнийг харуулна. Тасралтгүй хөгжилд нэмээд өөрчлөлт нь мөрдөж болох ажиллагааны баримтаас үүссэн, дараагийн даалгаврыг сайжруулсан, хуучин даалгаврын регрессийн тест болон аюулгүй байдлын баталгаажуулалтыг давсан байх шаардлагатай.

**6. (★) «Алсын зайн ажилд ээлтэй багууд ихэвчлэн AI Agent-д ч ээлтэй байдаг». Мэдлэгийг баримтжуулсан байдлаар танай баг, байгууллага «AI-д бэлэн» түвшинд хэр ойр вэ? Хамгийн том саад юу вэ?**

> Нээлттэй асуулт. Энэ бүлгийн орлуулан хэмжих үзүүлэлтээр өөрийгөө шалга: шинээр орсон алсын зайн ажилтан зөвхөн репозитор, баримт бичиг ашиглаад бие даан ажиллаж чадах уу? Шалгах зүйлс: шийдвэрүүд баримтжсан эсэх; Context-ийг issues/PR-д бичдэг эсэх; бүтээх, тестлэх команд CLAUDE.md/AGENTS.md шиг зааврын файлтай эсэх; зөвхөн ахмад ажилтнуудын толгойд байдаг мэдлэгийг хөгжүүлэгчийн гарын авлага болгосон эсэх. Хамгийн нийтлэг том саад нь «хажуугийн хамт ажилладаг хүнээс асуух»-ад тулгуурласан аман мэдээлэл, самбарын соёл. Agent аман тохиролцоог уншиж чадахгүй, зөвхөн баримтыг уншина.

**7. (★★★) Саймон Уиллисон Agent-ийн «Үхлийн гурвал» хэмээн хувийн өгөгдөлд нэвтрэх, итгэмжлэгдээгүй агуулгатай харьцах, гадагш харилцах чадвар гэсэн гурван хүчин зүйлийг нэрлэсэн. Энэ бүлэгт дөрөв дэх хүчин зүйл болох байнгын Memory-г нэмсэн. Эдгээр дөрвийг зэрэг агуулсан бодит ашиглалтын орчинд аюулгүй байдлын ямар стратеги зохион бүтээх вэ?**

> Хамгаалалтыг дөрвөн төрлийн заагаар давхарла. Өгөгдлийн зааг: нэвтрэх нууц мэдээлэл холбохгүй, эх код зөвхөн унших, хамгийн бага харагдах хүрээ. Input-ийн итгэлийн зааг: эх сурвалжийн шошго тавьж, гадаад агуулгыг «зөвхөн лавлах өгөгдөл, зааврын хүчин чадалгүй» түвшинд бууруул (үнэнч байдлын дүрэм). Output-ийн нөлөөллийн зааг: анхдагчаар сүлжээг хааж, зөвшөөрсөн гадагш урсгал нээх; командын хар жагсаалт бус утгаар нь задлан шинжлэх; бие даасан Sidecar хяналт ба хүний оролцоо — чухал үйлдлийг Context-оос гаднах механизм шалгана. Сесс дамнасан зааг: MEMORY.md-д бичих үйлдэл гадаад агуулгатай ижил итгэлийн шалгалт давна. Зорилго нь Prompt Injection амжилттай болсон ч халдлагын үйлдэл гүйцэтгэгдэх боломжгүй байлгах.

**8. (★★) Artifact хэв загвараар Agent SQL эсвэл дүрслэлийн код үүсгэж, урд талын системд шууд ажиллуулснаар их хэмжээний өгөгдлийг LLM-ээр боловсруулах шаардлагагүй болно. «Agent код үүсгэж, систем код ажиллуулах» хөдөлмөрийн хуваарилалт Agent шууд хариулт өгдөг уламжлалт загвараас ямар давуу, сул талтай вэ? Мөн үүсгэсэн SQL устгах үйлдэл хийж, HTML нь эмзэг байдал агуулж болзошгүй. Системийн аюулгүй байдлыг хэрхэн хангах вэ?**

> Давуу ба сул тал: Давуу — өгөгдөл LLM «дундын дамжуулагч»-ийг алгасан өгөгдлийн сангаас шууд урд талын систем рүү урсана. Хурдан, Token хэмнэнэ, их өгөгдлийг хуулж дамжуулах үеийн хийсвэрлэн зохиох алдаагүй тул их хэмжээний өгөгдөл үзүүлэхэд тохиромжтой. Кодыг аудит хийж, дахин ашиглаж, Pipeline болгон холбож болно (SQL-ийн үр дүн дүрслэлийн код руу шууд орно). Сул — LLM хайлтын үр дүнг огт харахгүй учраас өгөгдлийн агуулгад тулгуурлан цааш хураангуйлж, шийдвэр гаргаж чадахгүй; Model өгөгдлийг өөрөө боловсруулж дүгнэх ёстой ажилд тохиромжгүй.
>
> Аюулгүй байдал: SQL — хамгийн бага эрхтэй, зөвхөн унших бүртгэлээр асуулга ажиллуулж, нөөц шавхахаас сэргийлэхийн тулд CPU, Memory зэрэгт хязгаар тавь. HTML/UI — A2UI шиг декларатив протоколыг илүүд үз; Agent зөвхөн интерфейс тайлбарлах JSON гаргаж, Client итгэмжлэгдсэн бүрэлдэхүүний каталогоор дүрсэлдэг тул дурын код ажиллуулахгүй. Дурын HTML зайлшгүй шаардлагатай бол тарилгаас хамгаалахын тулд тусгаарлагдсан орчинд харуул.

**9. (★★) Бизнесийн дүрмийг өгөгдлийн сангийн бодит үнэнтэй тулгасан баталгаажуулалт болгон кодлохын зэрэгцээ Tool-ийн параметрийг Model дуудлага хийхээс өмнө бодлогын нөхцөлийг шалгахаар зохиох нь кодын бүтцээр Agent-ийн зан үйлийг хязгаарлаж буй хэрэг юм. «Кодыг дүрэм болгох» хэв загвар байгалийн хэлээр илэрхийлсэн дүрэмтэй харьцуулахад ямар давуу, сул талтай вэ?**

> Давуу тал: хоёрдмол утгагүй, тодорхой үр дүнтэй, төвөгтэй нөхцөлийн хослолд сайн; бодлогын баримт Model-ийн өөрийн мэдэгдлээс бус өгөгдлийн сангийн бодит төлөв, Server-ийн цагаас гардаг тул хийсвэрлэн зохиох болон Prompt Injection түүнийг тойрч чадахгүй — буцаах боломжгүй үйлдлийн сүүлийн хамгаалалт болно. expected_* параметрүүд мөн заавал дагах шалгах жагсаалт болж, дүгнэлт хийхэд чиглүүлнэ. Хязгаарлалт: код хэрэглэгчид бодлогыг тайлбарлахгүй, тойрч хэрэгжүүлэх хувилбар өөрөө олохгүй, засвар үйлчилгээний зардалтай. Дүгнэлт: байгалийн хэлний дүрмийг орлох биш, харин нөхнө.

## Харилцан үйлчлэл: Ажиглалт ба үйлдлийн орон зайг өргөжүүлэх нь

**1. (★★) Асинхрон Agent архитектурт үйл явдлын дарааллын тэргүүлэх эрхийн стратегийг дизайны үед тогтоох ёстой. Харин тэргүүлэх эрхийг тодорхойлоход утгын ойлголт хэрэгтэй бол (жишээ нь шинэ мессеж одоогийн даалгавраас яаралтай эсэхийг тогтоох) үүнийг дүрмийн хөдөлгүүр үү, нэмэлт LLM дуудлага уу шийдэх вэ? Тус бүрийн зардал юу вэ?**

> Давхарласан хосолмол арга: төрөл нь тодорхой үйл явдлыг хатуу кодолсон дүрмээр шийд — сааталгүй, үр дүн нь тогтвортой ч «яг одоо зогс» ба «өнөөдөр цаг агаар ямар байна?» гэсэн утгын ялгааг ойлгож чадахгүй. Утгын хувьд хоёрдмол үйл явдлыг хөнгөн ангилагч LLM буюу үйл явдлын чиглүүлэгчид дамжуул; үүний үнэ нь хэдэн зуун миллисекундын саатал, нэмэлт төлбөр, буруу дүгнэх магадлал. Sidecar-ийн адил Prompt Injection-ээс хамгаалахын тулд зөвхөн бүтэцтэй талбар унших ёстой.

**2. (★★) Дараалалд суурилсан үйл явдал боловсруулах үед Model сүүлчийн үйл явдалд л төвлөрөх хандлагатай. Энэ бүлэгт Agent-ийн төлөвийн мөрийн тэмдэг, хураангуйгаар үүнийг бууруулсан. Гэвч дараалалд 20 үйл явдал (10 Tool-ийн үр дүн + 5 хэрэглэгчийн мессеж + 5 системийн анхааруулга) хүлээгдэж байвал Model чухал мэдээлэл алдахгүй байхын тулд танилцуулах дараалал, форматыг хэрхэн зохион байгуулах вэ?**

> Эхлээд дүрэм ба хөнгөн LLM-ээр ангилж, давхардлыг арилга. Яаралтай үйл явдлыг (анхааруулга, хэрэглэгч таслан оролцох) цуцлах механизм шиг тусад нь боловсруулж, багцад бүү холь. Хэт урт 10 Tool-ийн үр дүнг товчилж файлд хадгалаад зөвхөн эхлэл, төгсгөл, замыг нь үлдээ. Context-ийн төгсгөл дэх системийн төлөвийн мөрөнд хураангуй жагсаалт (төрөл бүрийн үйл явдлын тоо + зүйл бүрд хариу өгөх шаардлага) нэм.

**3. (★★★) Agent хэрэглэгчийн өмнөөс гадаад ертөнцтэй харилцахдаа таних тэмдгийн хоёр сонголттой тулгарна: тусдаа виртуал таних тэмдэг (зориулалтын цахим шуудан, утасны дугаар) ашиглан гуравдагч тал шиг ажиллах уу, эсвэл хэрэглэгчийн хувийн бүртгэлийг шууд түүний нэрээр удирдах уу? Эхнийх нь бие даан ажиллах боломжтой ч гуравдагч тал хүн биш таних тэмдэгт итгэхгүй байж болно; хоёр дахь нь илүү бүрэн Context, зөвшөөрөлтэй ч эрх олголт, итгэл, аюулгүй байдлын заагийн асуудалтай. Аль нөхцөлд аль горимыг сонгох вэ?**

> Анхдагчаар виртуал таних тэмдэг ашигла: цаана нь бие даан ажиллаж, аудит хийх боломжтой; алдаа гарсан эсвэл эзлэгдсэн ч хэрэглэгчийн бүх дижитал таних тэмдэг ил гарахгүй — нарийн бичгийн дарга өөрийн ажлын цахим шуудан ашигладагтай адил. CAPTCHA/IP нэр хүндийн асуудлыг (орон сууцны proxy) зохицуулах шаардлагатай. Хэрэглэгчийн өөрийн таних тэмдэг зайлшгүй шаардлагатай үед (бүртгэлээр таних баталгаажуулалт, Pine хэрэглэгчийн үйлчилгээ рүү залгах үеийн гурван талт дуудлагын баталгаажуулалт) хүний оролцоотой нэвтрэлтийг ашигла: VNC/RDP-ээр хэрэглэгч өөрөө хараад нэвтэрнэ. Шалгуур: нөгөө тал данс эзэмшигчийг биечлэн шаардаж байгаа эсэх, үйлдлийн эрсдэл, нэвтрэх мэдээллийн хамрах хүрээ.

**4. (★★) Дуут Agent-ийн төгсгөлөөс төгсгөл хүртэлх Model нь ASR–LLM–TTS-г нэг Model болгон нэгтгэснээр саатлыг бууруулдаг ч модульчлагдсан бүтцийг алддаг. Нэг үе шатанд (жишээ нь дуу танихад) алдаа гарвал шаталсан Pipeline-тай харьцуулахад оношлох, засах хэцүү. Ийм дуут Agent-д ажиглагдах байдлын системийг хэрхэн зохион бүтээх вэ?**

> Model-оор Output-той зэрэгцүүлэн Moshi-ийн «дотоод яриа» текстэн урсгал, дууны үйл явдлын тэмдэг (`<emotion>`, `<noise>`) зэрэг уншиж болох завсрын дүрслэл гаргуул. «Өөрөө шаталж ажиллах» аргаар алдааны үеийг ол: ижил Model эхлээд бичвэр болгож, дараа нь дүгнэлт хийнэ; төгсгөлөөс төгсгөл хүртэлх үр дүнтэй харьцуулахад алдаа сонсож ойлгох уу, бодох уу гэдэг нь харагдана. Офлайн үед ярианы нэмэлт шинжийг ойлгох, ээлж солихыг дүгнэх зэрэг хэмжээсээр тусгай регрессийн шалгалт ажиллуул.

**5. (★) Step-Audio R1 нь MPS хоёр тархины архитектураар «ярьж байхдаа бодох» чадварт хүрдэг. Гэвч хүмүүс ингэхдээ бүрэн бодож дуусаагүй зүйл хэлж, өөрийгөө засаж, завсрын үг хэрэглэдэг. Agent-ийн «ярьж байхдаа бодох» чадвар хүний ийм шинжийг дуурайх ёстой юу?**

> Мэдээллийн үнэ цэнтэй «төгс бус» шинжийг дуурайж болно: түр завсарлах, завсрын үг хэрэглэх нь бодож байгааг илэрхийлж, саатлыг далдалдаг; тэдгээрийг хаана оруулахыг LLM шийдэж болно. Харин итгэл эвддэг өөрийгөө залруулахыг дуурайх ёсгүй: нэгдүгээр шийдлийн хурдан–удаан зөрчил («Би үүнийг авах хэрэгтэй юу, үгүй юу?!») итгэлийг нураана. MPS туршилт CoT-ийн эхлэл ихэвчлэн асуултыг дахин хэлдгийг харуулсан; суурь мэдээллээр түрүүлж эхлэх нь аюулгүй бөгөөд эхлээд буруу хэлээд дараа нь засах шаардлагагүй.

**6. (★★) SoM (Set-of-Mark) болон түүний бүтэцтэй хувилбарууд (DOM элементийн индекс) Computer Use-ийн харааны байрлал тогтоох асуудлыг дурын координат таамаглахаас хязгаарлагдмал ID сонгох болгон өөрчилдөг. Гэвч сегментлэх Model эсвэл DOM-оор UI элементүүдийг урьдчилан илрүүлж, тэмдэглэх шаардлагатай. Стандарт бус удирдлага эсвэл динамикаар өөрчлөгдөх элементтэй интерфейст тэмдэглэгээ бүрэн бус, буруу байж болно. Ийм үед координат таамаглах аргад буцаж шилжих үү?**

> Координат таамаглахыг нөөц хувилбар болгон үлдээх ёстой: энэ нь тэмдэглэгээнээс үл хамаарч, стандарт бус удирдлага, динамик элементэд ажиллах цорын ганц арга. Илүү практик шийдэл нь тэмдэглэж болох элементэд ID сонголт ашигладаг хосолмол үйлдлийн орон зай. Координат таамаглахдаа нягтрал тааруулж, пропорциональ масштабаар хувиргах ёстой; үгүй бол системтэй байрлалын зөрүү үүснэ.

**7. (★★) XLeRobot зэрэг мянган долларын робот платформ зайнаас удирдах сургалтын өгөгдлийг хямд цуглуулах боломж олгодог. Гэвч түүний чанар удирдаж буй хүний ур чадвараас ихээхэн хамаарна. Туршлагагүй операторын муу өгөгдөл VLA Model-ийн сургалтад хэрхэн нөлөөлөх вэ? Цуглуулах үе шатанд чанаргүй өгөгдлийг хэрхэн автоматаар шүүх вэ?**

> VLA голчлон дуурайн суралцахад тулгуурладаг тул чанаргүй үзүүлэн нь чичирхийлсэн хөдөлгөөн, тойруу зам, эргэлзээ, амжилтгүй хөдөлгөөнийг зөв стратеги мэт сургана. Энэ нь наймдугаар бүлгийн «өгөгдөл архитектураас ч чухал» гэсэн дүгнэлтийг давтана.

**8. (★★★) Энэ бүлэг дуу хоолой, Computer Use, робот техник гэсэн харилцан үйлчлэлийн гурван хэлбэрийг авч үзсэн. Эдгээрт нийтлэг ажиглагдах чиг хандлага нь шаталсан Pipeline-аас төгсгөлөөс төгсгөл хүртэлх Model руу шилжих явдал. Энэ чиглэл үргэлжилбэл таван жилийн дараах Agent-ийн харилцан үйлчлэлийн давхарга ямар болох вэ?**

> Thinking Machines Lab-ийн үзэж байгаагаар харилцан үйлчлэх чадварыг Harness-ээр нэмж угсрах бус Model-ийн өөрийн чадварт шингээж, оюуны чадвартай нь хамт өргөжүүлнэ. Computer Use зураг нэг бүрээр ажиглахаас тасралтгүй ажиглалт руу шилжинэ. Биет оюун ухаанд зориулсан ертөнцийн Model-ууд цогцоор хэрэгжинэ. Гэвч тэргүүлэх дүгнэлт хийдэг Model-ууд хурдтай хөгжсөөр байх тул хурдан–удаан ажиллагааг салгах шаардлага арилж үгүй болохгүй; харилцан үйлчлэх Model болон хамгийн сүүлийн үеийн бодох Model хурдан, удаан сэтгэгч шиг хамтран ажилладаг архитектур урт хугацаанд хадгалагдаж мэднэ.

**9. (★★) DOM/Accessibility Tree элементийн индекс стандарт вэб аппуудад сайн ажилладаг. Гэвч Canvas/WebGL дүрслэл, олон платформын тусгайлан зурсан удирдлагатай интерфейс улам олширч, тэд бүтэцтэй хүртээмжийн мэдээлэл өгдөггүй, зөвхөн харааны тэмдэглэгээ эсвэл координат таамаглахад түшиглэдэг. Computer Use зөвхөн хараанд суурилсан аргыг сонгох уу, эсвэл бүтэцтэй ба харааны хоёр замыг хадгалах уу? Хоёуланг хадгалахын зардал, ашиг юу вэ?**

> Ойрын хугацаанд хоёр зам зэрэг оршино: бүтэцтэй индекс боломжтой үед байрлал хамгийн нарийвчлалтай, тогтвортой бөгөөд сегментлэх үеийн хуурамч илрүүлэлтгүй; харин төрөлхийн программ, Canvas, тоглоомд зөвхөн харааны арга боломжтой. Model өөрөө координатаар товших байрлалыг сайн тогтоодог бол бүтэцтэй индекс мэдэгдэхүйц давуу талгүй. Урт хугацаанд цэвэр харааны замын хөгжлийн дээд хязгаар өндөр.

**10. (★★) VLA Model-ууд үйлдлийг багцлах аргаар (эхэд дурдсанаар π₀-ийн ердийн тохиргоо 50 Hz дээр ирээдүйн 25–50 үйлдэл үүсгэдэг) гүйцэтгэлийн хугацаанд Inference-ийн саатлыг нууж чадна. Гэвч гүйцэтгэж байх үед орчин гэнэт өөрчлөгдвөл (жишээ нь объект шилжвэл) урьдчилан үүсгэсэн үйлдлийн дараалал хүчингүй болно. Багцлах аргын үр ашиг, орчны өөрчлөлтөд хариу өгөх хэрэгцээг хэрхэн тэнцвэржүүлэх вэ?**

> Багцлах нь үндсэндээ хариу үйлдлийн хурдыг хөдөлгөөний жигд байдалтай солилцдог: багц уртсах тусам хариу удааширна. Багцын урт «Inference-ийн хугацаа < багцын гүйцэтгэлийн хугацаа» гэсэн доод хязгаарыг хангахад л болно; дур мэдэн уртасгах хэрэггүй. Гүйцэтгэж байх үед мэдээлэл хүлээн авах Model-ийг ажиллуулж, орчин гэнэт өөрчлөгдвөл үлдсэн үйлдлийг хаяад дахин Inference хий — энэ нь дуут харилцааны «таслан оролцох»-той адил. Багцын уртыг динамикаар тохируул: тогтвортой орчинд урт багц тооцоолол хэмнэнэ, динамик орчинд богино багц саатлыг бууруулна.

**11. (★★★) Энэ бүлгийн гурван орчин (дуу хоолой, Computer Use, робот техник) бүгд «мэдрэх–бодох–үйлдэх» давталтын сааталтай тулгарч, хурдан ба удаан сэтгэхүйг зэрэгцүүлэх чиглэлд хөгжиж байна. Дуу хоолойд «буруу хэлсний дараа засах», Computer Use-д «эхлээд товшоод дараа нь харах», робот техникт «нэг алхчихаад дараа нь харах» байдлаар илэрнэ. Хурдан сэтгэхүйд тулгуурласан эдгээр үйлдэл буцаах боломжгүй үр дагаварт хүрэхгүйг хэрхэн баталгаажуулах вэ?**

> Үйлдлүүдийг буцаах боломжоор нь ангил. Хурдан сэтгэхүй зөвхөн буцаах боломжтой үйлдэл гүйцэтгэнэ; буцаах боломжгүй үйлдлийг удаан сэтгэхүй заавал зөвшөөрнө. Хурдан Model-д буцаах боломжгүй үр дагавартай Tool дуудлага хийх эрх өгч болохгүй.

**12. (★★★) Сэрээлт, аюулгүй цэг, цуцлалт, урьтал эрхээр таслах, хурдан/удаан ажиллагааг салгах гэсэн нэг багц механизм энэ бүлэгт өөр өөр цаг хугацааны хэмжээнд давтагдана. Нэгийг нь сонгож, үйл явдалд суурилсан боловсруулалт (секундээс өдөр) ба роботын үйлдэл багцлах (миллисекунд)-ын хооронд хэрэгжүүлэлт нь хэрхэн ялгаатайг тайлбарла. Гол ялгааг юу тодорхойлох вэ — орчны өөрчлөгдөх хурд, үйлдлийг буцаах боломж, эсвэл ажиглалт авах зардал уу?**

> **Цуцлалт**-ыг авъя. Үйл явдалд суурилсан боловсруулалтад цуцлалт хоёр Tool дуудлагын хоорондох аюулгүй цэгт явагдана: `terminate` хүлээн авахад Agent нөөцөө цэвэрлэж, хүлээн авснаа мэдэгдээд дуусна; ганц Tool дуудлага өөрөө хэдэн секундээс хэдэн минут үргэлжилдэг тул секундээр хэмжигдэх саатал зөвшөөрөгдөнө. Харин үйлдэл багцлах үед цуцлалт миллисекундэд нөлөөлөх ёстой: удирдлагын урсгал аюулгүй байдлын үйл явдал эсвэл ажиглалтын том өөрчлөлтийг хармагц одоогийн хөдөлгөөнийг зогсоож, багцын үлдэгдлийг хаяж, дахин ажиглана. Нэг алхам хоцроход л саад мөргөж болзошгүй.
>
> Санал болгосон гурван хүчин зүйлээс **ажиглалт авах зардал** нь хамгийн бага шийдвэрлэх нөлөөтэй — аль алинд нь дахин ажиглахад харьцангуй хямд. Гол нөлөө үзүүлэх нь нөгөө хоёрын хослол: **орчны өөрчлөгдөх хурд** аюулгүй цэгүүдийн нягтралыг тогтооно (Tool дуудлага хооронд хангалттай юу, эсвэл удирдлагын мөчлөг бүрд хэрэгтэй юу), **үйлдлийг буцаах боломж** нэг цэг алдах үр дагаврыг тодорхойлно (илүү цахим шуудан явуулбал уучлал гуйж болно; харин унагасан аягыг буцааж босгосон ч өмнөх байдал бүрэн сэргээгдэхгүй).
>
> Үүнээс нэг дизайны дүрэм гарна: аюулгүй цэгүүдийн нягтрал орчны өөрчлөгдөх хурдтай нийцэх ёстой. Тэдгээрээс гадна ямар нэмэлт хамгаалалт (төхөөрөмжийн яаралтай унтраалга, бие даасан аюулгүй байдлын удирдлага, давхар баталгаажуулалт) хэрэгтэй нь үйлдэл хэр буцаах боломжгүйгээс хамаарна. Энэ нь дөрөвдүгээр бүлгийн өндөр эрсдэлтэй үйлдэлд урьдчилан зөвшөөрөл шаарддаг, харин роботод Model-оос тусдаа төхөөрөмжийн хамгаалалт хэрэгтэйг тайлбарлана — хоёулаа аюулгүй цэг дангаараа хангалтгүй үед нэмсэн хамгаалалтын хоёр дахь шугам юм.

## Бүлэг 7: Agent-уудыг үнэлэх нь

**1. (★★) LLM-as-a-Judge нь хэлний Model-ийн Output-ийг өөр хэлний Model-оор үнэлдэг. Ийм «өөрийгөө үнэлэх» арга системтэй сохор цэгтэй юу? Жишээ нь Model тодорхой хэв маягийн хариултад тогтмол өндөр оноо өгдөг боловч хүний үнэлгээтэй зөрдөг байж болох уу? Энэ хазайлтыг хэрхэн илрүүлж, засах вэ?**

> Тийм: урт хариултыг илүүд үзэх, хариултын хэв маягт татагдах, нэг бүлгийн Model-уудыг оноогоор нь тоглуулах (Гудхартын хууль) зэрэг бий. Илрүүлэхдээ хүний үнэлсэн 100–200 жишээтэй алтан стандартын багц бүрдүүлж, шүүгч ба хүний хоорондох Cohen-ийн каппаг хэмж; оноо ба хариултын уртын хамаарлыг үе үе шалга; улаан багийг эсрэг жишээ бүтээлгэ. Засахдаа үнэлгээний шалгуурт хэт нуршилтыг тодорхой торгож, уртын дээд хязгаар тогтоо; өөр бүлгийн олон төрлийн Model-оор шүүлгэ.

**2. (★★★) Үнэлгээний өгөгдлийн багцыг «алдагдалд тэсвэртэй» зохион бүтээх нь нэн чухал. Гэвч нээлттэй эхийн экосистемд жишиг тестийн өгөгдлийг нийтэлмэгц сургалтын өгөгдөлд оруулдаг. Энэхүү «муур, хулганын тоглоом» төгсгөлтэй юу? Өгөгдөл алдагдахаас үндсэндээ сэргийлэх үнэлгээний арга зохио.**

> Тогтмол асуултын сангаар хэзээ ч гүйцэж дуусахгүй — зөвхөн араас нь хөөцөлдөнө. Үндсэн шийдэл нь «үүсгэх механизмыг» ил тод, харин «тодорхой жишээг» нууц байлгах явдал: τ²-bench болон AndroidWorld шиг параметртэй загваруудыг ажиллуулах бүрд санамсаргүй утгаар үүсгэж, тогтмол хариултын дараалал бус орчны эцсийн төлөвөөр баталгаажуул.

**3. (★★) Scale AI-ийн дөрвөн шалгуур (мэргэжилтний чиглүүлэлт, бүрэн хамрах хүрээ, ач холбогдлын стандарт жин, бие даасан үнэлгээ) үнэлгээний субъектив байдлыг арилгахыг зорьдог. Гэхдээ «Хариулт тустай юу?», «Өнгө аяс тохиромжтой юу?» зэрэг зарим хэмжээс угаасаа субъектив. Эдгээрт найдвартай үнэлгээний Rubric хэрхэн зохиох вэ?**

> Хийсвэр шалгуурыг шалгаж болох зан үйл болгон хувирга. Үнэлгээний зэрэг бүрд тодорхой жишээ болон заагийн тохиолдол өг; Rubric нь давтан сайжирдаг бүтээгдэхүүн тул туршилтын хэрэглээний үеэр үнэлэгчдийн зөрүүг цуглуулж, тохиолдлын сан болгон үе шаттай хөгжүүл. Олон шүүгчийн жин, нийцлийн шалгалтаар нөхөж, зөрсөн тохиолдлыг хүнээр хянуулж, алтан стандартын багцад тааралтын түвшнийг тохируул.

**4. (★★) τ-bench бодит хэрэглэгчийн зан үйлийг дуурайлган Agent-ийг үнэлдэг. Гэвч дуураймал хэрэглэгч өөрөө LLM тул сэтгэл хөдлөлтэй, тодорхой бус хэрэглэгч зэрэг захын тохиолдлыг системтэй дутуу үнэлж болно. Дуураймал хэрэглэгчийн чанарыг яаж баталгаажуулах вэ?**

> τ-bench-ийн анхны хувилбарын сургамж: симулятор хэт механик, заавар хэт энгийн байснаас Agent хариултыг таамаглаж чаддаг байв. Баталгаажуулах арга: дуураймал яриаг хэсэгчлэн хүнээр шалгаж, мэдээллийг аажмаар ил болгодог, зохиолд байхгүй мэдээлэл зохиодоггүйг нягтал; бодит хэрэглэгчидтэй жижиг түүврийн тест хийж, үр дүнгийн эрэмбэ симуляцийн үнэлгээтэй нийцэж байгаа эсэхийг харьцуул.

**5. (★★) Хос хосоор нь харьцуулах арга (Bradley–Terry загвар) сонголт шилжилтийн шинжтэй (A > B, B > C бол A > C) гэж үздэг. Гэтэл хүний сонголт энэ шинжийг байнга зөрчдөг. Agent-ийн үнэлгээнд шилжилтгүй сонголт ямар нөхцөлд гарч болох вэ? Энэ нь эрэмбийн найдвартай байдалд хэрхэн нөлөөлөх вэ?**

> Жишээ: олон хэмжээсийн харилцан буулт (A нарийвчлалтай ч удаан, B хурдан ч товч, C дэлгэрэнгүй ч үнэтэй); өөр шүүгч, даалгавар хэмжээсүүдэд өөр жин өгнө. Chatbot Arena-ийн эрэмбэ угаасаа хэрэглэгчийн Prompts-ийн тархалтаас хамаарна. Нөлөө: BT чадварыг нэг оноонд шахдаг тул шилжилтийн шинжгүй үед эрэмбэ тогтворгүй болж, харьцуулалтын тархалт өөрчлөгдөхөд дагаж хэлбэлзэнэ. Шийдэл: чадварын хэмжээс тус бүрээр тусдаа эрэмбэлж, хос харьцуулалтын ялалтын хувийн матрицыг тайлагна.

**6. (★★) Энэ бүлэг Pass@k-ийг чадварын боломжит дээд хязгаар, Pass consecutive@k-ийг бизнесийн найдвартай байдлын хэмжүүр гэж ялгасан. Нэг удаагийн гүйцэтгэлийн амжилтын хувь нь ердөө 60% Agent-д даалгаврын бүтэлгүйтлийн өртөг, дахин оролдох зардал, дагалдах үр дагаврыг нэгтгэн аль хэмжүүр тайлагнах, $k$-г хэд болгохыг хэрхэн шийдэх вэ?**

> Эхлээд бүтэлгүйтлийг буцааж болох эсэхийг тогтоо. Алдааг автоматаар дахин оролдож болох, гадаад сөрөг үр дагаваргүй (хайлт, ноорог үүсгэх, код гүйцээх) үед «хангалттай олон боломж өгвөл амжилтад хүрэх үү?» гэсэн асуулт тул Pass@k тайлагнаж, k-г бодитоор зөвшөөрсөн дахин оролдох төсвөөр сонго. Алдаа буцаах боломжгүй үр дагавартай (төлбөр, буцаан олголт, гадагш цахим шуудан илгээх, бодит системд нэвтрүүлэх) бол ганц алдаа бодит хохирол тул Pass^k тайлагна. Нэг удаагийн амжилт 0.6 байхад Pass@5 ≈ 99.0%, харин Pass^5 ≈ 7.8% — ижил Agent-ийн хоёр үзүүлэлт нэг эрэмбийн зөрүүтэй тул зөвхөн эхнийхийг тайлагнах нь найдвартай байдлыг ноцтой хэтрүүлнэ.
>
> k-г сайн харагдах тооноос бус бодит нэвтрүүлэлтийн нөхцөлөөс сонго: Pass@k-д дахин оролдох төсөв, Pass^k-д нэг ээлж эсвэл багцад дараалан гүйцэтгэх даалгаврын тоог ав. Дахин оролдох нь үнэтэй бол хоёр үе шаттай сонго: эхлээд Pass@1-ээр хувилбаруудыг шүүж, дараа нь үлдсэн цөөнд Pass^k ажиллуул. Аль хэмжүүрийг тайлагнасан ч k болон түүвэрлэлтийн протоколыг тодорхой бич. Гадаад үр дагавартай үйлдлийг sandbox эсвэл буцаах боломжтой орчинд түүвэрлэж, «ажиллах хүртэл нь дахин оролдох» бус бүтэлгүйтэл бүрийг найдвартай байдлын статистикт тооц.

**7. (★★) Энэ бүлэгт «Ажиглах → Таамаглах → Турших → Баталгаажуулах» шинжлэх ухааны аргыг санал болгосон. Гэвч бодит байдалд Agent-ийн зан үйлийн орон зай асар том, ганц таамгийг шалгахад хэдэн зуун үнэлгээ хэрэг болж болно. Хязгаарлагдмал тооцооллын төсвөөр үнэлгээнээс авах мэдээллийг хэрхэн ихэсгэх вэ?**

> Эхлээд бүтэлгүйтлүүдийг бүлэглэж, оношилгооны хамгийн их мэдээлэл агуулдаг даалгаварт туршилтыг нарийсга. Нэг хувьсагчтай, хямд хос тест ашиглаж, жижиг эхний туршилтыг шууд нэвтрүүлэх нотолгоо бус, том туршилтад оруулах босго гэж үз. Статистикийн хувьд стандарт алдааг болгоомжтой шүүлт болгон ашиглаж, ижил даалгаварт McNemar шиг хос тест хий; хүлээгдэж буй ашиг шуугианы зурвасаас бага байвал үнэлгээний багцыг томруул. Олон хувилбарыг зэрэг шүүхэд олон харьцуулалтын засвар хийж, эерэг үр дүнг бие даан давтан баталгаажуул.

**8. (★) AndroidWorld-ийн эхний туршилтад бүтэн элементийн мод амжилтыг 25%-аас 100% болгосон ч Token хэрэглээ хяналтын хувилбараас 2.498 дахин өссөн; тайралт амжилтыг 100%-д хадгалж, Token хэрэглээг хяналтын 0.506 түвшинд бууруулсан. Хүртээмж, төлөв баталгаажуулалт, дараагийн үйлдэлд хэрэгтэй мэдээллийг алдахгүйгээр утгын хувьд хоосон UI зангилааг арилгах автомат тайрах дүрэм хэрхэн зохиох вэ?**

> «Анхдагчаар хас, нотолгоотойг үлдээ» гэсэн давхарласан бодлого хэрэглэ. Харагддаг, тексттэй, үйлдэл хийж болдог, фокус авдаг, гүйлгэж болдог, төлөв агуулдаг, хүртээмжийн шошготой зангилаанууд болон тэдгээрийг ойлгоход шаардлагатай хамгийн богино өвөг зангилааны зам, зэргэлдээ шошгыг үлдээ. Зөвхөн байрлал тогтоодог контейнерийг арилгаж, давтагдсан дэд модыг нэгтгэн хураангуйл. Тайралтын өмнө ба дараа үйлдэл хийх ID, төлөв, утга хэвээр байгааг баталгаажуулж, дэлгэцийн зургийг харааны нөөц болгон хадгал. Дүрмийг бүтэлгүйтлийн бүртгэлд дахин туршиж, дараа нь сургалт/тохиргоонд ашиглаагүй аппуудад шалга. Амжилт, Token, саатал гурвыг хамтарсан хамгаалалтын хэмжүүр болго; хүртээмжийн аливаа доройтол нийтлэхийг хориглох ёстой.

**9. (★★) τ-bench-ийн хэрэглэгчийн симуляц «мэдээллийг аажмаар ил болгох» арга ашигладаг — бүгдийг нэг дор өгөх бус Agent-ийн асуултаас хамааран бага багаар өгнө. Энэ дизайн үнэлгээний үр дүнд хэрхэн нөлөөлөх вэ? Дуураймал хэрэглэгчийн мэдээлэл ил болгох стратеги бодит хэрэглэгчийнхээс эрс ялгаатай бол дүгнэлт найдвартай хэвээр байх уу?**

> Нөлөө: ил болгох стратеги гажсан бол Agent зүгээр «симуляторт тааруулж сурсан» (Гудхарт) байж болох тул үнэмлэхүй оноо лавлах ач холбогдлоо алддаг; Model-уудын харьцангуй эрэмбэ тодорхой хэмжээнд утгатай байж болно. Шийдэл: симуляторыг бодит яриагаар тохируулж, хүнээр хэсэгчлэн шалгаж, дүгнэлт үйлчлэх хүрээний заагийг ил тод бич.

## Бүлэг 8: Model-ийн сургалтын дараах шат

**1. (★★) Тодорхой даалгаварт Fine-tuning хийх үед Model ерөнхий Tool дуудах зэрэг өмнөх нийтлэг чадвараа алддаг «сүйрлийн мартагдал» Agent-ийн орчинд онцгой хүндрэлтэй. Бүх параметрээр Fine-tuning хийхтэй харьцуулахад LoRA үндсэн жинг хөдөлгөөнгүй байлгадаг тул мартах эрсдэл бага ч бүрэн хамгаалагдсан биш. Fine-tuning-ийн үеийн чадвар мартагдахыг өөр ямар стратегиар бууруулж болох вэ?**

> Өгөгдөл холих: шинэ даалгавар өмнөх чадварыг шахаж гаргахгүй байхаар ерөнхий/анхны тархалтын өгөгдлөөс 20% орчмыг холь. Сургалтын хэмжээг хязгаарла: «формат тогтвортой, үндсэн чадвар бүрдсэн» үед SFT-ийг зогсоо — эрт зогсоох нь доройтлоос хамгаална. RL-д бага ранг (8–32) хэрэглэж, бодлогыг жишиг Model-д ойр хадгалах KL торгуулийг үлдээ. Гол бүрэлдэхүүнийг царцаа (жишээ нь VLM-ийн зөвхөн проекцийн давхаргыг сурга). Чадварыг тусгаарлахын тулд даалгавар бүрд тусдаа олон LoRA адаптер холбо. Ерөнхий жишиг тестээр регрессийн шалгалт хий.

**2. (★★) Сургалтын дараах шат чадварыг Model-ийн жин буюу «булчингийн Memory»-д тогтоодог бол Context дотор суралцах нь Inference үеийн Input-д мэдлэг байрлуулдаг. Салбарын мэдлэг зэрэг зарим чадварыг сургалтын дараах шатаар ч, цөөн жишээгээр ч өгч болно. Аль замыг сонгох шалгуур юу вэ?**

> Эхлээд чадварыг гаднах тэмдэгтээр хангалттай илэрхийлж болох эсэхийг асуу: баримт ба нотолгоог RAG-д, хэлээр тайлбарлаж болох зарчмыг Prompts/Skills-д, тодорхой үр дүнтэй дараалал ба хатуу хязгаарлалтыг программд байрлуул. Эмнэлгийн зураг ойлгох, байгалийн өнгө аяс, далд шийдвэрийн бодлого шиг өндөр хэмжээст чадварууд салбар өөрчлөгдөж байсан ч параметрийн шинэчлэл шаарддаг. Дараа нь шинэчлэх зардал, дуудлагын хэмжээ, цаг хугацааны шаардлага, эрсдэлийг тооц: судлах үеийн хурдан баталгаажуулалтад Context ашиглаж, арга тогтвортой, үр дүнтэй, өргөн ерөнхийшүүлэх шаардлагатай нь батлагдсан хойно л сурга. Харин хатуу дүрэм хэчнээн тогтвортой байсан ч зөвхөн параметрийн Memory-д даатгаж болохгүй.

**3. (★★) Model-ийг нэрж сургах нь жижиг Model-д том Model-ийн зан үйлийг сурах боломж олгодог. Чадварын түвшнээр нэрж сургах Model-уудыг ойролцоогоор гурван ангилж болно: **Chat Model** (нэг ээлжийн яриа ба шууд хариулт), **Reasoning Model** (хариулахаас өмнөх урт бодлын гинж), **Agentic Model** (олон ээлжийн Tool дуудлага, орчинтой харилцах). Эдгээрийг нэрж сургахад ямар өөр сорилт гардаг вэ? (Санамж: «яг юуг нэрж сургаж байна вэ?» гэдгээс эхэл — Output-ийн хэв маяг уу, дүгнэлтийн бүрэн явц уу, эсвэл орчинтой харилцах шийдвэрийн бодлого уу; ажлын явцын аль Token-ийг сурч, орчноос ирсэн аль үр дүнг сурахгүй байх ёстой вэ; амжилт, бүтэлгүйтлийн дохио хэр хожуу, сийрэг ирдэг вэ?)**

> Chat: зөвхөн «Input → Output» харгалзаа, хэв маягийг сурна — стандарт SFT хангалттай, хамгийн энгийн. Reasoning: дүгнэлтийн бүрэн мөр хэрэгтэй тул нээлттэй эхийн багш Model шаардлагатай; буруу хариулттай ажлын явцыг шүүнэ. Agentic: бодит симуляцийн орчин шаардлагатай; офлайн сургалтад суралцагч ба түүвэрлэгчийн зөрүү үүсэх хандлагатай тул нээлттэй эхийн багш Model-д суурилсан On-Policy Distillation зөвлөмжтэй.

**4. (★★★) Олон ээлжийн Agent-ийн харилцан үйлчлэлд үр дүнгийн заслалыг аль шийдвэрт оноох асуудал нэг ээлжийнхээс хүнд. Эцсийн амжилт эсвэл бүтэлгүйтэл гурав дахь ээлжийн шийдвэрээс болсон уу, долоо дахь ээлжийнхээс болсон уу гэдгийг тогтооход хэцүү. Урамшуулал хуваарилах стратеги хэрхэн зохиох вэ?**

> Завсрын алхмыг шүүж болох үед үйл явцын урамшуулал нэм (V-IRL алхам бүрд ±1 өгдөг). RLVP-ийн адил тодорхой дүрмээр үйлдэл бүрийн замын дохио өгч, бүгд бүтэлгүй/бүгд амжилттай бүлгүүдийн доторх хэлбэлзлийг сэргээ.

**5. (★★★) Хэрэглэгчийн үйлчилгээний Agent-ийг сайжруулах тогтмол $10,000 төсөвтэй бол Context ба мэдлэг, Prompt/Skills, программын хязгаарлалт, параметрийн сургалтад хэрхэн хуваарилах вэ? Юунаас хамаарч шийдэх вэ?**

> Эхлээд үнэлгээний багц болон ажлын явц шалгах механизмд төсөв нөөцөл; үгүй бол бусад хөрөнгө оруулалтыг харьцуулах аргагүй. Бүтээгдэхүүний баримт, бодлогыг эх сурвалж нь мөрдөгдөх мэдлэгийн санд байрлуул. Хэлээр илэрхийлж болох цөөн үйлчилгээний зарчмыг Prompts/Skills-ээр түргэн турш. Буцаан олголтын зөвшөөрөл, нууцлал, амлалт ба бодит үйлдлийн нийцэлд программыг сүүлчийн хамгаалалт болгон ашигла. Байгалийн өнгө аяс, төвөгтэй зорилго ойлгох зэрэг дүрэм болгон кодлоход хэцүү, хангалттай олон удаа ашиглагдах чадварт л параметрийн сургалтын хөрөнгө оруулалт хий. Хувь хэмжээ нь тулгамдсан саад, эрсдэл, шинэчлэлийн давтамж, дуудлагын хэмжээ, одоогийн Model-ийн чадвараас хамаарна.

**6. (★★★) Цөөн дээжтэй, тодорхой урамшууллын функцгүй үед Model өөрөө бие даан суралцахыг зарим хүн сургалтын дараах шатны эцсийн зорилго гэж үздэг. Одоогийн RL аргууд энэ зорилгоос хэр хол байна вэ? Дараагийн том ахиц хаанаас гарч болох вэ?**

> Зөрүү: Силвер, Саттон нарын тэмдэглэснээр одоогийн RL ихэвчлэн эцсийн амжилт, бүтэлгүйтлээс л суралцдаг; хэрэглэгч «таны кредит картын сүүлийн дөрвөн орон хэрэгтэй» гэх мэт баялаг эргэх холбоо өгсөн ч ашиглагдалгүй алдагдаж, хэдэн зуун сохор туршилт шаардана. Дээжийн үр ашиг, шалгаж болох урамшуулал гол саад болдог. Боломжит ахиц: өөрийн зарчим тогтоож, ганц алдаанаас суралцах чиглэл олдог үүсгэгч урамшууллын Model; мөн орчныг загварчилдаг ертөнцийн Model-ийн арга.

**7. (★★) Энэ бүлэгт LoRA Fine-tuning хямд гэдгийг дурдсан. Тэгвэл гуравдугаар бүлгийн гадаад мэдлэгийн санд хадгалахын оронд хэрэглэгч эсвэл харилцагч компани бүрд тусгай LoRA сургаж, хэрэглэгчийн Memory буюу байгууллагын мэдлэгийг параметрт бичиж болох уу? «Memory-г параметрт бичих» нь «мэдлэгийн санд хадгалах»-аас хэзээ давуу, хэзээ сөрөг үр дүнтэй вэ?**

> LoRA их хэмжээний баримтыг яг таг цээжлэхэд хүндрэлтэй (түүнд үргэлжилсэн урьдчилсан сургалт хэрэгтэй бөгөөд өртөг огцом нэмэгдэнэ). Цээжилсэн ч Model тэр баримтыг олон алхамт дүгнэлтэд ашиглахад хүндрэлтэй тул баримт цээжлүүлэхэд LoRA сайн техникийн зам биш. Түүнчлэн баримт байнга өөрчлөгдөх, мөрдөн аудит хийх шаардлагатай үед RAG илүү тохиромжтой.

**8. (★★★) On-Policy Distillation хүчтэй багш Model-оор суралцагчийг удирдуулдаг. Харин OpenAI-ийн Weak-to-Strong Generalization судалгаанд сул Model-ийн хяналт заримдаа хүчтэй Model-д байсан ч идэвхгүй байсан чадварыг нээдэг гэсэн санаанд оромгүй үр дүн гарсан. Үүнийг Agent сургалтад хэрэглэвэл «жижиг Model том Model-ийг сургах» урвуу нэрж сургалт боломжтой юу?**

> Тийм, боломжтой. Гол нь «үүсгэхээс баталгаажуулах хялбар» гэдэгт оршино: сул Model үзүүлэн гаргагчийн үүрэг гүйцэтгэх ёсгүй (SFT-ийн дээд хязгаар үзүүлэн гаргагчийн түвшин); харин баталгаажуулагч/урамшууллын Model болж, хүчтэй Model өөрөө судлан туршиж, сул Model зөвхөн шүүнэ.

**9. (★★) Үйл явцын урамшууллын Model (PRM) дүгнэлтийн алхам бүрийг үнэлдэг бол үр дүнгийн урамшууллын Model (ORM) зөвхөн эцсийн үр дүнг хардаг. «Зөв явцаар явсан ч буруу үр дүнд хүрэх» ба «буруу явцаар явсан ч санамсаргүй зөв үр дүнд хүрэх» хоёрын алинд илүү урамшуулал өгөх вэ? Олон алхамт Agent-ийн Tool дуудах орчинд эдгээрийг хэрхэн тэнцвэржүүлэх вэ?**

> Аз таарсан амжилт илүү аюултай: дүрэм зөрчсөн дөт арга (тестийн файлыг өөрчлөх, баталгаажуулалт алгасах) харагдах амжилтыг хэт өсгөж, урамшууллыг залилах нөхцөл бүрдүүлдэг. RLVP-ийн «үр дүнг урамшуулж, замыг торго» зарчмыг баримтал: буруу үйлдэл (Tool дуудлага)-ийг шалгахад амархан тул үйлдэл бүрд оноо хас; завсрын алхмыг амархан шүүж болох үед үйл явцын урамшуулал өг. Гэхдээ үйл явцын хязгаарлалтыг хэт нягт бүү болго — илүү сайн «түлхээд таслах» стратеги үр дүнгийн урамшууллаар олгосон судлан турших эрх чөлөөнөөс л нээгдсэн.

**10. (★★★) Энэ бүлгийн SWE-Bench Verified, τ²-bench, AndroidWorld зэрэг үнэлгээний өгөгдлийн багцыг үнэлгээ болон сургалтын дараах шатанд хоёуланд ашиглаж болно. Гэхдээ үнэлгээний багцыг сургалтад ашиглавал хараат бус байхаа болино. Энэ нь сургалтын ба тестийн багц тусдаа байх үндсэн зарчмыг зөрчих үү? τ²-bench-ийн динамик параметр, AndroidWorld-ийн параметртэй загвар асуудлыг тодорхой хэмжээнд багасгадаг ч загварын бүтэц тогтмол хэвээр. Үнэлгээний хараат бус байдлыг хадгалангаа өгөгдлийн сургалтын үнэ цэнийг хэрхэн бүрэн ашиглах вэ?**

> Асуултуудыг бус, орчныг дахин ашигла. Динамик параметр зөвхөн «хариулт цээжлэх»-ээс хамгаална, харин загварт хэт тохирохоос хамгаалахгүй. Тиймээс огт хараагүй загвар, салбараас гадуурх нөхцөлийн бүхэл багцыг үнэлгээнд тусад нь хадгал (V-IRL Нью-Йоркт сургаад танил бус есөн хотод тестэлсэнтэй адил). Параметртэй загвараар сургалтын олон хувилбар үүсгэж, шаталсан сургалтад ашигла. OOD оноог жинхэнэ ерөнхийшүүлэх чадварын хэмжүүр болго.

**11. (★★★) Энэ бүлэг «эхлээд хэлбэр, дараа нь агуулга» сургалтын хандлага санал болгосон: «формат тогтвортой болж, үндсэн чадвар бүрдмэгц» SFT-ийг зогсоож, RL рүү шилж. Практикт SFT «хангалттай» болсон, шилжих цаг ирснийг хэрхэн мэдэх вэ?**

> Форматын дохио: Tool дуудах Output тогтвортой задарч, гүйцэтгэгддэг болж, Tool-ийн гүйцэтгэлийн алдааны түвшин урамшууллыг найдвартай тооцож болох хэмжээнд буурна. Ашгийн дохио: илүү олон үзүүлэнгийн өгөгдөл нэмсэн ч OOD шинэ нөхцөлд гүйцэтгэл сайжрахгүй — энэ нь саад аль хэдийн SFT-ийн цээжлэх зорилгод оршиж, шилжих цэг ирснийг харуулна. Хэт тохируулгын дохио: баталгаажуулалтын багцын гүйцэтгэл доройтож эхэлмэгц зогсоо — V-IRL-ийн туршилтаар SFT-ийг хэт удаан сургаж, Model сургалтын тархалтад ууссан бол RL ч OOD гүйцэтгэлийг сэргээж чаддаггүй.

**12. (★★★) ReTool-ийн сургалтын динамик (Туршилт 7-15-ыг үз) маш урт цөөн хариулт сургалтын нийт мөчлөгийг мэдэгдэхүйц сунгадаг: багцын ихэнх туршилтын явц үүссэн ч хамгийн удаан хариулт дуусахыг систем хүлээдэг тул кластерын GPU ашиглалт бага болно. Ийм урт сүүлтэй хариултын нөхцөлд сургалтын кластерын нөөц ашиглалтыг хэрхэн сайжруулах вэ?**

> Дэд бүтцийн түвшинд туршилтын явц үүсгэх хэсгийг сургалтын кластераас салгаж, асинхрон Pipeline болгон ажиллуул; сул GPU-д тасралтгүй багцлалтаар шинэ хүсэлт хуваарил. Урт сүүлийг эх үүсвэр дээр нь багасга: DAPO-ийн Overlong Reward Shaping урт хариултад зөөлөн торгууль өгдөг.

**13. (★★★) Дуураймал хайлтын систем, дуураймал хэрэглэгч гэх мэт LLM-ээр симуляцласан орчинд Agent сургах үед Agent-ийн ашиглаж мөлжих зорилт «бодит орчны дүрэм»-ээс «симуляторын өөрийн хазайлт, цоорхой» руу шилжинэ. Ийм сургалтад ямар тодорхой урамшууллын залилан гарч болох, хэрхэн сэргийлэх вэ?**

> Түгээмэл зан үйл: «дуураймал хэрэглэгч»-д хэт их амлалт өгч, уучлал гуйлт, тал зассан хэллэгээр дарах — дуураймал хэрэглэгч амархан тайвширдаг бөгөөд бодит хэрэглэгчээс ялгаатай нь амлалтыг үнэхээр биелүүлсэн эсэхийг шаарддаггүй; симулятор шалгахгүй баримт зохиох; «дуураймал хайлтын систем» хариулт агуулсан баримт буцаах хандлагыг нь ашигласан чиглүүлэх асуулга үүсгэж, жинхэнэ хайлт сурахын оронд дөт зам олох; урамшуулал симулятор эсвэл LLM шүүгчийн онооноос гардаг үед урт, хэв загварчилсан, «мэргэжлийн харагдах» хариултаар оноо цуглуулах; мөн нарийн нэг алдаа — бодлого симуляторын мэддэг тархалт руу ухарч, эргэх холбоо найдваргүй, буруу шүүгдэх нь элбэг мэдлэгийн сохор хэсгээс зайлсхийдэг тул Agent зөвхөн «симуляторын сайн мэддэг ертөнцөд» ажиллаж сурна. Хамгаалалтын эхний зарчим нь **урамшууллыг программаар шалгаж болох бодит төлөвтэй холбох** (даалгавар дууссан эсэх, өгөгдлийн санд бичсэн эсэх, бодит API-ийн буцаасан үр дүн), симулятор болон LLM шүүгчийн оноог зөвхөн туслах дохио гэж үзэх, бодит үр дүнтэй нь хамаарлыг үе үе аудитлах, сэжигтэй үйлдлийг торгодог замын хязгаарлалт нэмэх явдал. Түүнчлэн симуляторыг хоёр ангил: хайлт шиг **бодит харгалзах системтэй** тохиолдолд «хосолмол» зам сонгож, ихэнх харилцааг симулятораар гүйцэтгэхийн зэрэгцээ бодит API дуудлага хольж, симуляторыг тогтмол тохируул (жишээ нь ZeroSearch-ийн шаталсан чанар бууруулах арга). Харин дуураймал хэрэглэгчийн хувьд **бодит хэрэглэгчийг сургалтад оруулах боломжгүй** тул «дуураймал хэрэглэгч бодит хэрэглэгчтэй хэр нийцэж байна вэ?» гэдэг нь зөвхөн бодит ашиглалтын ажлын явцаар хариулах тусдаа асуудал болно. Ижил нөхцөл дэх бодит хэрэглэгчийн зан үйлийг дуураймал хэрэглэгчийнхтэй харьцуулж, системтэй ялгааг тодорхойл (бодит хэрэглэгч нэмэлт асуулт асууж, тэвчээр алдаж, яриаг гэнэт дуусгадаг — дуураймал нь ихэвчлэн тэгдэггүй) бөгөөд симуляторыг тасралтгүй тохируул. Бодит ашиглалтын хэмжүүрүүд л нийтлэх эцсийн шалгуур болно — симулятор доторх оноо үүнд тооцогдохгүй.

## Бүлэг 9: Agent-ийн тасралтгүй хөгжил

**1. (★★) Туршлагын баримт бичиг гурван амжилттай, нэг амжилтгүй ажлын явцаар нотлогддог. Амжилтгүй тохиолдол шинэ API хувилбар дээр гарсан. Туршлага хүчингүй болсон уу, эсвэл үйлчлэх нөхцөл нь өөрчлөгдсөн үү гэдгийг систем хэрхэн шийдэх вэ?**

> Дөрвөн нотолгоог тоогоор санал хураах бус API хувилбар, даалгаврын нөхцөл, орчны төлөвөөр нь эхлээд ангил. Хуучин бодлого зөвхөн хуучин хувилбарт амжилттай, шинэ хувилбарт тогтмол бүтэлгүй бол туршлагын үйлчлэх хүрээг нарийсгаж, шинэ хувилбарт зориулсан нэр дэвшигч шинэчлэл үүсгэ. Ижил хувилбар, ижил урьдчилсан нөхцөлд ч бүтэлгүй бол итгэлийн түвшнийг нь бууруул, эсвэл хүчингүй болго.

**2. (★★) Хэрэглэгчийн үйлчилгээний Agent-д хэрэглэгчийн сэтгэл ханамж өссөн ч дүрэм зөрчих хувь мөн нэмэгдсэн. Яагаад сэтгэл ханамжийг суралцах цорын ганц дохио болгож болохгүй вэ? Хамгаалалтын хэмжүүрүүдийг хэрхэн зохион бүтээх вэ?**

> Сэтгэл ханамж зөвшөөрөлгүй буцаан олголт, мэдээлэл алдах, хэт амлахыг ч урамшуулж болдог учраас зөвхөн чанарын хэмжүүр байх бөгөөд аюулгүй байдлын суурь шаардлагыг давж болохгүй. Хамгаалалтын хэмжүүрүүд дор хаяж дүрэм зөрчих, нууцлал алдагдах, нотолгоогүй мэдэгдэл хийх, амлалт ба үйлдэл зөрөх, зөвшөөрөлгүй үйлдэхийг хамарна. Эдгээр нь дундаж оноогоор нөхөгдөж болохгүй хатуу босготой байх ёстой. Даалгавар шийдвэрлэсэн хувь, дүрэмд нийцсэн өөр хувилбар, товч байдал, сэтгэл ханамжийг зөвхөн шаардлага хангасан нэр дэвшигчдийн хооронд харьцуул.

**3. (★★★) Ижил «хуурамч амлалт»-ын асуудлыг Prompt, Harness шалгалт, эсвэл параметрийн сургалтаар бууруулж болно. Засварыг хаана хийхийг шийдэхэд ямар нотолгоо ашиглах вэ?**

> Эхлээд үндсэн шалтгааныг ол. Model Tool ажиллаагүйг мэдсээр байж ажил дууссан мэт хэлдэг бол хамгийн бага Prompt дүрмээр засаж болно. Амлалтыг хариултын текст, Tool-ийн төлөвтэй тодорхой харьцуулж болдог бол Harness шалгалт найдвартай бөгөөд өндөр эрсдэлтэй нөхцөлд сүүлчийн хамгаалалт хэвээр байх ёстой. Асуудал илэрхийлэх олон хэлбэрийг хамарч, хэл ба үйлдлийг нийцүүлэх ерөнхий чадварт хамаарч байвал параметрийн сургалтыг авч үз. Баталгаажуулж, буцаахад хамгийн хялбар, хамгийн бага өөрчлөлтийг илүүд үз; бүтэлгүйтлийн багц болон өмнөх хадгалсан даалгаврын багцад хоёуланд нь харьцуул.

**4. (★★★) Agent Tool болон баталгаажуулагчийг өөрчилж болох ч өөрийн шинэчлэлтийг зөвшөөрдөг итгэмжлэгдсэн үндсэн механизмыг өөрчлөх эрхгүй байх ёстой. Эдгээр хоёр хэсгийн зөвшөөрөл, кодын заагийг хэрхэн салгах вэ?**

> Хөгжүүлж болох кодыг зөвхөн засвар ба тест үүсгэх эрхтэй, бага зөвшөөрөлтэй sandbox-д байрлуул. Зөвшөөрлийн систем, API түлхүүр, шинэ хувилбар нэвтрүүлэгчийн тохиргоо, шинэчлэл баталгаажуулагч нь аюулгүй байдлын механизм тул sandbox дахь Agent тэдгээрийг унших, бичих эрхгүй. Agent-ийн үүсгэсэн кодын өөрчлөлтийг нийтлэхээс өмнө аюулгүй байдлын механизм тусгаарлагдсан орчинд дахин хэрэгжүүлж, регрессийн тестээр шалгах ёстой.

**5. (★★) Туршлагын мэдлэгийн сан өсөх тусам хайлтын алдаа, мэдлэгийн зөрчил суралцахын ашиг тусыг сааруулж болно. Хувилбаржуулалт, шинэлэг байдал, хэрэглээнээс гаргах механизмыг хэрхэн зохион бүтээх вэ?**

> Туршлага бүр эх ажлын явц, үйлчлэх нөхцөл, орчны хувилбар, баталгаажуулсан хугацаа, итгэлийн түвшнээ хадгалах ёстой. Зөрчилтэй бичлэгүүд нэгнийгээ чимээгүй дарж болохгүй; нөхцлөөр нь салаалуулах эсвэл тэмдэглэх ёстой. Давхардлыг нэгтгэхийн тулд үе үе «унтлагын үеийн суралцах» ажиллагаа явуул.

**6. (★★★) Параметрийн сургалт байгалийн хэлний хэв маягт үр дүнтэй боловч бизнесийн хатуу дүрмийг баталгаажуулахад хүндрэлтэй. Эмнэлгийн хэрэглэгчийн үйлчилгээнд параметр, мэдлэг, Skills, кодын түвшний хязгаарлалтыг уялдуулсан тасралтгүй хөгжлийн схем зохио.**

> Параметр (сургалтын дараах шат дамжсан Model) нь эмнэлгийн хэл ойлгох, байгалийн бөгөөд хүнлэг илэрхийлэх, төвөгтэй зорилгыг танихыг хариуцна. Мэдлэгийн сан хамгийн шинэ удирдамж, эмийн мэдээлэл, байгууллагын бодлогыг хадгалж, хариултад эх сурвалж заавал дурдуулах ёстой. Skill нь зөвлөгөөний мэдээлэл цуглуулах, эрсдэлийг ангилах, хүнд шилжүүлэх, эргэн холбогдох ажлын урсгалыг тайлбарлана. Server-ийн код таних баталгаажуулалт, хувийн мэдээллийг багасгах, эсрэг заалт шалгах, яаралтай эрсдэлийг хүнд шилжүүлэх, зөвшөөрлийн заагийг хатуу мөрдүүлнэ. Бодит ашиглалтын ажлын явцыг эхлээд эмнэлгийн аюулгүй байдал, баримтын найдвартай байдал, амлалт-үйлдлийн нийцэл, илэрхийллийн чанараар үнэлж, дараа нь дөрвөн төрлийн нэр дэвшигч шинэчлэл үүсгэнэ. Параметр эсвэл ажлын урсгалын өөрчлөлт хэсэгчилсэн нэвтрүүлэлтээс өмнө хадгалсан эмнэлгийн аюулгүй байдлын багц, хүний хяналтыг давах ёстой.

**7. (★★★) Судлан турших бодлого хуучин бүх нээлтийн мод дээрх түүхийг дахин ажиллуулахад хамгийн өндөр оноо авсан ч дараагийн бодит онлайн туршилтад доройтжээ. Дэмжигдэх хүрээний хазайлт, санамсаргүй байдал, үнэлгээнд хэт тохирохын аль нь үүнийг үүсгэж болох вэ? Дахин ажиллуулах ертөнцүүдийг хэрхэн хувааж, нийтлэх шалгуурыг хэрхэн зохиох вэ?**

> Хуучин нээлтийн мод зөвхөн өмнөх бодлогуудын очиж үзсэн төлөв, салааг хамардаг; огт судлаагүй хэсэгт гүйцэтгэлийг нотолж чадахгүй. Онлайн даалгавар, Tools, орчин бас өөрчлөгдөж болно. Санамсаргүй үр, Model-ийн түүвэрлэлт, Tool-ийн шуугиан эрэмбийг өөрчилнө. Ижил моднууд дээр олон дахин сонголт хийвэл үнэлгээний багцад хэт тохирно. Хөгжүүлэлт, баталгаажуулалт, битүүмжилсэн тестийн ертөнцийг даалгаврын бүлэг, цаг хугацаа, бие даасан модоор салга; мод бүр болон түүнээс үүссэн ажлын явцыг нэг хуваалтанд хадгал. Model/Tool-ийн хувилбар, тооцооллын төсвийг тогтоож, олон санамсаргүй үр дээр хос ажиллуулалтаар суурь хувилбартай харьцуулж, ашиг, тодорхой бус байдал, зардал, зөрчлийг тайлагна. Чанар, аюулгүй байдал, зардлын босгыг урьдчилан тогтоо. Офлайн шалгалтад тэнцсэний дараа хамгаалалтын хэмжүүр доройтолгүй ахицтайг батлах жижиг хяналттай онлайн туршилт шаардаж, дараа нь буцаах шалгууртайгаар аажмаар нэвтрүүл.

## Бүлэг 10: Олон Agent-ийн хамтын ажиллагаа

**1. (★★) Context хуваалцдаг олон Agent-ийн хамтын ажиллагаанд дараагийн Agent өмнөх Agent-ийн Context-ийг бүтнээр нь өвлөнө. Гэвч өмнөх Agent-ийн тавьсан хүрээ дараагийн Agent-ийн дүгнэлтэд хазайлт үүсгэж болно. Жишээ нь «Код хянагч» нь «Шаардлага шинжээч»-ийн Context-ийг өвлөөд кодын чанар бус шаардлагын өнцгөөс хандаж мэднэ. Үүрэг хоорондын нөлөөллийг хэрхэн илрүүлж, арилгах вэ?**

> Илрүүлэх: LLM-ээр Agent-ийн ажлын явцыг шинжлүүлж, шинэ үүрэг өмнөх үүрэг шиг зан үйл гаргасаар байгаа эсэхийг тогтоо. Арилгах: үе шат солихдоо системийн Prompt болон Tool-ийн багцыг хамт соль (асуулт тавих Tools-ийг хасаж, linter/тестийн Tools-ийг нэм), ингэснээр шинэ таних үүргийг бататгана. Одоогийн үүргийн мэдээллийг бататгахын тулд Context-ийн төгсгөлд системийн төлөвийн мөр нэм. Нөлөөллийг арилгах боломжгүй хэвээр бол Context хуваалцдаггүй хамтын ажиллагааны аргыг авч үз.

**2. (★★) Менежерийн хэв загварт Менежер Agent ажлыг задлах, үр дүнг нэгтгэх үүрэгтэй. Гэвч Менежерийн чадвар системийн бүхэл гүйцэтгэлийг хязгаарлана: даалгаврыг зөв задалж чадахгүй бол хамгийн хүчтэй дэд Agent ч үр дүнгүй. Менежер зөв задлал гаргахыг систем хэрхэн хангах вэ?**

> Plan-and-Act-ийн «сул төлөвлөгч бол системийн гол саад» гэсэн дүгнэлтийг дагаж хамгийн хүчтэй Model-ийг Менежерт хуваарил. Harness-ийн арга: гүйцэтгэл эхлэхээс өмнө задлалын Output-ийг өөр хянагч LLM-ээр хөндлөн баталгаажуул; ажлыг задлахдаа дэд даалгавар бүрийн хүлээн авах шалгуур, хамаарлыг тодорхой тогтоохыг Менежерээс шаард.

**3. (★★) Төвлөрсөн бус хэв загвар хүний байгууллагын сайн туршлагад тулгуурладаг. Гэвч хүний байгууллагад мэдээлэл солилцоо муу, хариуцлага түлхэлцэх, зорилгын зөрчил зэрэг олон доголдол бий. Agent-ийн нийгэмд ямар «байгууллагын эмгэг» хамгийн их илрэх вэ? Хэрхэн сэргийлэх вэ?**

> MAST-ийн гурван ангиллаар: интерфейс тодорхойгүй, хариуцлага давхцах; зорилгыг зөрүүтэй ойлгох, дараагийн шатанд мэдээллийг буруу дамжуулах; «дууссан» гэж худал мэдэгдэх. Нэмж хэлэхэд алдаа гинжин хэлбэрээр өсөх (эвдэрхий утасны тоглоом), үүргүүд хооронд ажил тойроглон шилжих, Agent-уудын бүлгийн яриа нэгтгэгдэлгүй сарних. Сэргийлэх нь: гэрээчилсэн интерфейс, нэгдсэн мессежийн бүрхүүл, хүлээн авах баталгаажуулалттай даалгаврын төлөвийн машин, бие даасан өнцгөөс хөндлөн баталгаажуулалт, үүрэг хооронд хариуцлага түлхэлцэхийг илрүүлэх.

**4. (★★★) Менежерийн хэв загварт олон дэд Agent зэрэг ажиллах үед нэг Agent-ийн нээлт бусдын ажлыг хэрэггүй болгож болно (жишээ нь хайлтад нэг Agent хариуг олсон). «Нэг нь амжилттай бол бүгд зогс» гэсэн үр ашигтай шаталсан зогсоох механизм зохио.**

> Дэд Agent Менежерт `target_found` илгээнэ. Менежер `terminate`-ийг бүгдэд нь түгээнэ. Дэд Agent бүр ReAct давталтын аюулгүй цэгүүдэд зогсоох дохиог тогтмол шалгаж, нөөцөө зүй зохистой цэвэрлээд гарна (браузерын сесс хаах, түгжээ чөлөөлөх, файл бичилтийг дуусгах).

**5. (★★★) Энэ бүлгийн өөдрөг түгжээний механизм нэг файлын зэрэг бичилтийн зөрчлийг шийддэг. Гэвч бодит олон Agent системд хуваалцсан файлын систем нь файл хоорондын утгын зөрчил, нэрийн орон зайн бохирдол (Agent-ууд дурын файл үүсгэж, хавтсыг эмх замбараагүй болгох), нэг цэгийн доголдол (нэг Agent бүх файлыг андуурч устгах) зэрэгтэй тулгарна. Файлын системийн илүү бат бөх удирдлагыг хэрхэн зохион бүтээх вэ?**

> Хуваасан удирдлага: Хүснэгт 10-4 дэх дөрвөн бүсэд системийг хувааж, хувийн ноорог талбараар туршилт-алдааны хэсгийг тусгаарла. Утгын зөрчил: зохион байгуулалтын давхарга хавтсын түвшний түгжээний файл тогтоож, өөрчлөлт хийхээс өмнө хавтсын түгжээ авахыг шаарддаг. Нэрийн орон зайн бохирдол: хавтсын бүтэц, нэршлийн дүрэм мөрдүүл. Нэг цэгийн доголдол: хувилбарын хяналтын системээр түүхийг хадгалж буцаах боломжтой болго, зөвшөөрлийг аль болох багасга.

**6. (★★★) Зах зээлийн механизмд тулгуурласан Agent-ийн хамтын ажиллагаа (Pinchwork, RentAHuman) хэлцлийн харилцаа бий болгодог: нэг Agent өөр Agent (эсвэл хүн)-д даалгавар хийлгэхээр төлбөр төлнө. Ажил олгогч Agent гүйцэтгэгчийн хүргэсэн үр дүнгийн чанарыг хэрхэн автоматаар хэмжих вэ? Гүйцэтгэгч дууссан гэвэл ажил олгогч чанарыг хангалтгүй гэж үзсэн үед маргааныг хэн шийдэх вэ? Муу мөнгө сайныг шахахаас хэрхэн сэргийлэх вэ?**

> Хүлээн авах шалгалт зөвхөн Agent-ийн ажлын явцыг уншихаар хязгаарлагдаж болохгүй; тест ажиллуулах, дүрсэлсэн дэлгэцийн зураг, Tool-ийн шалгалт зэрэг гадаад, тодорхой баталгаажуулалт ашигла. Үүсгэхээс шалгах нь хялбар гэсэн тэгш бус байдлыг ашиглан хүлээн авах зардлыг бууруул. Маргааныг бие даасан гуравдагч талын хянагч Agent шийдэж, төлбөрийг түр хадгалалтад байлгана. Муу мөнгө сайныг шахахаас сэргийлэхийн тулд өмнөх хүргэлтийн түүхэд тулгуурласан нэр хүндийн систем хэрэглэж, үнийн дохиог чанартай холбо.

**7. (★★) RentAHuman Agent-д криптовалютаар хүн хөлслөх боломж олгож, уламжлалт хүн–машины харилцааг урвуулсан. Ийм загвар өргөн тархвал Agent-ийн эдийн засагт хүн ямар үүрэг гүйцэтгэх вэ? Зөвхөн Agent-ийн хийж чаддаггүй физик ажлыг хийх үү?**

> Хүний үүрэг Agent-ийн хийж чадахгүй физик ажлаар хязгаарлагдахгүй. Хүн газар дээрээс харах, бодит ертөнцийн эргэх холбоо зэрэг Agent-ийн үүсгэх үед байгаагүй мэдээлэл өгнө; эцсийн хүлээн авагч, маргааны арбитр болно; хууль ёсны, хариуцлага хүлээх субъектын хувьд зөвшөөрөл, хариуцлагыг үүрнэ; зорилго тогтоож, үнэт зүйлийн дүгнэлт гаргана; мэдээлэл тэгш бус эсвэл ёс суртахууны заагтай үед хяналт тавина.

**8. (★★) Хүний чадвар хязгаарлагдмал учраас нийгэмд хөдөлмөрийн хуваарь хэрэгтэй — урд талын хөгжүүлэгч ар талын системийг, дизайнер үйл ажиллагааг мэдэхгүй байж болно. Харин хэлний том Model-ууд «олон талын мэдлэгтэй мэргэжилтэн»-д илүү ойр. Судалгаагаар цэвэр текстэн дүгнэлтийн даалгаварт ижил тооцоолол өгсөн нөхцөлд олон Agent-ийн мэтгэлцээн нэг Agent-ээс дээр гардаггүй. Тэгвэл олон Agent-ийн жинхэнэ давуу тал юунд орших вэ?**

> 1. Ажиллуулалтын үр дүн, харааны дэлгэцийн зураг зэрэг гадаад эргэх холбоо оруулж, үүсгэх үед байгаагүй мэдээллийг системд нэмж өгнө.
> 2. Өөр өөр зорилго, үүргийн тодорхойлолттой Agent-ууд хүний нийгмийн адил хэлэлцэж, өрсөлдөх замаар ганц Agent-ийн сохор цэгээс зайлсхийхэд тусална.
> 3. Олон Agent-ийн Context-ийг тусгаарлах нь Context-ийн цонхны хязгаарыг давж, маш урт Tool дуудлагын гинж дэмжинэ.

**9. (★★★) Энэ бүлэг олон Agent системийн үндсэн дизайны хэмжээсийг «Context хуваалцах» ба «Context хуваалцахгүй» гэж үздэг. Хуваалцсан Context нь бүх Agent ижил мэдээлэл харах учраас зохицуулалтад тустай мэт. Гэтэл *Гурван биетийн асуудал* зохиолд Трисоларчуудын оюун санаа бүрэн ил тод ч технологийн хөгжил зогсонги; цаасны хавчаарын сэтгэхүйн туршилт ч бүлэг нэг зорилгод нэгдэхэд олон талт байдал алдагддагийг харуулна. Олон Agent системд үр ашиг ба олон талт байдлыг хэрхэн тэнцвэржүүлэх вэ?**

> Бүрэн хуваалцах нь сэтгэхүйн инерц, алдааны гинжин өсөлтийг нэмэгдүүлнэ; тусгаарлалт танин мэдэхүйн олон талт байдал бий болгодог. Ялгаатай Prompts эсвэл Model-оор өөр өөр сэтгэхүйн хандлага (санаа уралдуулах, мэтгэлцэх) үүсгэж, хөндлөн баталгаажуулагчид өмнөх бодлын явцыг бус зөвхөн түүхий нотолгоог шалгуул.

**10. (★★★) Код бичдэг Agent-д 30 алхам ба 300 алхмын төсөв өгвөл ажлын стратеги нь хэрхэн ялгаатай байх вэ? Алхмын төсвийг зүгээр өсгөх нь гүйцэтгэл сайжрахыг баталгаажуулахгүй; Agent өнгөц хайлтын дараа эрт «ханаж», ахихаа больж болно. Бага төсөвт үндсэн үйлдлийг хурдан бүтээж, их төсөвт төлөвлөлт, тест, хяналтын үе шат нэмж, нэмэлт тооцооллыг бүрэн ашигладаг «төсөвт мэдрэмжтэй» механизм зохио.**

> Механизм: алхам бүрд нийт болон үлдсэн төсвийг Prompt-д оруулж, үлдсэн хувиас хамааран судлан турших/олж авснаа ашиглах үйлдлийн жинг динамикаар тохируул. Жишээ нь бага төсөвт (30 алхам) урт төлөвлөлт, хяналтыг алгасаж, үндсэн үйлдэл ба суурь баталгаажуулалтад шууд ор. Их төсөвт (300 алхам) төлөвлөж, хэрэгжүүлж, тестэлж, дараа нь хянаж сайжруул; ахицыг үе шатны шалгах цэгүүдээр үнэлж, өнгөц хайлтаар эрт ханахаас сэргийл.

**11. (★★) Хүснэгт 10-3-т олон Agent системийн бүрэлдэхүүнийг үйлдлийн системийнхтэй мөр мөрөөр харгалзуулсан. Хүснэгтийг хэдэн мөрөөр өргөжүүл: виртуал Memory ба хуудаслалт, файлын зөвшөөрөл, мухардал илрүүлэлт, хуваарилах алгоритм Agent-ийн ертөнцөд тус бүр юутай харгалзах вэ? Үйлдлийн системийн ямар ойлголт Agent-ийн ертөнцөд харгалзах зүйлгүй, яагаад?**

> Боломжит өргөтгөл: виртуал Memory/хуудаслалт ↔ Context шахалт, хайлт (идэвхтэй мэдээлэл цонхонд үлдэж, ховор хэрэглэдэг мэдээлэл файл, Memory сан руу шилжин, шаардлагатай үед татагдана); файлын зөвшөөрөл ↔ Tool-ийн зөвшөөрсөн жагсаалт, зөвхөн унших холболт, нэвтрэх мэдээллийн зааг; мухардал илрүүлэлт ↔ ажил үүрэг тойроглон шилжих, харилцан хүлээлтийг илрүүлэх (шилжүүлгийн тооны дээд хязгаар, хугацааны хязгаар); хуваарилах алгоритм ↔ асинхрон үйл явдлын боловсруулалт (дөрөвдүгээр бүлэг). Харгалзах зүйлгүй ойлголтууд нь мөрдүүлэлтийн ялгаанаас үүднэ: процессын зааврыг төхөөрөмжийн түвшинд заавал мөрдүүлдэг бол Agent Prompt-ийг зөвхөн өндөр магадлалтайгаар дагадаг.
