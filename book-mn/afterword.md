# Төгсгөлийн үг: Agent = LLM + Context + Tools томьёо руу буцах {.unnumbered}

Энэ ном нэг томьёогоор эхэлсэн: **Agent = LLM + Context + Tools**. Арван бүлгийг уншиж дуусаад эдгээр гурван бүрэлдэхүүнийг эргэн харахад бид тэднийг бодитоор ажилладаг нэг систем болгон нэгтгэж чаддаг болсон байна: Model даалгаврыг ойлгож, шийдвэр гаргана; Context тухайн мөчид хэрэгтэй мэдээллийг өгнө; Tools ажиглалт цуглуулж, үйлдлийг гүйцэтгэнэ.

Нэгдүгээр бүлэгт энэ функциональ задаргаагаар ерөнхий зургийг гаргаад, дараа нь **Agent = Model + Harness** томьёогоор бодит хэрэгжүүлэлт дэх үүргийн хуваарилалтыг тайлбарласан: Model шийдвэр гаргана; Harness нь Context, Tool-ийн интерфейс, ажиллах давталт болон төлөвийг зохион байгуулж, хязгаарлалт, баталгаажуулалт, залруулгыг хэрэгжүүлнэ.

- **Agent бүтээх (2–6 дугаар бүлэг).** Контекстийн инженерчлэл нэг шийдвэрт шаардлагатай мэдээллийг цэгцэлж, санах ой ба мэдлэгийн сан нь мэдээллийг сесс дамжуулан хадгалах, хайлт хийх боломжийг олгоно. Tools ажиглалт ба үйлдлийн интерфейсийг бүрдүүлж, код үүсгэх чадвар нь Agent-д шинэ Tool болон систем бичих боломж олгоно. Харилцан үйлчлэлийн бүлэг эдгээр интерфейсийг дуу хоолой, график интерфейс, физик ертөнц хүртэл өргөжүүлж, үйл явдлыг тасралтгүй хүлээн авч ажиллах горимыг авч үзсэн.
- **Үнэлгээ ба хувьсал (7–9 дүгээр бүлэг).** Үнэлгээ нь системийн гүйцэтгэлийг харьцуулах, бүтэлгүйтлийн шалтгааныг илрүүлэхэд тусална. Дараах сургалт өгөгдөл болон орчноор дамжуулан Model-ийн параметрийг шинэчилнэ. Тасралтгүй хувьсал нь ажиллах явцын туршлагыг мэдлэг, заавар, программ эсвэл параметрийн шинэчлэлт болгон хувиргаж, өөрчлөлтийг баталгаажуулалт ба нийтлэх үйл явцаар удирдана.
- **Хамтын ажиллагаа (10 дугаар бүлэг).** Олон Agent-ийн систем гишүүн бүрт өөр Context, Tools, үүрэг хариуцлага оноож, харилцаа холбоо ба харилцан шалгалтаар даалгаврыг хамтдаа гүйцэтгэнэ. Гишүүдийн тоо өсөхөд хуваалцсан төлөв, даалгаврын хамаарал, нөөц, маргааныг ч удирдах шаардлагатай болно.

Оршилд дурдсан тэр төлбөрийн баримт руу буцъя. Харилцагчийн үйлчилгээний ажилтан «хөнгөлж болно» гэж хэлсэн бол энэ амлалтыг ярианы бичлэгээс олж болно. Дараагийн сарын төлбөрийн баримт гарсны дараа л бодит хөнгөлөлтийг тулгах өөр нэг нотолгоо бий болно. Хэрэв эргэн залгасан дуудлага хэрэглэгчийн утсанд ирвэл туслахын урьдчилан илгээсэн хүсэлтийн дугаар болон хэлэлцээрийн хураангуй нь хэрэглэгч асуудлаа үргэлжлүүлэн шийдэх үндэс болно.

Хэрэглэгч утсаа аваад бүх зүйлийг дахин эхнээс нь ярих хэрэгтэй болвол юуг засах ёстой вэ? Эхлээд өмнөх ярианы хураангуйг уншина. Ажилтны амласан хөнгөлөлтийн хэмжээ ч тэмдэглэгдээгүй бол хэлэлцээрийн үр дүнг бүртгэх алхмыг сайжруулах хэрэгтэй. Хураангуй тодорхой бичигдсэн ч эргэн залгасан яриа дууссаны дараа л ирсэн бол асуудал нь хүлээлгэн өгөх цаг хугацаанд байна. Coding Agent-ээр илгээх Tool-ийг засуулж, өмнөх яриа дуусмагц хураангуйг хэрэглэгчид хүргэдэг болгож болно. Тэгвэл дараагийн удаа байгууллага эргэн залгахад хэрэглэгчийн гарт асуудлын бүх учир шалтгаан бэлэн байна.

## Хоёр үүл {.unnumbered}

1900 онд Кельвин дулаан ба гэрлийн динамик онолын өмнө тулгарсан бэрхшээлийг «хоёр үүл» гэж нэрлэсэн бөгөөд эдгээр нь эфирийн хөдөлгөөн болон энергийн тэгш хуваарилалттай холбоотой байв.[^kelvin] Энэ зүйрлэлийг ашиглавал зохиогч Agent-ийн хөгжилд мөн хоёр үүл харж байна: бодит цагийн харилцан үйлчлэл, мөн харилцан үйлчлэлээс тасралтгүй суралцах чадвар.

**Эхний үүл бол Agent байнга өөрчлөгдөж буй орчныг хэрхэн гүйцэж мөрдөх вэ гэдэг асуудал.** Ээлжилсэн ярианд та нэг өгүүлбэр хэлж дуусахад туслах бодож байгаад хариулна. Гэвч та үгээ хэлмэгцээ засахыг хүсэж болох бөгөөд туслах мэдээлэл хайж байх хооронд хуудас шинэчлэгдсэн байж ч болно. Хэн ч юу ч хэлээгүй байхад шинэ имэйл ирсээр байна. Зохиогчийн хүсэн хүлээж буй Agent нь «амьд» мэдрэмж төрүүлэх ёстой: сонсож байхдаа бодож, ярьж байхдаа бодож, хэрэглэгч үгээ дуусгаагүй байхад төлөвлөж эхэлдэг, хэрэглэгчийн тавьсан зорилгод тулгуурлан «энэ имэйлийг одоо шийдэх хэрэгтэй» гэдгийг өөрөө анзаардаг байх.

Зохиогчийн бодлоор хэрэглэгчийн үгийг хэр хурдан хүлээж авах, асуудлыг хэр нарийн бодож боловсруулах хоёр нь тус тусад нь сайжруулж болох хоёр өөр асуудал. Хэрэглэгч «Үүнээс эрт нислэг байна уу?» гэж асуухад туслах шууд хариу өгч болох ч нислэг болон буцаах, солих нөхцөлийг нарийн шалгахад цаг хэрэгтэй.

Нэг зам нь **хурдан ба удаан замыг архитектурын түвшинд салгах** явдал. Ар тал нислэг хайсаар байтал хэрэглэгч гэнэт «Би үдээс өмнө хүрэх ёстой» гэж нэмж хэллээ. Урд тал энэ үгийг сонсож, цаг алдалгүй хариу өгөөд, шинэ ирэх цагийг ар талд дамжуулах ёстой. Ар тал хайлтаа үргэлжлүүлж ч болно, утгаа алдсан хайлтыг цуцалж ч болно. Зохиогч ийм хуваарилалтыг илүүд үздэг: урд тал хэзээ хариулах, хэзээ зогсоод сонсохыг шийднэ; ар тал хайлт ба дүгнэлт хийхэд цаг зарцуулна. Шинэ нислэг олдмогц ар тал үр дүнг урд талд илгээж, яриаг хөтөлж буй урд тал хэрхэн хариулахаа шийднэ.

Нөгөө зам нь **Model-ийн inference-ийг хурдасгах** явдал. Үүсгэх хурд өсөхөд ижил хэмжээний бодолт богино хугацаанд дуусна. Ижил хэдхэн секунд хүлээх хугацаанд туслах тасалбар солих олон хувилбарыг бодож, аль нь үдээс өмнө хүргэхийг харьцуулах боломжтой болно. Xiaomi MiMo-ийн тайланд дурдсанаар FP4 квантчлал, DFlash таамаглан декодлох арга, TileRT inference системийг хамтад нь оновчлосноор ерөнхий зориулалтын 8 GPU бүхий нэг зангилаан дээр нэг триллион параметртэй Model-ийн үүсгэх хурдыг секундэд 1000-аас дээш token-д хүргэжээ.[^mimo] Харин Taalas HC1 нь тухайн Model-д зориулсан чип ашиглан Llama 3.1 8B дээр нэг хэрэглэгчид секундэд ойролцоогоор 17000 token үүсгэх хурдыг мэдээлсэн.[^taalas] Эдгээр хоёр жишээ ерөнхий зориулалтын тоног төхөөрөмж дээрх системийн оновчлол, мөн тодорхой Model-д зориулсан тоног төхөөрөмжийн мэргэшлийг тус тус харуулж байна.

Үүсгэх хурд хангалттай өндөр болоход ээлж хүлээх хугацаа мэдэгдэхүйц богиносож, харилцан үйлчлэл бодит цагийн ярианд улам ойртоно. Agent орчны өөрчлөлтийг гүйцэж мөрдөхийн тулд оролтыг тасралтгүй хүлээн авах, үйл явдлыг цаг тухайд нь хуваарилах, шийдвэр өөрчлөгдөхөд хуучин үйлдлийг цуцалж төлөвийг уялдуулах шаардлагатай хэвээр байна.

**Хоёр дахь үүл бол Agent хүн шиг орчинтойгоо харилцах явцын амжилт, бүтэлгүйтлээс туршлага тасралтгүй хуримтлуулах вэ гэдэг асуудал.** Model сургалтын явцад өргөн мэдлэг эзэмшиж болох ч ажилд орсныхоо дараа шинэ хэрэглэгч, шинэ бизнесийг таньж мэдэх шаардлагатай хэвээр байна. Даалгавар бүр шинэ туршлага авчирна: аль алхам үр дүнтэй байсан, аль Tool амархан алдаа гаргадаг, хэрэглэгч ямар илэрхийллийг хүлээн авсан гэх мэт. Даалгавар дуусахад эдгээр туршлага Context-той хамт алга болбол дараагийн удаа ижил алдаагаа давтаж болно. Эдгээр туршлагыг хэрхэн хадгалж, Agent-ийг хэрэглэх тусам улам сайжруулах вэ гэдэг нь Бүлэг 3 болон Бүлэг 9-ийг туултал хэлэлцсэн асуудал.

Тасралтгүй суралцах нь хэр чухал вэ гэдэг нь Model-ийн эзэмших ёстой мэдлэгийг бид хэрхэн харахаас хамаарна. Зохиогч хоёр хандлагыг «жижиг ертөнц», «том ертөнц» гэж нэрлэдэг.

**«Жижиг ертөнцийн таамаглал»** нь ерөнхий мэдлэгийг хангалттай том Model шингээж чадна гэж үздэг. Энэ чиглэлээр явбал хэдэн триллион параметртэй Model туйлын өргөн мэдлэг, аргачлалыг багтааж чадах бөгөөд гол саад нь хангалттай хэмжээний өндөр чанартай сургалтын өгөгдөл олж авах эсэх болно. Программчлал үүний сургамжтай жишээ: асар их нээлттэй код, баримт бичиг, ажиллуулж болох тестүүд нь Model суралцах болон үр дүнг шалгах нөхцөлийг бүрдүүлсэн. Салбар хоорондын хамтын ажиллагаа мэргэжлийн даалгавар ба туршлагыг сургалтад оруулж, илүү олон салбарын чадварыг суурь Model-д шингээж болно.

**«Том ертөнцийн таамаглал»** нь тодорхой нөхцөл байдлын олон янз байдал, өөрчлөлтийг онцолдог. Нэг компанийн код бичих стандарт, нэг хэрэглэгчийн дуртай PPT хэв маяг, нэг үйлчлүүлэгчийн харилцааны зуршил зэргийг бодит харилцан үйлчлэлийн явцад л мэдэж авна. Ийм мэдлэг хүн бүрээр эрс ялгаатай бөгөөд байгууллагын үйл явц, хэрэглэгчийн сонголт өөрчлөгдөхийн хэрээр байнга шинэчлэгддэг тул нэг удаагийн урьдчилсан сургалтаар урьдаас хамруулах боломж бага. Иймээс систем санах ой, мэдлэг, ажлын аргачлалаа тасралтгүй хөтөлж, эргэх холбоонд тулгуурлан зан төлөвөө тохируулах ёстой. Туршлагыг эхлээд мэдлэгийн баримт бичиг, заавар эсвэл программ болгон бичиж, шүүж баталгаажуулсны дараа Model-ийн параметрийг шинэчлэхэд ч ашиглаж болно.

Даалгавар рекурсив өөрийгөө сайжруулалт (RSI) болон AI for Science хүртэл өргөжихөд Agent хүн төрөлхтний хараахан шийдээгүй асуудлуудыг судлах шаардлагатай болно. Нэг таамаглал туршилтад тэсч үлдэхгүй бол Agent аль алхамд алдаа гарсныг тодорхой хэлж, үүнд үндэслэн таамаглалаа засаад дахин туршилт хийх чадвартай байх ёстой. Бэлэн хариултгүй газар хүрэхэд дараагийн удаа юуг турших вэ гэдгээ ч өмнөх үр дүнгээсээ суралцах хэрэгтэй. **Зохиогчийн бодлоор суралцах ба дасан зохицох чадвар эцэстээ Model-ийн хамгийн хүчтэй чадвар болно.**

Ойрын хэдэн жилийн хувийн Agent руу харвал шинэ бүтээгдэхүүн яг аль алхмыг урагшлуулсныг хэрхэн дүгнэх вэ? Зохиогч 2026 оны 11 дүгээр сард Портод тавьсан илтгэлдээ энэ асуултыг таван чиглэлд задалсан. Харилцан үйлчлэлийн Model, хурдан inference, бодит ертөнцөд хүрдэг Tools аль хэдийн туршиж үзэх эсвэл хэмжиж болох хэрэгжүүлэлттэй болсон. Харин хүн болон олон Agent-д зориулсан уугуул үйлдлийн систем, мөн урт хугацааны хэрэглээнд дүгнэлт хийж сурахын зэрэгцээ хуучин чадвараа хадгалдаг тасралтгүй суралцах систем нь зохиогчийн бодлоор шинэ дизайн шаардсаар байна.[^porto-jarvis]

2026 оны 9 дүгээр сард Meta хувийн туслах Muse-ийг танилцуулж, АНУ-ын хэрэглэгчдэд нээж эхэлсэн. Бүтээгдэхүүний тайлбараас үзвэл хэрэглэгч Muse-д тодорхой барааны үнэ хэзээ буурахыг ажиглахыг даалгаад аппликейшнаа хааж болно. Тусгай виртуал машин дахь хөтөч хэрэглэгчийн өмнөөс үнийг ажигласаар байж, өөрчлөлт гармагц мэдэгдэнэ. Хэрэв түүгээр худалдан авалт хийлгэхийг хүсвэл хэрэглэгч эхлээд ямар захиалга өгөх гэж байгааг нь хараад, авах эсэхээ шийдэж болно. Ийм туслах хүнийг дэлгэцийн өмнө суугаад хүлээх ажлаас аль хэдийн чөлөөлж чадна. Хэрэглэгч дараа нь төсвөө бууруулсан бол туслах дараагийн удаа үнэ буурахыг хараад урьдын адил худалдан авч болох уу? Хүний өмнөөс үнэ ажиглахаас хүний өмнөөс шийдвэр гаргах хүртэлх зайд хэрэглэгчийн сонголт ба эрх олголт оршино.[^afterword-muse]

Аялалд ч мөн ижил асуудал гарна. Утсан дээрээ хүссэн үедээ дуудаж болдог нь **нэвтрэх цэгийн** асуудлыг шийднэ. Энэ удаа та хүүхэдтэйгээ явж байгаа, дамжин нисэх хугацаа хэт давчуу байж болохгүйг санаж байгаа нь **Context**-ийг илэрхийлнэ. Тохирох нислэгийг олж чадах ч тасалбар бичүүлж чадах эсэх нь таны ямар **эрх олголт** өгсөн, агаарын тээврийн компани ямар захиалгын аргыг хүлээн зөвшөөрдгөөс хамаарна.

[^afterword-muse]: Meta, Muse-ийн нийтлэлийн тайлбар болон хөтөч ашиглах заавар.

[^porto-jarvis]: Bojie Li, 2026 оны 11 дүгээр сарын 10-нд Портод тавьсан илтгэл «The Road to JARVIS: Where the Moats Are for Personal Agents».

## Model ба Agent-ийн хамтын хувьсал {.unnumbered}

Harness доторх давхар давхар логикийг эргэн харъя: олон түвшний Context шахалт, бүтэлгүйтлийн дараах дахин оролдлого, үр дүнгийн баталгаажуулалт, хандалтын хяналт. Давхарга бүр бодит даалгаварт тулгарсан бэрхшээлийг тэмдэглэн үлдээсэн байдаг. Мэдээлэл оролтын багтаамжаас хэтэрвэл шахах хэрэгтэй; Tool алдаатай хариу буцаавал дахин оролдож болох эсэхийг шийдэх хэрэгтэй; Model дуусгах нөхцөлийг орхигдуулбал бие даан баталгаажуулах хэрэгтэй; үйлдэл тусгай эрх шаардвал эрхийн шалгалтыг хэрэгжүүлэх хэрэгтэй. Эдгээр инженерийн туршлага нь Model болон системийг дараа нь юугаар сайжруулахыг ч бидэнд хэлж өгдөг.

Хувийн туслахын чадвар нь байгууллага ямар үйлчилгээний сувгийг нээлттэй болгосноос ч хамаарна. Нэг удаагийн төлбөрийн хэлэлцээрийг төсөөлье: хэрэглэгч туслахад үнийн мэдээлэл лавлах эрх олгосон бөгөөд байгууллага түүнд хөнгөлөлтийн нөхцөлөө тайлбарлаж болох ч өөрчлөлтийг дансны эзэн өөрөө утсаар баталгаажуулахыг шаардана. Туслах эхлээд хэмжээ, хүчин төгөлдөр болох хугацаа, нэмэлт нөхцөлийг тодруулж, хэрэглэгч өөрөө ярих шаардлагатай болоход юуг тохиролцсон, одоо алийг нь баталгаажуулах ёстойг товч тайлбарлана. Ингэснээр сүүлийн алхмыг хүн өөрөө хийх ёстой байсан ч хэрэглэгч өмнөх лавлагаа, хүлээлт, давтан тайлбарлах ажлаас чөлөөлөгдөнө. Хэрэв байгууллага зөвхөн эзэмшигчтэй нь шууд харилцдаг бол туслах материалыг урьдчилан цэгцэлж, асуултуудыг жагсааж, хэрэглэгч асуудлаа нэг дор тодорхой хэлэхэд нь тусалж чадна.

Хэрэглэгч байгууллагын эргэн залгасан дуудлагыг авсны дараа туслах асуудлыг хэрхэн буцааж хүлээж авах вэ? Хэрэглэгч «Ажилтан дараагийн тооцооны хугацаанаас эхлэн хөнгөлнө гэж амласан» гэж дамжуулсан гэж бодъё. Туслах энэ хариултыг тэмдэглэж аваад, төлбөрийн баримт гарахад дүнг тулгаж шалгана. Үүрэн холбооны оператор төлбөрийн мэдэгдэл илгээдэг бол мэдэгдэл ирэхэд шалгахад хангалттай; зөвхөн өөрөө лавлах боломжтой бол туслах тооцооны хугацаанд тааруулан нэг сануулга тавьж, тухайн үед явцыг шалгана. Хэрэглэгч өөрөө оролцох шаардлагатай нь зөвхөн утсаар баталгаажуулах хэсэг бөгөөд цаашдын хяналтыг туслахад даатгаж болно.

Энэ даалгавар сайжруулах ёстой нэг нарийн зүйлийг ч үлдээж болно: хэрэглэгч хөнгөлөлт аль өдрөөс хүчин төгөлдөр болохыг дахин асуух хэрэгтэй болсон. Эхлээд туслах ба ажилтны хоорондох ярианы бичлэгийг үзнэ. Ажилтан зөвхөн «хөнгөлж болно» гэж хэлсэн бол туслах ярианы явцад хүчин төгөлдөр болох огноог тодруулж асуудаг болгох хэрэгтэй. Харин ажилтан огноог тодорхой хэлсэн атал туслах хураангуйдаа удаа дараа орхигдуулсан бол л өөр төрлийн сургалтын материал бий болно: огноо агуулсан эх ярианы хэсгийг шалгаж баталгаажуулсан хураангуйтай хослуулж жишээ болгоно.

Нэгдүгээр бүлэгт нэг асуулт тавьсан: **Model эцэстээ Harness-ийг залгих уу?** Зохиогчийн дүгнэлт: **давхарга давхаргаар нь залгина, харин Harness чадварын шинэ хил рүү тасралтгүй шилжинэ.** Өмнө нь гадны зохион байгуулалтаар хэрэгжүүлдэг байсан чадварыг Model тогтвортой эзэмших бүрд харгалзах зохион байгуулалтыг хялбарчилж болно. Бүлэг 6-ийн харилцан үйлчлэлийн Model үүний нэг жишээ: Model ээлж тодорхойлох, яриа таслах, дуугаар хариулахыг шууд сурсны дараа систем харгалзах эвристик дүрмүүдээ багасгаж болох бөгөөд аудио дамжуулалт, гүйцэтгэлийг цуцлах, төлөвийн удирдлагыг ажиллах орчин үргэлжлүүлэн хариуцна.

Зарим үүрэг Model-оос гадна үлдэх ёстой. Бизнесийн эрхийг итгэмжлэгдсэн таних тэмдэг ба эрх олгох дүрмүүд тодорхойлно; төсвийг ажиллах орчин болон үйлчилгээний квот хэрэгжүүлнэ; гадаад үйлдлийг Tools болон орчин гүйцэтгэнэ.

Тодорхой чадварыг ирээдүйд Model-д сургаж болох байсан ч бизнес дараагийн сургалт, байршуулалтыг хүлээж чадахгүй байж болно. Нэг компани өнөөдөр батлах журмаа өөрчилсөн бол туслах өнөөдрөөс л шинэ журмаар ажиллах ёстой. Баг эхлээд Harness-ийг засаж, давтагдан тулгардаг хүнд асуудлуудыг дараагийн сургалтад үлдээж болно. Зохиогч «Гашуун сургамж»-ийг (The Bitter Lesson) ийнхүү ойлгодог: ерөнхий хайлт ба суралцах аргууд давуу талаа тасралтгүй өргөжүүлсээр байх бөгөөд тэдгээр аажмаар боловсорч гүйцэх явцад Harness өнөөгийн чадварыг бодит даалгаварт холбож, дараагийн суралцахад эргэх холбоо үлдээнэ.

Model ба бүтээгдэхүүнийг нэг баг тасралтгүй сайжруулж байх үед энэ эргэх холбооны гинж илүү нягт болж чадна. Anthropic-ийн Claude Code-ийг жишээ болговол Model-ийн чадвар Tool болон Context-ийн дизайнд нөлөөлж, бодит хэрэглээнд илэрсэн асуудлууд дараагийн Model ба системийн сайжруулалтад чиглэл өгдөг. Нэгдүгээр бүлэгт танилцуулсан LangChain-ийн жишээ системийн инженерчлэлийн шууд үр ашгийг харуулсан: GPT-5.2-Codex-ийг тогтмол ашиглаж, зөвхөн Harness-ийг тохируулснаар Terminal Bench 2.0-ийн оноо 52.8%-иас 66.5% болж өссөн. Дуусгахаас өмнөх өөрийгөө шалгах, давтагдсан үйлдлийг илрүүлэх, төсвийн хуваарилалт бүгд бүтэлгүйтлийн явцыг тодорхой задлан шинжилсний үр дүн юм.

Зохиогчийн бодлоор **бодит бизнес, эргэх холбооны өгөгдөл, Model-ийн шинэчлэл гурав харилцан бие биеэ түлхэх энэ эргэлт бол энэ эриний хамгийн гүн хамгаалалтын шуудуу юм.** Гурав нь хэдий чинээ нягт уялдана, баг бодит асуудлаас бусдын хуулбарлахад хэцүү хуримтлалыг төдий чинээ бий болгоно. Model-ийн багийн хувьд үнэ цэнтэй даалгавар ба эргэх холбоог сургалт болон үнэлгээнд аль болох хурдан оруулж, энэ эргэлтийг жинхэнээсээ ажиллуулах хэрэгтэй.

Аппликейшний багт зохиогчийн зөвлөмж: **Harness-ийг богино хугацааны хамгийн хурц техникийн хөшүүрэг болгон ашиглаж, түүгээр цаг хожиж, урт хугацааны давуу талаа хуримтлуул.** Өмнө нь инженерийн аргаар нөхдөг байсан чадварыг Model эзэмшсэний дараа холбогдох хэрэгжүүлэлтийг хуулбарлах улам хялбар болно. Харин өвөрмөц өгөгдөл, тогтвортой суваг, хэрэглэгчийн итгэл, сүлжээний нөлөө, мөн хүн ба Agent хамтдаа оролцдог физик ертөнцийн нөхцөлүүдийг урт хугацаанд бүтээн байгуулах шаардлагатай. Бүтээгдэхүүнээ сайн хийж, хэрэглэгчдээ сайн үйлчлэх нь энэ хугацааг ашиглан өөрийн хамгаалалтын хэрмийг босгож буй хэрэг юм.

Model, API, бүтээгдэхүүн өөрчлөгдсөөр байх ч «одоо ямар мэдээлэл хэрэгтэй вэ», «ямар үйлдэл хийхийг зөвшөөрөх вэ», «үр дүнг хэрхэн баталгаажуулах вэ» гэсэн асуултууд системийн дизайныг туултал үргэлжилсээр байна. Эдгээр гурван асуултыг ойлговол шинэ чадварыг хаана байрлуулах нь зүйтэй, аль бүрэлдэхүүнийг хялбарчилж болох, аль хэсгийг бэхжүүлэх шаардлагатайг дүгнэж чадна.

Зохиогч энэ ном танд ийм дүгнэх чадвар төлөвшүүлэхэд тусална гэж найдаж байна: тодорхой даалгавраас эхэлж, Agent-ийн бүтцийг ойлгож, ажилладаг систем бүтээгээд, эргэх холбоонд тулгуурлан тасралтгүй сайжруулах. Номын эх бичвэр, зураг, дагалдах туршилтын код бүгд нээлттэй эхтэй тул туршилтуудыг өөрийн гараар ажиллуулж, шинэ шийдлийг туршиж, олж мэдсэнээ issue болон PR-ээр хуваалцахыг урьж байна. Agent код бичих замаар Tool бүтээж, чадвараа өргөжүүлж чаддаг нь бидэнд санаагаа хэрэгжүүлэх илүү олон боломжийг олгож байна.
