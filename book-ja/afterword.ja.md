# あとがき：Agent = LLM + コンテキスト + ツール に立ち返る {.unnumbered}

本書は一つの公式から始まりました。**Agent = LLM + コンテキスト + ツール**です。全 10 章を読み終えたいま、この 3 つの要素を実際に動くシステムの中に位置づけられるようになりました。モデルはタスクを理解して意思決定を行い、コンテキストはその時点で必要な情報を提供し、ツールは観測を取得して行動を実行します。

第 1 章では、この機能分解で全体像をつかんだうえで、**Agent = Model + Harness** という式で本番実装における役割分担を説明しました。モデルは意思決定を担い、Harness はコンテキスト、ツールインターフェース、実行ループ、状態を組織し、制約・検証・是正を実施します。

- **Agent を構築する（第 2〜6 章）。** コンテキストエンジニアリングは一回の意思決定に必要な情報を組み立て、メモリと知識ベースはセッションをまたいだ保存と検索を支えます。ツールは観測と行動のインターフェースを提供し、コード生成によって Agent は新しいツールやシステムを自ら書けるようになります。インタラクションの章では、これらのインターフェースを音声、GUI、物理世界へと広げ、イベントを継続的に受け取りながら動く方式についても論じました。
- **評価と進化（第 7〜9 章）。** 評価はシステムの性能を比較し、失敗の原因を見つける助けになります。ポストトレーニングはデータと環境を通じてモデルのパラメータを更新します。継続的進化は運用中の経験を知識・指示・プログラム・パラメータの更新へと変え、その変化を検証とリリースのプロセスで管理します。
- **協調（第 10 章）。** マルチ Agent システムはメンバーごとに異なるコンテキスト、ツール、責任を割り当て、通信と相互チェックを通じて共同でタスクを完了させます。メンバーが増えれば、共有状態、タスク間の依存関係、リソース、意見の対立も管理しなければなりません。

「はじめに」で取り上げた請求書の話に戻りましょう。担当者が「減額できます」と言ったなら、その約束は通話記録から確認できます。次の請求書が発行されれば、実際に減額されたかを照合するもう一つの証拠が手に入ります。折り返しの電話がユーザーのスマートフォンに鳴ったとき、アシスタントが事前に送っておいた案件番号と交渉の要約が、ユーザーが手続きを引き継ぐための拠り所になります。

もしユーザーが電話に出たあと、一から説明し直さなければならなかったとしたら、どこを直すべきでしょうか。まず前回の通話の要約を読みます。担当者が約束した減額の金額すら記録されていなければ、交渉結果を記録する手順を改善する必要があります。要約はきちんと書けているのに、届いたのが折り返しの電話が終わったあとだったなら、問題は引き継ぎのタイミングにあります。その場合は Coding Agent に送信ツールを修正させ、前回の通話が終わった時点で要約をユーザーに届けるようにできます。そうすれば、次に事業者から折り返しがあったとき、ユーザーの手元にはそれまでの経緯がそろっています。

## 二つの暗雲 {.unnumbered}

1900 年、ケルビンは熱と光の動力学理論が直面する難題を「二つの暗雲」と表現しました。そこにはエーテルの運動とエネルギー等分配の問題が含まれていました。[^kelvin] この比喩を借りれば、筆者には Agent の発展にも二つの暗雲が見えます。リアルタイムのインタラクションと、インタラクションからの継続的な学習です。

**第一の暗雲は、刻々と変わる環境に Agent がどう追いつくかです。** ターン制の対話では、ユーザーが一言話し終えるのを待って、アシスタントは考えてから答えます。しかし、ユーザーは言い終えた途端に言い直したくなるかもしれませんし、アシスタントが調べ物をしている間にページが更新されているかもしれません。誰も口を開かなくても、新しいメールは届きます。筆者が期待する Agent は「生きている」と感じられるものです。聞きながら考え、話しながら考え、ユーザーの話が途中でも計画を立て始め、ユーザーが設定した目標に基づいて「このメールはもう処理すべきだ」と自ら気づけるような Agent です。

筆者の見るところ、ユーザーの話にどれだけ素早く応じられるかと、物事をどれだけ周到に考え抜けるかは、それぞれ別々に改善できる問題です。ユーザーが「もっと早い便はありますか」と尋ねたら、アシスタントはすぐに応答できます。しかし、便の空き状況や変更・払い戻しの条件まで確かめるには時間がかかります。

一つ目の道は、**アーキテクチャ上で速い経路と遅い経路を分離すること**です。バックエンドがまだ便を探している最中に、ユーザーが「正午までには着かないといけないんです」と付け加えたとします。フロントエンドはこの一言を聞き取ってすぐに応答し、新しい到着時刻の条件をバックエンドに渡さなければなりません。バックエンドはそのまま検索を続けることも、意味を失った検索を取り消すこともできます。筆者が好むのは次のような分担です。フロントエンドはいつ応答し、いつ黙って聞くかを判断し、バックエンドは時間をかけて検索と推論を行います。新しい便が見つかったら、バックエンドは結果をフロントエンドに送り、会話を続けているフロントエンドがどう答えるかを決めます。

もう一つの道は、**モデルの推論を速くすること**です。生成速度が上がれば、同じ推論にかかる時間を短縮できます。同じ数秒を待つ間に、アシスタントは変更案をより多く検討し、どれなら正午までに到着できるかを比べられるようになります。小米（Xiaomi）MiMo は、FP4 量子化、DFlash 投機的デコーディング、TileRT 推論システムを協調して最適化することで、汎用の 8 GPU ノード 1 台で 1 兆パラメータのモデルの生成速度 1000 token/s 超を達成したと報告しています。[^mimo] 一方、Taalas HC1 はモデル専用チップを採用し、Llama 3.1 8B でユーザー 1 人あたり約 17000 token/s の生成速度を報告しています。[^taalas] 前者は汎用ハードウェア上でのシステム最適化の、後者は特定モデルに向けたハードウェア専用化の例です。

生成速度が十分に速くなれば、ターンごとの待ち時間は大きく縮まり、インタラクションはリアルタイムの会話に近づきます。それでも、Agent が環境の変化に追いつくには、入力を継続的に受け取り、イベントを適時にスケジューリングし、意思決定が変わったときには古い操作を取り消して状態を同期する仕組みも必要です。

**第二の暗雲は、Agent が人間のように、環境とのインタラクションにおける成功と失敗から経験を継続的に蓄積するにはどうすればよいかです。** モデルは訓練時に幅広い知識を学べますが、現場に出てからは新しいユーザーや新しい業務を理解していく必要があります。タスクのたびに新しい経験が生まれます。どの手順が有効だったか、どのツールが誤りを起こしやすいか、ユーザーがどんな言い方を受け入れたか。タスクが終わるとこうした経験がコンテキストとともに失われてしまうなら、次回も同じ過ちを繰り返しかねません。これらの経験をどう保存し、使うほどに Agent を良くしていくかは、第 3 章と第 9 章を通じて論じてきた問題です。

継続的な学習がどれほど重要かは、モデルが身につけるべき知識をどう捉えるかによって変わります。筆者はこれを「小さな世界」と「大きな世界」という二つの考え方にまとめています。

**「小さな世界仮説」**は、汎用的な知識は十分に大きなモデルに吸収できると考えます。この方向に進めば、数兆パラメータのモデルがきわめて幅広い知識と手法を収められる可能性があり、主なボトルネックは質の高い訓練データを十分に得られるかどうかになります。プログラミングは示唆に富む例です。大量の公開コード、ドキュメント、実行可能なテストが、モデルの学習と結果の検証を可能にしてきました。業界との協力によって専門的なタスクや経験を訓練に取り込めば、より多くの分野の能力を基盤モデルに取り入れることができます。

**「大きな世界仮説」**は、具体的な状況の豊かさと変化を重視します。ある会社のコーディング規約、あるユーザーが好む PPT のスタイル、ある顧客のコミュニケーションの癖は、いずれも実際のインタラクションの中で理解していくしかありません。こうした知識は個別性が強いうえに、組織のプロセスやユーザーの好みの変化に合わせて絶えず更新されるため、一度の事前学習で前もってカバーすることは困難です。そのためシステムは、メモリ、知識、操作手順を継続的に維持し、フィードバックに応じて振る舞いを調整する必要があります。経験はまず知識ドキュメント、指示、プログラムとして書き出し、選別と検証を経たうえで、モデルパラメータの更新に使うこともできます。

タスクが再帰的自己改善（RSI）や AI for Science にまで広がると、Agent は人類がまだ解いていない問題を探究しなければなりません。ある仮説が実験に耐えられなかったとき、Agent はどのステップに問題があったかを説明し、それに基づいて仮説を修正し、もう一度実験できなければなりません。出来合いの答えがない領域に踏み込めば、次に何を試すべきかさえ、前回の結果から学ぶしかありません。**筆者は、学習と適応こそが最終的にモデルの最も強い能力になると考えています。**

今後数年の個人向け Agent に目を向けたとき、新しい製品が実際にどの段階を前に進めたのかは、どう判断すればよいでしょうか。筆者は 2026 年 11 月のポルトでの講演で、この問いを五つの方向に分解しました。インタラクションモデル、高速な推論、現実世界に届くツールには、すでに体験したり測定したりできる実装があります。一方、人間と複数の Agent のためのネイティブなオペレーティングシステム、そして長期の利用を通じて判断を学びながら既存の能力も保ち続けられる継続学習システムには、筆者の見るところ、まだ新しい設計が必要です。[^porto-jarvis]

2026 年 9 月、Meta は個人向けアシスタント Muse を発表し、米国のユーザー向けに提供を始めました。製品説明によれば、ユーザーは Muse にある商品の値下がりを見張るよう頼み、そのままアプリを閉じることができます。専用の仮想マシン上のブラウザが引き続きユーザーに代わって価格を見張り、変化があれば知らせてくれます。代わりに購入してほしい場合は、Muse が出そうとしている注文を先に確認してから、買うかどうかを決められます。このようなアシスタントは、画面の前で待ち続ける作業から人をすでに解放しつつあります。では、ユーザーがあとで予算を下げていたら、アシスタントは次に値下がりを見つけたとき、以前と同じように購入してよいのでしょうか。価格を見張ることから代わりに判断することまでの間には、ユーザーの好みと権限委任という隔たりがあります。[^afterword-muse]

旅行でも同じ問題に突き当たります。スマートフォンからいつでも気軽に呼び出せるかは、**入口**の問題です。今回は子ども連れであること、乗り継ぎ時間に余裕が必要なことを覚えているかは、**コンテキスト**の問題です。条件に合う便を見つけられても、発券まで進めるかどうかは、ユーザーがどんな**権限**を与えたか、そして航空会社がどの手続き方法を受け付けるかにかかっています。

[^afterword-muse]: Meta、Muse のリリースノートおよびブラウザ利用に関する説明。

[^porto-jarvis]: 李博杰、2026 年 11 月 10 日ポルトでの講演「The Road to JARVIS: Where the Moats Are for Personal Agents」。

## モデルと Agent の共進化 {.unnumbered}

Harness の中に幾重にも積み重なったロジック、すなわち多段階のコンテキスト圧縮、失敗時のリトライ、結果の検証、アクセス制御を振り返ると、その一層一層が実際のタスクで遭遇した困難を記録しています。情報が入力容量を超えれば圧縮が必要になり、ツールが異常を返せばリトライできるかを判断しなければならず、モデルが完了条件を見落とせば独立した検証が必要になり、操作に特定の権限が要るなら認可チェックを確実に行わなければなりません。こうしたエンジニアリングの経験は、モデルとシステムが次に何を改善すべきかも教えてくれます。

パーソナルアシスタントの能力は、事業者がどの手続き方法を開放しているかにも左右されます。請求額の交渉を例に考えてみましょう。ユーザーはアシスタントに見積もりの問い合わせを任せ、事業者はアシスタントに割引条件を説明できるものの、契約変更については契約者本人が電話で確認することを求めているとします。アシスタントは先に金額、適用開始時期、付帯条件を詰めておき、本人が話す必要が生じた段階で、何が合意済みで、いま何を確認すればよいのかをユーザーに手短に伝えられます。こうすれば、最後の一歩は人が行わなければならないとしても、ユーザーはそれまでの問い合わせ、待ち時間、繰り返しの説明から解放されます。事業者が本人による手続きしか受け付けない場合でも、アシスタントは資料を整理し、確認すべき点を書き出して、ユーザーが一度で用件を伝えきれるよう手助けできます。

ユーザーが事業者からの折り返し電話に出たあと、アシスタントはどうやって案件を引き取ればよいでしょうか。ユーザーが「担当者が次の請求期間から減額すると約束してくれた」と伝えてきたとします。アシスタントはこの回答を記録し、請求書が出たら金額を照合できます。通信事業者が請求確定の通知を提供しているなら、通知を受け取ってから確認すれば済みます。こちらから照会するしかない場合は、請求期間に合わせてリマインダーを一つ設定し、その時点で進捗を確認すればよいのです。本人が出る必要があるのは電話での確認だけで、その後の追跡はアシスタントに任せられます。

この依頼からは、改善に値する細かな点が見つかることもあります。たとえば、減額がいつから適用されるのかをユーザーが改めて尋ねなければならなかった場合です。まず、アシスタントと担当者の通話記録を確認します。担当者が「減額できます」としか言っていなかったのなら、通話中に適用開始日を確認するようアシスタントを改めるべきです。担当者は日付をはっきり伝えていたのに、アシスタントが要約で繰り返し書き漏らしていたのなら、そこで初めて別種の訓練素材が得られます。日付を含む元の発言と、検証済みの要約とを組にした例です。

第 1 章では一つの問いを提起しました。**モデルは最終的に Harness を食べ尽くすのか。** 筆者の判断はこうです。**一層ずつ食べていく。そして Harness は絶えず新しい能力の最前線へと移っていく。** かつて外部のオーケストレーションで実現していた能力をモデルが一つ安定して身につけるたびに、対応するオーケストレーションは簡素化できます。第 6 章のインタラクションモデルはその一例です。モデルがターンの判断、割り込み、音声応答を直接学習すれば、システムは対応するヒューリスティックなルールを減らせます。一方、音声の伝送、実行の取り消し、状態管理は引き続きランタイムが担います。

一方で、モデルの外に残すべき責務もあります。業務上の権限は信頼できる身元と認可ルールによって決まり、予算はランタイムとサービスのクォータによって執行され、外部への操作はツールと環境によって完了します。

ある能力がいずれモデルに学習されうるとしても、業務が次の訓練とデプロイまで待てるとは限りません。企業が今日承認ルールを変えたなら、アシスタントは今日から新しいルールに従って動かなければなりません。チームはまず Harness を修正し、繰り返し直面する難題は次の訓練に回すことができます。これは筆者なりの『苦い教訓』の理解の仕方でもあります。汎用的な探索と学習の手法は優位を広げ続けますが、それらが徐々に成熟していく過程で、Harness は現在の能力を実際のタスクにつなぎ、次の学習のためのフィードバックを残していくのです。

モデルと製品を同じチームが継続的に磨き上げている場合、このフィードバックの連鎖はより緊密になります。Anthropic の Claude Code を例にとれば、モデルの能力がツールとコンテキストの設計に影響を与え、実際の利用で見つかった問題が今後のモデルとシステムの改善に方向性を与えます。第 1 章で紹介した LangChain の事例は、システムエンジニアリングの直接的な効果を示しています。GPT-5.2-Codex に固定したまま Harness を調整しただけで、Terminal Bench 2.0 のスコアは 52.8% から 66.5% に向上しました。完了前のセルフチェック、繰り返し操作の検出、予算の配分は、いずれも失敗の過程を具体的に分析した結果から生まれたものです。

筆者は、**実際の業務、フィードバックデータ、モデルのイテレーションが互いを推し進めるこの循環こそが、この時代で最も深い堀（モート）だ**と考えています。三者が緊密に結びつくほど、チームは実際の問題から他者には模倣しがたい蓄積を築けます。モデルを作るチームにとっては、価値あるタスクとフィードバックをできるだけ早く訓練と評価に取り込み、この循環を実際に回すことが求められます。

アプリケーションを作るチームへの筆者の助言は、**Harness を短期的に最も鋭い技術的レバレッジとして使い、それで時間を稼いで長期的な優位を積み上げること**です。かつてエンジニアリングで補う必要があった能力をモデルが身につけるにつれて、関連する実装はますます模倣しやすくなります。一方、独自のデータ、安定したチャネル、ユーザーの信頼、ネットワーク効果、そして人間と Agent がともに関わる物理世界の場面は、長い時間をかけて育てる必要があります。製品を磨き、ユーザーにしっかりとサービスを提供することこそ、この時間を使って自らの防壁を築くことにほかなりません。

モデル、API、製品はこれからも変わり続けますが、「いまどんな情報が必要か」「どんな行動を許可するか」「結果をどう検証するか」という問いは、システム設計を貫き続けます。この三つの問いを理解していれば、新しい能力をどこに置くべきか、どのコンポーネントを簡素化でき、どの部分を補強すべきかを判断できます。

筆者は、本書がそうした判断力を養う助けになることを願っています。具体的なタスクから出発し、Agent の構造を理解し、実際に動くシステムを構築し、フィードバックに基づいて改善を続ける力です。本文、図版、付属の実験コードはすべてオープンソースとして公開しています。ぜひ実験を自分の手で動かし、新しい方法を試し、issue や PR で発見を共有してください。Agent はコードを通じてツールを生み出し、能力を広げることができます。それは私たちにとっても、アイデアを形にする手段が増えたことを意味します。
