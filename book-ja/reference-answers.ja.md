# 演習問題の解答例

参考解答は AI が生成し、人手で簡単に校閲したものです。

## 第一章 AI Agent 入門

**1. (★★) モデル、コンテキスト、ツールのうち一つだけを優先して改善できるとしたら、最も投資する価値のある箇所をどのように判断しますか。どのような評価結果が出たら、その選択を変えますか。**

> まず、タスクの完了に必要な情報をモデルが受け取れているかを確認します。この確認で漏れを直接見つけられ、局所的な修正もしやすくなります。次に失敗軌跡を分析します。業務上の事実、過去の決定、タスクの状態が欠けているならコンテキストを改善し、観測や実行のためのインターフェースが欠けているならツールを補います。十分な情報と適切なツールがそろっていてもモデルが推論をやり遂げられない場合に、はじめてより強力なモデルと比較します。同じタスクセットを使って一度に一項目ずつ調整し、完了率、エラーの種類、所要時間、コストを記録します。

**2. (★★★) 各ラウンドで追加されるメッセージ量がほぼ一定で、毎ラウンドそれまでの履歴全体をモデルに渡すとします。累積入力量がラウンド数に対しておおむね二次関数的に増えるのはなぜでしょうか。キャッシュ、圧縮、履歴の切り詰めは、それぞれどのコストを変えますか。**

> まずメッセージ履歴だけを数え、各ラウンドで 100 token ずつ増えるとします。最初の 3 ラウンドで送る量はそれぞれ 100、200、300 token です。3 回目のリクエストに含まれる履歴は 300 token にすぎませんが、3 回のリクエストの合計ではすでに 600 token を送っています。前者は 3 回目のリクエストから読み取れ、後者は 3 回分の使用量記録にある履歴入力を足し合わせて求めます。一般に、各ラウンドで $m$ token 増えるなら、第 $i$ ラウンドで送るのは約 $mi$ token、最初の $n$ ラウンドの累計は約 $mn(n+1)/2$ になります。これとは別に長さ $P$ の固定システムプロンプトがあり、毎ラウンド入力に含まれるなら、合計にさらに $nP$ が加わります。
>
> 引き続き上の例のメッセージ履歴だけを数えます。2 ラウンド目以降、サービスが前のラウンドの入力をすべて再利用できるとすると、2 ラウンド目では 100 token、3 ラウンド目では 200 token がキャッシュにヒットします。3 ラウンドを合計すると、入力 600 token のうち 300 token がキャッシュにヒットし、残りの 300 token は初めて処理されます。キャッシュが再利用したのは、その 300 token 分のプレフィックス計算です。
>
> 圧縮は履歴を短い要約に置き換えるもので、要約の呼び出しとキャッシュ再構築のコストが生じます。切り詰めは履歴の一部を直接取り除くもので、目標と状態、そして呼び出しと結果の対応関係を残しておく必要があります。フェーズの区切りや長さの閾値に達した時点で履歴をまとめて処理するのを優先すれば、ラウンドごとの圧縮に伴う要約呼び出し、キャッシュ再構築、そして圧縮を重ねることによる情報の欠落を減らせます。大きな成果物は外部化して必要時に読み込むか、サブ Agent で探索過程を分離したうえで、情報の欠落とコストを比較します。

**3. (★★) モデルがツール呼び出しの判断をますます担うようになる一方で、Harness もより長く複雑なタスクを支える必要があります。両者の役割はどのように変わるでしょうか。どの仕組みを簡素化でき、どの仕組みを強化すべきでしょうか。**

> モデルが直接計画を立ててツールを選べるようになれば、固定のルーティング、形式の修正、一部のヒューリスティックなプロンプトは一つずつ簡素化できます。タスクが長くなるほど、Harness はコンテキストを組み立て、ツールインターフェースを管理し、制約・検証・修正を実行する必要が高まります。強化できる仕組みとしては、権限チェック、予算とタイムアウト、重複呼び出しの検出、永続的な状態、エラー回復が挙げられます。モデルを更新するたびにタスクの比較評価を行い、どのルールを減らせるかを決めます。本人確認、認可、外部への実行は、引き続き信頼できるランタイムと環境が担います。

**4. (★★) 実験では、ツール結果が欠けていると呼び出しの繰り返しが起きました。本番システムでは、ほかにどのような原因で同様のループが生じるでしょうか。どのように検出・回復し、終了条件を設定しますか。**

> よくある原因としては、ツールが同じエラーを返し続ける、モデルが存在しない機能を繰り返し要求する、圧縮によって完了済みの状態が失われる、メッセージ形式がインターフェースの要件に合わない、タスクに必要な入力が欠けている、などがあります。ツール名、パラメータ、返り値、状態の変化を組み合わせて繰り返しの挙動を検出します。ループを見つけたら、まずエラーの原因を確かめ、そのうえで情報を補う、経路を変える、状態を復元する、といった対応をとります。ランタイムにはラウンド数、時間、費用、連続失敗回数の上限を設け、上限に達したら進捗を保存して、タスクのルールに従って終了するか引き継ぎます。

**5. (★) 日常的に使っている AI 製品を一つ選び、コンテキストに含まれる主な情報、実行できる操作、実行方策をそれぞれ書き出してください。どの段階で最も失敗しやすいでしょうか。あなたならどう改善しますか。**

> たとえば旅行アシスタントを分析してみます。コンテキストには目的地、日程、予算、ユーザーの好み、それまでの検索結果が含まれます。操作には航空便の検索、ホテルの照会、プランの修正、確認の依頼があります。実行方策としては、自律的な検索と固定の予約フローを組み合わせられます。予算を超えるプランを繰り返し勧めるようなら、予算が現在の入力に含まれているか、価格が適時に更新されているか、絞り込みのルールが実際に適用されているかを確認し、同じ旅程タスクのセットで改善を評価します。

> 同じ見積もりを 2 件の依頼で試してみることができます。2 人のユーザーがどちらも 1200 元以内の航空券を買いたいと考えており、カスタマーサービスが提示した最安値はどちらも 1250 元でした。一方の出張客は、これまでこの程度の小幅な超過に直面したとき、時間どおりに到着することを重視してきました。もう一方は家族旅行で、毎回まず総予算を計算します。2 人ともアシスタントに代理予約を任せていた場合、前者についてはその人のいつもの判断に沿って 50 元の差額を受け入れ、予約後に実際の運賃を伝えればよいでしょう。後者については、まず見積もりを送って本人に決めてもらうべきです。さらに出張客の依頼に「今回の精算上限はちょうど 1200 元」という一文が加わったなら、アシスタントは発券の手前で止まる必要があります。出張客が後になって今回の 50 元の超過は受け入れられないと言った場合は、その訂正を記憶し、次に似た見積もりに出会ったときはまず本人に尋ねます。ユーザーの返答を待つあいだ、アシスタントはカスタマーサービスに一時的な価格保証ができないか問い合わせたり、別の便を探したりすることもできます。

**6. (★★) 航空券予約のカスタマーサービス向けにフローを設計してください。どのステップがワークフローに向き、どのステップが自律 Agent に向くでしょうか。ユーザーが急に旅程を変えたとき、両者はどのように連携しますか。**

> 本人確認、注文状態の確認、価格の確認、支払い、予約は、前提条件が明確なフローとして組み立てます。要求の明確化、代替便の検索、プランの比較は自律 Agent に任せます。支払いと発券の順序や、座席確保とタイムアウトのルールは、具体的な業務インターフェースに従って実行します。ユーザーが日付を変えたら、旅程のバージョンを更新し、無効になった見積もりと実行待ちの操作を取り消してから、価格と認可を改めて確認します。返金や高額の支払いといった操作はリスクルールに従って確認を求め、受領記録で結果を確かめます。

**7. (★★★) 同じ `delete_file` ツールでも、一時ファイルの削除と重要なシステムファイルの削除ではリスクが異なります。パラメータ、リソースの範囲、復元可能性を組み合わせて、どのように動的なリスク評価を行いますか。**

> リスク評価では、ツールの種類、パラメータ、対象リソース、呼び出し元の身元、操作の結果を同時に考慮すべきです。まずサーバー側で対象パスを解析・正規化し、実際のリソースが認可された範囲内にあるかを確認したうえで、ファイルの重要度、削除の規模、バックアップと復元の能力を考えます。シンボリックリンクや、チェック後にリソースが変化するケースも、実行の段階で処理する必要があります。リスクの低い一時ファイルはルールに従って直接削除し、重要なリソースにはプレビュー、確認、削除禁止などの方策をとり、結果の記録を保存します。モデルはタスクの意図を示し、アクセス制御はランタイムが担います。

**8. (★★) オープンエンドな行動空間では、あらかじめ列挙しきれない内容と操作の組み合わせが可能になります。どのようなタスクでは、行動を少数の事前定義された選択肢に限るほうが適しているでしょうか。その制限にはどのような利点と代償がありますか。**

> 返金、支払い、アカウント状態の変更には、事前定義された操作と構造化されたパラメータが適しています。金額の範囲、状態の遷移、認可の条件を確認しやすくなるためです。選択肢を限ると無効な組み合わせが減り、テストや追跡もしやすくなりますが、新しい要求に対応する柔軟性は下がります。範囲内のタスクには明確な操作を用意し、範囲外の依頼には明確化、人による対応、管理された拡張のための入口を設け、実際のユースケースでカバー率を確認するとよいでしょう。

**9. (★★) Agent が人の確認を必要とするとき、ユーザーがオンラインでなかったり、返答が遅かったり、指示が曖昧だったりすることがあります。システムはどのような状態を保存すべきでしょうか。どの作業を続けてよく、どの操作は待たなければならないでしょうか。**

> 元の目標、完了済みの事項、確認待ちの操作、現在のパラメータ、認可の状態、関連する成果物のバージョンを保存します。すでに認可を得ていて互いに独立した作業、たとえば資料の整理などは続けてかまいません。確認が必要な支払い、削除、外部への提出は待機させます。ユーザーが選んだチャネルで通知し、リマインドとタイムアウトのルールを設けます。返答が曖昧なら引き続き明確化を求めます。実行を再開する前には価格、在庫、本人確認、環境の状態を改めて確認し、元の操作がまだ有効であることを確かめます。

**10. (★★★) モデルの進歩とともに簡素化されていくエンジニアリング手法を一つ挙げ、それがもともと何を解決していたのか、そしてその背後にあるシステム設計の原則がどのように引き続き機能するのかを説明してください。**

> たとえば、モデルが構造化された呼び出しをより安定して生成できるようになれば、JSON の修正やパラメータの補完に特化したロジックは減らせます。それでも、インターフェースの Schema 検証、認可チェック、エラー処理が引き続き呼び出しの信頼性を支えます。

> 外部知識ベースも、学習能力の変化に応じて役割分担を見直せます。安定した知識の一部はモデルのパラメータに入り、リアルタイムの更新、正確な検索、アクセス制御、出典の追跡は外部システムが担います。

> 能力のインターフェースは、大量の専用ツールから「Skill のテキスト手順 + 汎用実行器」へと広げられます。モデルがインターフェースを理解し手順に従う能力が高まれば、より多くの操作を汎用実行器で引き受けられるようになり、専用ツールの数を減らせます。モデルが手順に沿ってコマンドを生成し、ランタイムがパラメータと権限をチェックします。標準化された呼び出しは構造化されたパラメータを受け渡し、検証やシステム間の相互運用を支えます。

> プロンプトとツール定義も必要に応じて読み込めます。初期の実装では、モデルが認識して従いやすいよう、それらを固定の位置に置くのが一般的でした。指示遵守能力が高まり、動的な読み込みが学習でカバーされるようになると、Skills や動的に発見されたツールを後続のコンテキストに追加できるようになり、あらかじめ渡しておく内容を減らせます。

## 第二章 コンテキストエンジニアリング

**1. (★★★) 実験 2-3 のスライディングウィンドウの実行記録を読んでください。5 回のツール呼び出しはそれぞれ何をしたのでしょうか。呼び出しの繰り返しが履歴の切り詰めによるものかを判断するには、ほかに何を記録し、どのような対照をとる必要がありますか。重要な状態を保持する切り詰めの方式を設計し、それがプレフィックスキャッシュに与える影響を説明してください。**

> 実験 2-3 のスライディングウィンドウの記録（`result_sliding_window_20260718_kimi_k2_6.json`）では、`task` にユーザーが Python ファイルの一覧を求め、`main.py` と `agent.py` を読んだうえで三文で要約するよう指示したことが書かれています。`tool_calls` には 5 回の呼び出しが並んでいます。最初の 3 回はいずれも `find("*.py")` で、毎回 13 個のファイルが見つかりました。後の 2 回はそれぞれ指定されたファイルを 1 つ読んでいます。委託内容と照らすと、この時点ではまだ最後の三文が残っています。1 回の返答で複数のツールを要求できるため、5 件の呼び出し記録だけでは、それを 5 回のモデルリクエストに 1 対 1 で対応させることはできません。記録にはツール呼び出しが保存されていますが、各ラウンドでモデルに送った完全なメッセージは保存されていません。現在の実装では、どのラウンドでも元のタスクが添付されます。切り詰めが繰り返しを招いたかを検証するには、各ラウンドで保持したメッセージ ID と取り除いたメッセージ ID を記録し、モデル、タスク、ラウンド数の上限を固定したうえで、完全な履歴とスライディングウィンドウそれぞれの場合の繰り返し回数と完了率を比べます。
>
> 一つの方法は、既読のファイル、重要な結果、ToDo をフェーズの要約に書き入れ、長い出力はアーカイブしてインデックスだけを残し、直近のツール要求と結果を対にして保持するものです。履歴を置き換えると、変更点より後ろのプレフィックスキャッシュに影響します。変更点より前にあるシステム指示とツール定義は、引き続き再利用できる可能性があります。もう一つの方法は、ファイルの探索をサブ Agent に任せ、結論とファイルの位置だけをメインの会話に持ち帰らせるものです。

**2. (★★) Qwen3 の Chat Template は、最後の本物のユーザークエリの位置を基準に過去の思考を扱います。1 回の ReAct ループが 100 ラウンドを超えて続く場合、次第に増えていく推論内容をどのように管理しますか。過去の思考の切り詰め、返送、プレフィックスへの紐付けという各プロトコルを比較し、Harness がどう適応すべきかを説明してください。**

> まず、モデルとインターフェースのプロトコルに従って、どの推論内容を返送しなければならないかを決め、そのうえで履歴の予算を設定します。過去の推論には、まだ実行していない計画や除外済みの経路が含まれていることがあり、長いタスクほどこうした状態を残す必要があります。単純に削除すると後続の判断は根拠を失い、すべて返送すると入力量が増えます。切り詰めを許すプロトコルでは直近の推論を残し、長期の計画は状態の要約として整理できます。返送を要求するインターフェースでは、元のレスポンスのフィールドを保存しておくべきです。thinking がプレフィックスに紐付いている場合は、プレフィックスを書き換えた後、影響を受ける推論ブロックをプロトコルに従って処理するか、サーバー側の圧縮を使います。

**3. (★★) 約 15 万文字の検索資料を 2,000 文字に圧縮するとします。どの事実、関係、出典を残しますか。要約が後続の質問を支えるのに十分かはどう確認し、省略した細部はどう復元しますか。**

> 人物、時間、組織、関係、重要な根拠、未解決の課題を残し、位置を特定するための識別子はそのまま保存します。要約のための後続クエリを設計して漏れや曖昧さを確認し、元の資料はアーカイブして出典、取得時刻、読み出しの入口を保存します。リンクは位置の特定に役立ち、原文のスナップショットは長期的な再確認を支えます。

**4. (★★) ツールのカウンターが呼び出しを 1 回取りこぼし、ステータスバーが誤った残り回数を示しました。イベントの記録、集計の検証、実行層でのチェックを設計し、この不整合をどう見つけて直すかを説明してください。**

> 呼び出し回数はまずプログラムで数えます。モデルに非構造化の記録からイベントを抽出させる場合も、まず 1 件ずつ抽出し、そのうえでプログラムが集計して、長い履歴での数え漏れや二重計上を減らします。呼び出しには一意なイベント ID を付け、要求、実行、返却の状態を記録し、上限が呼び出しの試行回数に対するものか成功回数に対するものかを明確にします。冪等な更新で二重計上を避け、イベントの再生と定期的な照合で数え漏れを見つけます。実行層は信頼できるカウントに基づいて呼び出しの残量を確認し、モデルは状態を読んで計画に使います。不整合が起きたらイベント記録を保存し、集計を再構築してから続行します。出所の不明なテキストは、検証待ちの資料として扱うべきです。
>
> たとえば、実行器が呼び出し A を受け付けたあと、同じ「A を受け付けた」という通知が 2 回届いたとします。呼び出しの識別子でまとめれば、2 件の通知で消費される予算は 1 回分だけです。予算を実際の実行回数で数えるなら、別にもう一度本当に発行されたリトライには独立した実行の識別子を持たせ、元の要求に関連付けます。

**5. (★★) 実験 2-4 では、話し方、情報の構成、ツールの説明を比較しました。システムプロンプトを複数の人が長期間にわたって保守する場合、バージョンはどう管理し、ルールの衝突はどう検査し、回帰タスクで各変更をどう評価しますか。**

## 第四章 ツール

> 進捗を表示しているウィンドウを閉じ、保存したタスク番号で開き直してみるとよいでしょう。同じタスクの最新の状態が取得できれば、タスクのライフサイクルとウィンドウが切り離されていることがわかります。そのうえでタスクを明示的に取り消し、実行器が本当に止まったかを確認します。

**2. (★★) 複数の MCP サーバーが似たツールを提供している場合、どのように選ぶべきでしょうか。「一方は要約を返し、もう一方は全文を返す」という例で、ツールの説明、出所の識別、選択の根拠を設計し、Agent がこの違いを活かせるようにしてください。**

> カタログサービスが要約を返し、アーカイブサービスが全文を提供するとします。ホストは 2 つのツールにそれぞれ `catalog.summary` と `archive.read_full` という別名を付け、各別名を設定済みのサーバーの識別情報と、そのサーバーが公開しているツール名に結び付けます。説明には、それぞれが対象とする資料、返す内容、ページングの方法、更新頻度、呼び出しのコストを明記します。モデルは、多数のファイルから候補を選ぶときはまずカタログを引き、ある原文や引用の条件を確かめるときは全文を読みます。ホストは結び付けに従って振り分け、サービスのバージョンと認可の範囲を確認します。
>
> 2 つの版がある契約書で一度試してみます。要約は、アーカイブサービスでも通用する文書の識別子とバージョンを示せるでしょうか。示せるなら、それを持って対応する原文を読みます。2 つのサービスで番号が共通でなければ、出典のリンクから位置を特定し直し、バージョンを確認します。こうすれば、ツールの説明が実際の返り値と合っているかを検証できるうえ、「要約では正しく選んだのに、開いたのは別の版だった」という誤りも見つけられます。

**3. (★★) コードを書いてから検査を実行する以外に、「実行—検証—フィードバック」はどのような場面に使えるでしょうか。2 つの例を選んで検証方法、失敗時のフィードバック、コストを説明し、どのようなときに即時検証、抜き取り検証、非同期検証が適しているかを論じてください。**

> 1 つ目の例は設定の変更です。まず形式とフィールドを確認し、次に隔離された環境でサービスを起動し、ヘルス状態や動作の結果を読み取ります。失敗したときは、誤りのあるフィールド、起動時の診断、実際の状態を返し、Agent が設定を直すべきか元の値に戻すべきかを判断できるようにします。2 つ目の例はプレゼンテーション資料の生成です。ページをレンダリングし、文字がはみ出していないか、図表が重なっていないかを確認し、ページ番号と位置を生成側にフィードバックします。形式の確認はコストが低いので即座に実行できます。1 ページの本文だけを変えたなら、まず変更したページと前後のページをレンダリングすればよいでしょう。テンプレート全体を替えたなら、全ページをバックグラウンドでレンダリングし、納品前に各ページの検査結果を読み戻す価値があります。抜き取りはどのページを調べるかを決め、非同期実行はいつ結果を待つかを決めます。この 2 つの選択は併用できます。
>
> 外部への操作でも、実行結果を問い合わせられます。たとえば、メールを送信した後にサーバー側のメッセージ状態を読む、注文を作成した後に業務上の番号で記録を照会する、といった方法です。状態、受領記録、監査記録を読み取る検証用のインターフェースを選び、「受け付け済み」と「完了済み」といった意味の違いを区別すべきです。外部に影響が及ぶ場合は、事前の承認と事後の検証がそれぞれの役割を担います。

**4. (★★) 数千個のツールに向き合うとき、能動的な発見のほかに、能力をどのように組織できるでしょうか。分類されたカタログ、ワークフローのテンプレート、汎用実行器を踏まえて、一つの方式の適用条件とトレードオフを説明してください。**

> 繰り返しの多い業務では、よくあるタスクをワークフローのテンプレートとしてまとめられます。たとえば資料集約のテンプレートでは「候補を検索—本文を読む—出典を確認—レポートを生成」と定め、各ステップでは関連するツールだけを提供します。テンプレートは同時に公開する定義を減らし、ステップ間のデータの依存関係をモデルが理解する助けにもなるため、手順が安定していて入力の違いが制御できるタスクに向いています。新しいタスクに出会ったときのために、ステップを調整したりツールを補ったりする入口を残しておく必要があります。
>
> ほかの方法と組み合わせることもできます。領域ごとにカタログを組織して少数の高頻度ツールを常駐させる、詳しい使い方を Skill に書いて必要に応じて読む、汎用のコード実行器で安定したライブラリや API を呼び出して専用インターフェースの数を減らす、といった方法です。

## 第五章 Coding Agent と汎用 Agent

**1. (★★) プロジェクトのファイルを読み、依存関係をインストールし、テストを実行する必要がある Coding Agent のためにサンドボックスを設計してください。ファイル、ネットワーク、プロセス、リソースの権限をどう設定しますか。タスクが権限の拡大を必要とするとき、要求をどう表現し、範囲をどう確認し、記録をどう残しますか。**

> まず、タスクに欠かせないアクセスを書き出します。プロジェクトの作業コピーは書き込み可、参考資料は読み取り専用、依存関係は承認済みのソースから取得します。独立した実行環境でプロセス、実行時間、メモリ、ディスクを制限し、認証情報は信頼できるサービスが保管します。権限を拡大するときは、対象のリソース、操作、期限、理由を示し、実行層がそれを確認して認可を記録します。ビルド、テスト、リソース上限超過のケースで設定を検証します。

**2. (★★★) 作成者が何世代にもわたって Agent を生成・修正し続けると、フレームワークの欠陥と領域の誤りが少しずつ積み重なることがあります。参照バージョン、回帰テスト、挙動の評価、ロールバックの仕組みを使って、この変化をどう追跡しますか。**

> 参照フレームワーク、各世代の成果物、要件のバージョンをそれぞれ保存し、生成元と変更を記録します。回帰セットはメッセージプロトコル、ツールの関連付け、状態の復元、実際の領域タスクを同時にカバーし、汎化を確かめるための独立したタスクも残しておきます。その中には、十分に難しく結果を検証できるタスクを含めるべきです。簡単なサンプルでは、世代を重ねて積み重なる欠陥が隠れてしまいがちです。新旧バージョンの成功率、コスト、失敗の種類を比較し、検証を通ったものを公開します。劣化が起きたら、直近で受け入れ検査を通ったバージョンに戻します。
>
> たとえば、同じ小さなプロジェクトを同じコミットに固定し、初期版と次世代の Agent にそれぞれ同じバグを一度ずつ直させます。新しいバージョンが目的のバグを直せたとしても、既存のテストを実行し、さらに 2 つのパッチを読んで、この問題だけに向けた特例を汎用フレームワークに書き込んでいないかを確認します。

**3. (★★) ログ形式の変化は、通常のアップグレードによる場合もあれば、生成側の欠陥による場合もあります。自己適応的な解析システムはどのような証拠を残すべきでしょうか。どのような条件に基づいて、パーサーの追加、異常の報告、処理の一時停止を決めますか。**

> 元のログ、生成側のバージョン、変更の説明、旧パーサーの結果を保存します。まずインターフェースの取り決めと照らしてフィールドの意味、型、値を確認し、次に正常なサンプルと異常なサンプルで検証します。確認済みの形式アップグレードはパーサーの改訂に回します。意味の衝突、データの欠落、出所の不明な変更は問題報告に記し、必要なら関連する処理を一時停止します。新しいパーサーとアラートの記録は両方とも残してかまいません。

**4. (★★) 提案者—レビュー担当者のループで、レビュー担当者はページの情報密度が妥当だと判断したのに、ユーザーは詰め込みすぎだと感じました。ユーザーの好みを例、採点の条件、インタラクションのフィードバックにどう変換し、後続の修正が要求に合っているかをどう確認しますか。**

> ユーザーに、許容できるページと詰め込みすぎのページに印を付けてもらい、文字サイズ、余白、情報密度などの具体的な基準を作ります。レビューのフィードバックにはページ番号と問題の位置を付け、修正後は同じページを示して比較しやすくします。好みの記録にはユーザー、タスク、適用範囲を含め、後続のタスクでは範囲に応じて参照します。抜き取りで再確認すれば、レビューの基準とユーザーの体験とのずれを見つけられます。

**5. (★★) Coding Agent は知識ベース、アーキテクチャ文書、プロジェクトの指示を更新でき、操作の手順をコードとして固定することもできます。冗長なルールや古くなったルールをどう見分け、ルールに適用範囲、検証方法、退出条件をどう設計しますか。一度の成功した修正から第九章で論じる継続的進化へと発展させるには、ほかにどのような蓄積と評価の仕組みが必要でしょうか。**

> ルールごとに出所、適用範囲、検証用のケース、最後に確認した日時を記録します。重複したルールは統合し、無効になったルールはバージョンとともにアーカイブし、安定していて判定可能な要件は Linter、テスト、ツールの検証に組み込みます。たとえば、元の指示では `pnpm test` を使うよう求めていたとします。あるワークスペースでパッケージマネージャーを移行したら、まずクリーンなチェックアウトで、継続的インテグレーションのテストが新しいコマンドで通ることを確かめ、そのうえでそのワークスペースの指示を置き換えます。引き続き pnpm を使うサブプロジェクトは、元のコマンドで検証を続けます。これで古いルールの退出条件と範囲が定まります。まず過去のタスクでルールの変更を検証し、次に新しいタスクでの効果を確認します。継続的進化には、さらに実行の証拠の蓄積、候補となる修正、独立した評価、公開とロールバックを長期的なループとして組み立てる必要があります。

**6. (★) リモートでの協働に向いたチームは、たいてい Agent にとっても作業の情報を得やすい環境です。よく知っているプロジェクトの要件、アーキテクチャ、意思決定の記録、受け入れ基準を確認し、最も補う必要のある文書を挙げ、それらが Agent のどのような具体的なタスクに役立つかを説明してください。**

> 新しいメンバーが初めてプロジェクトを引き継ぐ過程を想定して点検できます。要件の背景、アーキテクチャの関係、ビルドの方法、テストの入口、受け入れの条件を見つけられるでしょうか。現在のタスクに影響する知識を優先して補います。たとえば、あるモジュールの役割を説明する、ある技術的な取捨選択を記録する、実行可能な受け入れケースを用意する、といったものです。口頭でしか伝わっていない取り決めは Agent の入力に入りにくいため、チームの日々の議論で決まったことも検索できる記録として残すべきです。文書の責任者と更新のきっかけを明確にし、コードを変更するときに関連する資料もあわせて保守します。

**7. (★★★) 非公開のデータへのアクセス、信頼できない内容の処理、外部との通信、永続的なメモリの使用を同時に行う Agent では、身元と認可、出所の印付け、データフローの検査、メモリ書き込みのレビューをどう配置しますか。通常の業務の流れを一つ使って、これらの検査の位置を説明してください。**

> 顧客情報を読んでサービス通知を送る例で考えます。身元確認のサービスがアクセスできる顧客を決め、顧客資料と外部のウェブページにはそれぞれ出所の印を付け、通信のインターフェースが宛先と送信を許すフィールドを確認します。タスクが終わったら、メモリへの書き込みについて出所、必要性、機密度、有効期限を確認します。データの読み取り、外部への送信、セッションをまたぐ保存はそれぞれ記録し、異常の再確認や無効になった認可の取り消しをしやすくします。

**8. (★★) SQL と HTML の Artifact パターンでは、モデルが成果物を生成し、実行サービスがクエリやレンダリングを処理し、画面が結果をそのまま表示します。どのような情報をあらためてモデルに解釈させるのが適しているでしょうか。クエリの権限、リソースの予算、ページの隔離、表示結果の一貫性はどう確認しますか。**

> 完全な表は実行サービスがそのまま表示でき、モデルがデータを一つずつ生成する時間と token を省けるうえ、数値の書き写しの誤りも減らせます。要約や判断が必要なときに、モデルが必要に応じて集計結果、異常な行、フィールドの説明を読みます。クエリには権限を限ったアカウントと構造の検証を使い、アクセスできるデータ、関数、実行の予算を制限します。ページは隔離された環境でレンダリングし、宣言的なコンポーネントでも属性と動作を確認します。参照クエリとページの値を突き合わせて結果を確かめ、さらに単位、日付、統計の基準を確認します。

**9. (★★) ツールはデータベース上の業務状態に基づいてルールを検証し、パラメータの説明はモデルが呼び出しを準備する助けになります。予約の取り消しを例に、自然言語のポリシー、パラメータの例、実行層の検証、境界テストがそれぞれ何を担うかを説明してください。ポリシーが変わったら、どの内容を同期して更新する必要がありますか。**

> 自然言語のポリシーは、どの条件を調べるべきかをモデルに知らせ、ユーザーに結果を説明するのにも役立ちます。ユーザーが旅程を変更する場合を例にとると、呼び出し時には `reservation_id` と `cancellation_reason="change_of_plan"` を渡します。モデルは `expected_has_insurance` を指定して自分の判断を示すこともできます。実行サービスは身元と注文への認可を確認し、データベースにある予約時刻、保険、区間の状態、そしてサーバーの時計を使って判定します。モデルは保険に加入済みと考えていたのに注文記録では未加入となっていた場合、サービスはその差異を記録したうえで、注文の事実に従って処理します。検証と確定のあいだに並行して変更が入り、判定が無効になることも防ぐ必要があります。
>
> 本文の例のポリシーに沿って、まずほかの条件を固定します。エコノミークラス、保険なし、運航は正常、すべての区間が未使用です。予約からちょうど 24 時間なら取り消しを認め、24 時間と 1 秒なら拒否すべきです。次に区間の状態だけを変えます。たとえ 2 時間しか経っていなくても、すでに使った区間があれば拒否すべきです。この 3 つの例で、時間の境界とルールの優先順位をそれぞれ確認できます。ポリシーが変わったら、説明、実行コード、パラメータの例、境界テストを同期して更新し、既存の予約にどのバージョンのポリシーが適用されるかを確認します。

## 第六章 交互：観察空間と動作空間の拡張

**1. (★★) 非同期 Agent は新しいイベントを受け取ると、それが現在のタスクとどちらを優先するかを判断する必要があります。この判断に意味の理解が関わる場合、たとえばユーザーが条件を補っているのか、すぐに停止するよう求めているのかを見分ける場合、ルールエンジンと LLM の役割をどう分けるべきでしょうか。応答時間、費用、誤判定の結果を比較してください。**

> まず、信頼できる出所とイベントの種類に応じてルールを設定します。明確な停止信号、実行器の故障、期限が来たタスクは、それぞれの処理経路に流します。自然言語に含まれる意図は分類モデルで補助的に識別し、その結果はランタイムが権限と現在の状態に従って振り分けます。ルールはコストが低く、挙動も検査しやすい一方、モデルは表現の変化に対応できますが、推論の費用、遅延、誤判定の確率が増えます。重要な停止信号は専用の経路で直接効かせられるようにし、分類のタイムアウトや結果が不確かな場合の扱いも決めておきます。外部イベントの本文は分類待ちのデータとして扱い、権限と優先度は信頼できるメタデータと振り分けの方針で制約します。
>
> 続けざまに届く 2 つのメッセージで方式を検証します。ユーザーがまず「ちょっと待って」と言い、その後にツールが見積もりを返しました。約束を伴う操作は止めつつ、見積もりは再開時に使えるよう保存しておけます。リプレイでは、停止の指示を受け取ってから実際に止まるまでのあいだに、新しい注文が入っていないかを確認します。

**2. (★★) イベントキューに 20 件のイベントがたまっています。ツールの結果が 10 件、ユーザーのメッセージが 5 件、システムのリマインダーが 5 件です。モデルがタスクの依存関係を追い、重要な変化に対応できるよう、順序、形式、処理状態をどう組み立てますか。**

## 第九章 Agent の継続的進化

**1. (★★) ある経験文書には、成功した軌跡が 3 本と失敗した軌跡が 1 本あり、失敗は新しいバージョンの API で起きています。経験が無効になったのか、適用条件が変わったのかをどう区別しますか。**

>
> 同じ経験を古いインターフェースと新しいインターフェースにそれぞれ与え、同じ入力でリプレイし、変化が疑われるパラメータだけを変えてみることができます。新しいバージョンが求めるフィールドを補えば成功が戻るなら、経験文書にはそのフィールドがどのバージョンから必須になったかを記録すべきです。

**2. (★★) カスタマーサービスの Agent で、満足度とルール違反率がともに上がりました。学習の信号をどう組み合わせ、リリース時のガードレール指標をどう設定すべきでしょうか。**

> 担当者がポリシーで認められていない返金を約束し、ユーザーがその場で高評価を付けたとします。この高評価をそのまま学習の報酬にすれば、次のバージョンは同じ約束をもっと気前よくするようになりかねません。まず 3 つの記録を突き合わせます。ユーザーがサービスをどう評価したか、そのときのポリシーが何を認めていたか、返金ツールが実際に何を実行したか、です。この例は、担当者にポリシーを説明させ、認められる代替策を探させるための教材にはなります。しかしこの高評価だけで、返金を約束したことを手本とみなすことはできません。
>
> リリースの前に、同じ一連のリクエストで新旧のバージョンを比べ、解決率、満足度、規則の範囲内での柔軟な対応、表現が簡潔かどうかをそれぞれ記録します。さらに、あらかじめ取り決めた基準で、違反、プライバシーの漏洩、権限の逸脱、根拠のない陳述、約束と実行の不一致を集計します。たとえば、両方のバージョンが返金のリクエストを 100 件受け、旧バージョンが違反の承認を 1 回、新バージョンが 4 回したとします。リリースの条件がこの違反率を上げないことなら、新バージョンはたとえ高評価が多くても通りません。

**3. (★★★) ある Agent が、操作は完了したとしばしば述べるのに、ツールの記録ではまだ実行されていません。根本原因に応じて、Prompt、Harness での確認、パラメータの学習のどれを選ぶかをどう決めますか。**

> まず、返答の時刻、ツールの要求、実行結果を照らし合わせます。モデルが正しい状態を得ているのに、不適切な完了形の言い回しを繰り返しているなら、まず明確な表現のルールと例を補えます。操作の状態をプログラムが確実に読み取れるなら、Harness で返答と状態の一致を確認し、必要に応じて修正を求めます。問題が多数のタスクや表現にまたがるなら、そのうえで多様な学習データを使って言葉と行動の整合を改善します。範囲が小さく、検証とロールバックのしやすい修正を優先するとよいでしょう。

**4. (★★★) Agent はツールと業務の検証コンポーネントを修正する必要があり、自身の更新を承認するコントロールプレーンは独立したモジュールが保守しています。両者の権限、コード、テストをどう分けますか。**

> Agent は自分のワークスペースでツールと業務の検証プログラムを修正し、権限を限ったアカウントでパッチを試行できます。評価用のケース、リリースの基準、権限の設定、監査ログ、安定版は、いずれも独立したモジュールが管理し、テスト用のアカウントにはそれらを変更する権限がありません。修正したのが検証プログラムであっても、評価はこのモジュールが行います。Agent は認可に従って診断結果を見たり、パッチを修正したりできます。承認された後は、リリース権限を持つアカウントがデプロイし、どのパッチがどのテストを通り、誰が承認したかを記録します。

**5. (★★) 経験の知識ベースが大きくなるにつれて、検索の誤りやルールの衝突が起きるようになりました。バージョン、有効期限、統合、廃止の仕組みをどう設計しますか。**

> 経験ごとに、出所の軌跡、適用条件、環境のバージョン、検証した日時、状態を記録します。衝突が起きたら、まずバージョンや場面の違いによるものかを判断し、条件ごとに分けます。同じ条件でも衝突する経験は、確認待ちのキューに入れます。重複する経験は定期的に統合し、期限切れのものや新しい証拠で覆されたものは既定の検索範囲から外し、履歴と復元の入口は残しておきます。

**6. (★★★) 医療分野のカスタマーサービスのために継続的進化の方式を設計し、モデルのパラメータ、知識、Skill、コードによる制約の分担と、それぞれの更新の検証とリリースの手順を説明してください。**

> パラメータの学習は意図の理解と表現の仕方に重点を置きます。知識ベースは審査を経たガイドライン、医薬品の添付文書、機関のポリシーを保守し、バージョンと出典を保存します。Skill は情報の収集、人への引き継ぎ、フォローアップといった手順を組み立てます。コードは本人確認、データへのアクセス制御、機関が承認した業務上の検証を実行します。まず事実の正確さ、手順の遵守、約束と行動の一致、表現の品質で軌跡を評価し、誤りが生じた段階に応じて、知識の項目、処理の手順、プログラム、学習サンプルのいずれかを修正します。医療の内容に関わる変更は専門家が審査し、新しい場面、既存のタスク、安全性のタスクで検証したうえで、段階的にリリースして異常を監視します。

**7. (★★★) ある探索方策が、過去のすべての発見木で最高点をとったのに、次の回のオンライン探索では性能が落ちました。サポート領域の偏り、ランダム性、評価への過剰適合をどう分析し、それに基づいてリプレイ用の世界をどう分割し、リリースの基準をどう設定しますか。**

> 過去の発見木がカバーしているのは、これまでの方策が実際に探索した分岐であり、新しいタスクや新しい方策は別の領域に入る可能性があります。モデルのサンプリング、ツールのノイズ、環境の変化も方策の順位に影響します。同じ木の集まりを繰り返し使って方策を選ぶと、結果がその木に偏りがちです。あるノードまでリプレイしたとき、新しい方策が選んだ動作がこの木で一度も実行されていなければ、「観測なし」と記録し、その軌跡はそこで打ち切ります。リプレイを最後まで進められた割合と、そうした軌跡での成績をそれぞれ報告し、カバーされていない分岐はオンライン検証の優先対象として挙げます。タスクの系統、時期、独立した発見木ごとに開発用、検証用、封印したテスト用の集合に分け、同じ木とそこから派生した軌跡は同じ集合に置きます。モデル、ツールのバージョン、予算を固定し、複数の乱数シードを使ってベースラインと対にして、品質、コスト、違反率、不確かさを比べます。オフラインであらかじめ定めた基準に達したら、小規模なオンラインの対照実験を行い、効果とガードレールの結果に応じて段階的にリリースし、ロールバックの条件も残しておきます。

## 第十章 マルチ Agent 協調
