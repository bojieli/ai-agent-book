# Afterword: Back to Agent = LLM + Context + Tools {.unnumbered}

This book opened with a formula: **Agent = LLM + Context + Tools**. Having worked through ten chapters, we can now place these three elements inside a system that actually runs: the model understands the task and makes decisions, the context supplies the information needed right now, and the tools gather observations and carry out actions.

Chapter 1 used this functional decomposition to build an overall picture, and then used **Agent = Model + Harness** to describe the division of labor in production implementations: the model makes decisions, while the Harness organizes the context, tool interfaces, run loop, and state, and enforces constraints, verification, and correction.

- **Building Agents (Chapters 2–6).** Context engineering organizes the information a single decision needs, while memory and knowledge bases support storage and retrieval across sessions. Tools provide interfaces for observation and action, and code generation lets an Agent write new tools and systems. The interaction chapter extends these interfaces to voice, graphical interfaces, and the physical world, and discusses ways of running that continuously receive events.
- **Evaluation and Evolution (Chapters 7–9).** Evaluation helps us compare how systems perform and find the causes of failure; post-training updates model parameters through data and environments; and continuous evolution turns operational experience into updates to knowledge, instructions, programs, or parameters, managing those changes with validation and release processes.
- **Collaboration (Chapter 10).** A multi-agent system gives its members different contexts, tools, and responsibilities, and they complete tasks together by communicating and checking one another. As the number of members grows, shared state, task dependencies, resources, and disputes also need to be managed.

Go back to the bill from the Introduction. When the representative says "we can waive that," we can find that promise in the call transcript. Only when the next statement is issued is there a second piece of evidence to check the actual reduction against. If the callback rings on the user's phone, the reference number and negotiation summary the assistant sent ahead of time become what the user relies on to pick up the matter.

Suppose the user answers the phone and still has to explain everything from the beginning. What should be changed? Start by reading the summary of the previous call. If it does not even record the amount the representative agreed to waive, the step that records the outcome of the negotiation needs improving. If the summary is clear but arrived only after the callback ended, the problem lies in the timing of the handoff. You can ask a Coding Agent to adjust the sending tool so that the summary reaches the user as soon as the previous call ends. The next time the business calls back, the user will have the whole story at hand.

## Two Clouds {.unnumbered}

In 1900, Lord Kelvin used "two clouds" to describe the difficulties facing the dynamical theory of heat and light, which concerned the motion of the ether and the equipartition of energy.[^kelvin] Borrowing the metaphor, I also see two clouds over the development of Agents: real-time interaction, and continuous learning from interaction.

**The first cloud is how an Agent can keep up with an environment that changes at any moment.** In turn-based conversation, you finish a sentence and the assistant thinks before it answers. But you may want to take back what you said the moment it leaves your mouth, and the page the assistant is consulting may already have been updated. Even when no one says anything, new email keeps arriving. The Agent I look forward to should feel "alive": it listens and thinks at the same time, speaks and thinks at the same time, starts planning when the user is only halfway through a sentence, and, guided by goals the user has set, notices on its own that "this email needs handling."

As I see it, how quickly an assistant can respond to the user and how thoroughly it can think things through are two problems that can be improved separately. When a user asks, "Is there an earlier flight?", the assistant can reply right away, but checking the flights and their change and refund conditions still takes time.

One path is **separating fast and slow paths in the architecture**. While the back end is still searching for flights, the user suddenly adds, "I have to get there before noon." The front end must be able to hear this, respond promptly, and pass the new arrival time to the back end. The back end can keep searching, or cancel queries that no longer make sense. I favor this division of labor: the front end decides when to speak and when to stop and listen, while the back end takes its time with retrieval and reasoning. Once the back end finds a new flight, it sends the result to the front end, and the front end, which is the one in the conversation, decides how to reply.

The other path is **making model inference faster**. Higher generation speed shortens the time the same reasoning takes, so within the same few seconds of waiting, the assistant has a chance to consider several more rebooking options and compare which of them arrives before noon. Xiaomi MiMo reports that, by co-optimizing FP4 quantization, DFlash speculative decoding, and the TileRT inference system, it reached a generation speed of over 1000 token/s for a trillion-parameter model on a single general-purpose 8-GPU node.[^mimo] Taalas HC1 instead uses a model-specific chip and reports a single-user generation speed of about 17000 token/s on Llama 3.1 8B.[^taalas] The two examples show, respectively, system optimization on general-purpose hardware and hardware specialized for a particular model.

When generation is fast enough, the wait in turn-based exchanges shrinks dramatically, and interaction comes closer to real-time conversation. For an Agent to keep up with a changing environment, it also needs to receive input continuously, schedule events promptly, and, when a decision changes, cancel old operations and synchronize state.

**The second cloud is how an Agent can, like a human, keep accumulating experience from the successes and failures of its interactions with the environment.** A model can acquire broad knowledge during training, yet once on the job it still has to learn about new users and new businesses. Every task brings new experience: which steps worked, which tool tends to fail, what phrasing the user accepted. If that experience is lost along with the context when the task ends, the Agent may repeat the same mistake next time. How to preserve these experiences so that an Agent gets better with use is a question that runs through Chapters 3 and 9.

How much continuous learning matters depends on how we view the knowledge a model needs to master. I sum up the two lines of thinking as the "small world" and the "big world."

The **"Small World Hypothesis"** holds that general knowledge can be absorbed by a sufficiently large model. Along this line, a model with trillions of parameters might hold an extremely broad range of knowledge and methods, and the main bottleneck is whether enough high-quality training data can be obtained. Programming offers an instructive example: vast amounts of public code, documentation, and executable tests create the conditions both for the model to learn and for its results to be checked. Industry partnerships can bring specialized tasks and experience into training, so that capabilities from more domains make their way into foundation models.

The **"Big World Hypothesis"** emphasizes the richness and variability of specific situations. A particular company's coding standards, the slide style a particular user prefers, a particular client's communication habits: all of these have to be learned through actual interaction. Such knowledge varies greatly from one individual to the next and keeps changing as organizational processes and user preferences change, so a single round of pre-training can hardly cover it in advance. The system therefore has to keep maintaining memory, knowledge, and procedures, and adjust its behavior based on feedback. Experience can first be written down as knowledge documents, instructions, or programs; after selection and validation, it can also be used to update model parameters.

When tasks extend to recursive self-improvement (RSI) and AI for Science, Agents also have to explore problems humans have not yet solved. When a conjecture fails an experiment, the Agent must be able to say which step went wrong, revise the hypothesis accordingly, and run the experiment again. Where there are no ready-made answers, even what to try next has to be learned from the results of the previous attempt. **I believe that learning and adaptation will ultimately become the model's strongest capability.**

Looking ahead to personal Agents over the next few years, how can we judge which step a new product has actually advanced? In a talk in Porto in November 2026, I broke this question down into five directions. Interaction models, fast inference, and tools that reach into the real world already have implementations that can be tried or measured. A native operating system built for humans and multiple Agents, and a continuous-learning system that learns judgment over long-term use while retaining its existing abilities, still need new designs in my view.[^porto-jarvis]

In September 2026, Meta announced its personal assistant Muse and began rolling it out to users in the United States. According to its product description, a user can ask Muse to watch for a price drop on some item and then close the app. A browser in a dedicated virtual machine keeps watching the price on the user's behalf and notifies them when it changes. If the user also wants it to make the purchase, they can first review the order it is preparing and then decide whether to buy. An assistant like this can already free people from waiting in front of a screen. But if the user later lowers their budget, will the assistant still buy the item the next time it sees a price drop? Between watching prices for someone and making judgments for them lie the user's preferences and authorization.[^afterword-muse]

Travel raises the same problem. Being able to summon the assistant on your phone at any moment solves the problem of the **entry point**. Remembering that you are traveling with your child this time, and knowing that connections cannot be too tight, reflects **context**. It can find a suitable flight, but whether it can issue the ticket depends on what **authorization** you have given it and which ways of booking the airline accepts.

## The Co-Evolution of Models and Agents {.unnumbered}

Look back at the layers upon layers of logic in a Harness: multi-level context compression, retries after failure, result verification, access control. Each layer records a difficulty encountered in real tasks. When information exceeds the input capacity, it has to be compressed; when a tool returns an error, the system has to decide whether to retry; when the model overlooks a completion condition, the result has to be verified independently; when an operation requires specific permissions, authorization checks have to be enforced. This engineering experience also tells us what models and systems should improve next.

A personal assistant's capabilities also depend on which ways of doing business merchants make available. Imagine a bill negotiation: the user authorizes the assistant to ask about prices on their behalf, and the business is willing to explain its discount terms to the assistant, but requires the account holder to confirm the change on the phone. The assistant can first settle the amount, the effective date, and any attached conditions, and then, when the account holder needs to speak, give the user a brief account of what has been agreed and which item now needs confirming. Even if the last step must be done by a person, the user is spared the earlier inquiries, waiting, and repeated explanations. If the business deals only with the account holder in person, the assistant can still gather the materials and list the questions in advance, helping the user explain everything in one go.

After the user takes the business's callback, how does the assistant pick the matter back up? Suppose the user relays: "The representative agreed to the reduction starting next billing cycle." The assistant can record this answer and check the amount once the statement comes out. If the carrier sends billing notifications, the assistant can simply check when one arrives; if the only option is to look it up proactively, the assistant can set a reminder for the billing cycle and check on progress then. What requires the account holder in person is the confirmation on the phone; the follow-up can still be left to the assistant.

This errand may also leave behind a detail worth improving: the user still had to ask from which day the reduction takes effect. First go through the transcript of the assistant's call with the representative. If the representative said only "we can waive that," the assistant should be made to ask about the effective date during the call. If the representative did state the date but the assistant keeps leaving it out of its summary, then you have a different kind of training material: pair the original words containing the date with a verified summary to form examples.

Chapter 1 raised a question: **Will models eventually eat the Harness?** My answer is: **they will eat it layer by layer, and the Harness will keep moving toward new capability frontiers.** Each time a model stably masters a capability that used to depend on external orchestration, the corresponding orchestration can be simplified. The interaction model in Chapter 6 is an example: once the model directly learns turn-taking, interjection, and voice responses, the system can drop the corresponding heuristic rules, while audio transport, execution cancellation, and state management remain the job of the runtime.

Some responsibilities, however, must stay outside the model. Business permissions are determined by trusted identities and authorization rules, budgets are enforced by the runtime and service quotas, and external operations are carried out by tools and environments.

Even if a capability can eventually be learned by the model, the business may not be able to wait for the next round of training and deployment. If a company changes its approval rules today, the assistant has to follow the new rules today; the team can change the Harness first and leave the problems that keep recurring to the next round of training. This is also one way I understand the Bitter Lesson: general methods of search and learning will keep widening their advantage, and while they gradually mature, the Harness connects current capabilities to real tasks and leaves feedback for the next round of learning.

When the same team keeps refining both the model and the product, this feedback chain can be tighter. Take Anthropic's Claude Code: model capabilities shape the design of tools and context, and problems from real use in turn point the way for subsequent improvements to the model and the system. The LangChain case introduced in Chapter 1 shows the direct payoff of systems engineering: with GPT-5.2-Codex held fixed, adjusting the Harness raised the Terminal Bench 2.0 score from 52.8% to 66.5%. Self-checks before completion, detection of repeated actions, and budget allocation all came from concrete analysis of how runs failed.

In my view, **the cycle in which real business, feedback data, and model iteration drive one another is the deepest moat of this era.** The more tightly the three are combined, the more a team can build up, out of real problems, an accumulation that others find hard to copy. Model teams should get valuable tasks and feedback into training and evaluation as quickly as possible, so that this cycle truly turns.

For application teams, my advice is this: **treat the Harness as the sharpest technical lever in the short term, and use it to buy time to build long-term advantages.** Once models master capabilities that used to require engineering to fill in, the corresponding implementations become ever easier to copy. Unique data, stable channels, user trust, network effects, and physical-world scenarios in which humans and Agents take part together all require long-term cultivation. Building a good product and serving users well is precisely how you use this time to build your own barriers.

Models, APIs, and products will keep changing, but "What information is needed right now?", "Which actions are allowed?", and "How do we verify the result?" will continue to run through system design. Understand these three questions, and you can judge where a new capability belongs, which components can be simplified, and which parts need reinforcing.

I hope this book helps you develop that kind of judgment: start from a concrete task, understand the structure of the Agent, build a system that runs, and keep improving it based on feedback. The text, illustrations, and companion experiment code are all open source. You are welcome to run the experiments yourself, try new approaches, and share what you find through issues and PRs. Agents can create tools and extend their capabilities through code, and that gives us more ways to turn our ideas into reality.

Now, go build something.
